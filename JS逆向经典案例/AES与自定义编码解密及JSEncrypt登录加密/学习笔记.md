## 一、案例一：精灵数据 —— CryptoJS AES 响应解密

**课件文件**：`01 jlsj.py`（请求端）+ `02 jlsj.js`（解密算法，同款另见 `test/01 sjjl.py` + `test/02 sjjl.js`）

### 1.1 接口与加密位置

- 接口：`POST https://vapi.jinglingshuju.com/Data/getNewsList`
- 表单参数：`page` / `num`（主文件版另有 `uid`）
- 响应 JSON 中的 `data` 字段为 **AES 密文**（base64 文本），请求本身不加密

### 1.2 课件解密代码

```javascript
const cryptoJs = require("crypto-js")

function decrypt_data(data) {
    let z = {
        "words": [1146640983, 1685607770, 896165747, 1430671430],
        "sigBytes": 16
    }
    var e = cryptoJs.AES.decrypt(data, z, {
        iv: cryptoJs.enc.Utf8.parse("DXZWdxUZ5jgsUFPF".substr(0, 16)),
        mode: cryptoJs.mode.ECB,
        padding: cryptoJs.pad.Pkcs7
    });
    return JSON.parse(e.toString(cryptoJs.enc.Utf8))
}
```

### 1.3 关键发现（离线复算得出）

1. **WordArray 形式的 key 要还原成字节**：`words:[1146640983, 1685607770, 896165747, 1430671430]` 按大端打包 4 个 32 位字：

   ```
   hex  : 44585a576478555a356a677355465046
   ASCII: "DXZWdxUZ5jgsUFPF"
   ```

   **密钥就是字符串 `DXZWdxUZ5jgsUFPF`，与 iv 完全相同**——课件故意留的"障眼法"。

2. **mode 与 iv 矛盾时以实测为准**：代码写了 `mode: ECB` 却又传了 iv（ECB 根本不需要 iv）。实测结论：
   - AES-ECB + PKCS7 解密成功（20 条数据，JSON 完整可读）
   - 按 CBC + iv 解密报 `Padding is incorrect`
   - **真实模式就是 ECB，iv 是摆设**（通常是从别的代码复制残留的）

3. **报文规模**：密文 base64 文本长 16408 字符 → 解码后 12304 字节密文。

### 1.4 Python 复刻（已验证与 Node 逐字节一致）

```python
import struct, base64, json
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

words = [1146640983, 1685607770, 896165747, 1430671430]
key = struct.pack('>4I', *words)          # 大端打包 = b"DXZWdxUZ5jgsUFPF"

ct = base64.b64decode(data)
pt = unpad(AES.new(key, AES.MODE_ECB).decrypt(ct), 16)
out = json.loads(pt.decode('utf8'))       # -> {"list": [20 条资讯...]}
```

复刻要点：`struct.pack('>4I', *words)` 模拟 CryptoJS WordArray 的大端字节序；`unpad` 对应 Pkcs7。

### 1.5 响应字段速览

解密后结构：`list[]` 每项含 `title / cover_icon / news_time / news_source / detail(详情URL) / summary / hits / news_author / article_id / relation_arr`。

## 二、案例二：扇贝单词 —— 自定义 PRNG + 字符映射编码（伪装 Base64）

**课件文件**：`03 shanbei.py`（请求端）+ `04 shanbei.js`（解密算法，650 行 webpack 产物原样提取）

### 2.1 接口与前提

- 接口：`GET https://apiv3.shanbay.com/wordsapp/user_material_books/fyjfq/learning/words/today_learning_items`
- 参数：`ipp` / `page` / `type_of`
- **需登录态**：cookies 里的 `auth_token`（JWT）+ `csrftoken`，同步带上 `x-csrftoken` 请求头与 `origin/referer`（web.shanbay.com）
- 响应整体是一段看起来像 base64、实际为**自定义编码**的密文（样本长 48263 字符）

### 2.2 webpack 产物提取套路

`04 shanbei.js` 开头做了三件事，使其能脱离浏览器在 Node 里跑：

```javascript
window = global            // ① window 挂到 global
// ② webpack 引导函数里: window.loader = o  （挂载模块加载器）
// ③ 末尾附加解密入口:
function d(t) {
    if (!_checkVersion(t)) return "";
    let a = window.loader(1)       // 模块1: 解码器类
    let u = window.loader(2)       // 模块2: 标准 Base64 库(js-base64 2.5.1)
    var e = new a.default;
    e.init(t.substr(0, 4));        // 用密文前 4 字符做种子
    var r = e.decode(t);           // 还原出标准 base64 文本
    return u.Base64.decode(r);     // 标准 base64 解码 -> 明文 JSON
}
```

模块索引备忘：`0` 工具类(loop) ｜ `1` 解码器 ｜ `2` Base64 库 ｜ `3` 入口类 ｜ `4` 位运算工具 ｜ `5` PRNG。

### 2.3 算法四步拆解

**第 1 步 · 头校验**（`_checkVersion`）：

```javascript
function i(t) { var e = t.charCodeAt(); return 65 <= e ? e - 65 : e - 65 + 41 }
// 'A'-'Z' -> 0-25；其他字符(数字) code-65+41
function _checkVersion(t) {
    return ((32 * i(t[0]) + i(t[1])) * i(t[2]) + i(t[3])) % 32 <= 1
}
```

密文前 4 字符（如 `Y7IJ`）承担"版本头"角色，不满足公式直接返回空串。

**第 2 步 · PRNG 初始化**（模块 5，MT19937 变种）：

- `seed(s)`：4 个状态字取前 4 字符 charCode（不足补 110），并记录 `_mat1/_mat2/_tmat`
- `_init()`：7 次 `status[(i+1)&3] ^= (i+1) + mul(1812433253, status[3&i] ^ (status[3&i]>>>30))`（乘子 1812433253 与标准 MT 一致）；全零保护写入 `[66,65,89,83]`（"BAYS"）；再空转 8 次 `_next_state()`
- `generate(t)`：`_next_state()` 后取 `status[3] ^ (status[0] ^ (status[2]>>>8))`，奇数时再异或 `_tmat`，最后 `% t`

**第 3 步 · 构建字符映射树**（解码器 `init`）：

```javascript
var s = "ABCDEFGHIJKLMNOPQRSTUVWXYZ234567"   // 32 个符号的"字母表"
var c = [1, 2, 2, 2, 2, 2]
init(t) {
    this._random.seed(t);                     // 前 4 字符 = 种子
    u.default.loop(64, i => {
        e._addSymbol("ABC...+/"[i], c[parseInt((i + 1) / 11)])
    });                                       // 标准 Base64 表 64 个字符逐个建映射
    this._inter["="] = "="
}
```

- 长度分配：`c[parseInt((i+1)/11)]` → 索引 0-9 映射为 **1 个符号**，索引 10-63 映射为 **2 个符号**
- `_addSymbol`：从 32 符号表**随机**摇出 1/2 个符号拼成串，作为该 base64 字符在树中的"别名"；若新摇符号落在已终结分支上则重摇（保证前缀无歧义）

**第 4 步 · 解码**（`decode`）：

```javascript
decode(t) {
    for (var e = "", r = 4; r < t.length;)        // 跳过 4 字符头
        if ("=" !== t[r]) {
            for (var n = this._head; t[r] in n.getChildren();)
                n = n.getChildren()[t[r]], r++;   // 贪心走树
            e += n.getChar()                       // 到达终止节点取回 base64 字符
        } else e += "=", r++;
    return e
}
```

**本质：种子（前 4 字符）决定整张"base64 字符 → 随机别名"映射表；同一个种子在客户端与服务端生成同一张表，服务端编码、客户端逆向建表解码——一次一密的变体。**

### 2.4 复刻陷阱（本次实际踩坑）

> 位运算工具类中 `mul` 的常量：`((4294901760 & t) >>> 0) * e`——**4294901760 = 0xFFFF0000（高 16 位掩码）**，不是 0xFF000000！
> 这是 32 位乘法的高/低 16 位分解实现。复刻时若换算错十六进制，PRNG 输出全错、映射树构建失败甚至死循环。

JS 语义等价 Python 写法：

```python
def js_mul(t, e):
    r = ((0xFFFF0000 & t) * e) & 0xFFFFFFFF
    n = ((0xFFFF & t) * e) & 0xFFFFFFFF
    return (r + n) & 0xFFFFFFFF
# and(-and(e,1), mat)  →  mat if (e & 1) else 0   （借 -1 的全 1 位模式实现条件选择）
```

## 三、案例三：贝壳找房 —— JSEncrypt RSA 登录密码加密

**课件文件**：`05 beike.js`（13486 行完整 webpack 产物）+ `test/05 beike.py`（登录请求模板）+ `test/06 beike.js`（精简可跑版）

### 3.1 登录接口与请求结构

- 接口：`POST https://clogin.ke.com/authentication/authenticate`
- body 关键字段：
  - `credential.password`：**RSA 加密后的 base64 密文**（本案例核心）
  - `credential.{username, encodeVersion:"1"}`
  - `context`：`ua / clientSource / os / osVersion / registerPos / clickPos / screen / dataId`（风控环境指纹）
  - `loginTicketId`、`srcId`（见 3.4）、`version:"2.0"`、`ticketMaxAge`

### 3.2 JSEncrypt 内置与关键源码点

`05 beike.js` 内置 **JSEncrypt 3.0.0-rc.1**（`window.JSEncrypt = it`，3633 行）。关键代码位置：

```javascript
// ① 加密实例 + 全局调试暴露点（12000 行）——逆向时可直接在控制台调用
this.ec = new a.a;
window.yuan = this.ec;

// ② 公钥设置（2506 行 RSAKey.setPublic）：
//    this.n = L(t,16); this.e = parseInt(e,16)   -> 接受 hex 形式 n/e
//    也可 setPublicKey(PEM)（JSEncrypt 3.x 走 parseKey 的 ASN.1 解析）

// ③ 加密实现（3580 行）：
t.prototype.encrypt = function (t) {
    try { return u(this.getKey().encrypt(t)) }   // u = 密文 bytes -> base64
    catch (t) { return !1 }
};

// ④ 登录流程（11215-11219 / 11640 行）：
var e = t.data.publicKey.key;          // 先请求拿到服务端下发的公钥
r.ec.setPublicKey(e);
r.passwordTicketId = ...; r.publicKey = e; r.encodeVersion = t.data.publicKey.version;
...
o.publicKey && (t.password = o.ec.encrypt(t.password));   // 密码在此处被加密
```

加密流程一句话：**请求获取 `publicKey.key` → `setPublicKey` → `ec.encrypt(password)` → 即 base64(PKCS1v15(明文))**。

### 3.3 可运行验证（test/06 beike.js）

`06 beike.js` 开头有 `document/location/window/navigator` polyfill，Node 直接可跑；结尾自带演示调用：

```javascript
console.log(":::", window.loader(62).default())
console.log(window.loader(62).ec.encrypt("123"))   // 未设公钥 -> JSEncrypt 自生成 1024 位密钥
```

实测输出 172 字符 base64（= 128 字节 = 1024 位 RSA 密文），说明：**JSEncrypt 默认 `default_key_size=1024`、`default_public_exponent=010001(65537)`；未 setPublicKey 时自动生成密钥对再加密**（因此该输出每次运行都不同、无法解密，仅作可运行性证明）。

### 3.4 顺带发现：风控参数 srcId（9171 行）

```javascript

    t: t,                          // 时间戳
    r: window.location.href,       // 当前页面 URL
    os: "web",
    v: "0.1"

```

该值用于服务端校验请求来源场景，构造登录 body 时需一并携带。

### 3.5 离线互操作验证（自造密钥对模拟服务端公钥）

由于真实登录属敏感操作，采用"本地生成 1024 位密钥对 → 注入 JSEncrypt → 三向互操作"方式验证算法等价性：

| 验证链路 | 结果 |
|---|---|
| JSEncrypt `setPublicKey(PEM) + encrypt("1234asdf")` | 输出 172 字符 base64 密文 |
| Node `crypto.privateDecrypt`（RSA_PKCS1_PADDING）解 JSEncrypt 密文 | ✅ "1234asdf" |
| Python `cryptography` 解 JSEncrypt 密文 | ✅ "1234asdf" |
| Node crypto 公钥加密 → JSEncrypt 私钥解密 | ✅ "hello-from-node" |
| Python 公钥加密"test-from-python" → JSEncrypt 私钥解密 | ✅ "test-from-python" |

**结论：JSEncrypt 3.0.0-rc.1 的 encrypt 输出就是标准 RSA PKCS#1 v1.5 + base64。爬虫侧无需调用 JS，Python 直接用 `cryptography` 即可复刻加密**：

```python
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import padding
import base64

pub = serialization.load_pem_public_key(open('public.pem', 'rb').read())
ct = pub.encrypt(b"password", padding.PKCS1v15())
password_field = base64.b64encode(ct).decode()   # 可直接放入登录 body
```

## 四、三案例方法论小结

### 4.1 定位手段对照

| 场景 | 定位路径 |
|---|---|
| 响应密文（jlsj / shanbei） | 抓 XHR → 发现响应 `data`/整体密文 → 搜 `decrypt/AES/Base64` 关键字 → 调用栈回溯到解密函数 |
| 请求参数加密（beike） | 抓登录请求 → 搜 `encrypt/setPublicKey/password` → 断点看入参出参 → 找到 `ec.encrypt` 与公钥来源 |
| webpack 产物 | 搜特征字符串/网络请求路径 → 找模块导出 → 补 `window=global` 等环境直接跑模块 |

### 4.2 算法识别经验

1. **看特征字符串**：出现 `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/` = 标准 Base64 表；出现 `A-Z2-7` 32 符号集 + "摇号"逻辑 = 自定义编码（本案例二）。
2. **看常量**：`1812433253` = MT19937 种子乘子；`010001` = RSA 公钥指数 65537；`Pkcs7` = AES 填充。
3. **矛盾点必须实测**：如案例一"ECB 却带 iv"，只有离线复算才能定论。
4. **JS 位运算按 uint32 语义复刻**：`>>> 0 / ^ / & / <<` 与 `-1` 位取反（`and(-and(e,1), m)` 等价三元）是 Python 复刻的常见坑；十六进制常量换算务必用计算器核对（`4294901760 = 0xFFFF0000` 的教训）。
