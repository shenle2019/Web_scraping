## 一、eval 函数：字符串形式的代码立即执行

**课件文件**：`01 eval函数.py`、`02 eval函数.js`

同一个表达式在两语言中的对照演示：

```python
# 01 eval函数.py
exp02 = "1 + 2 * 3 / 4 + (5 ** 2 - 8)"
print(exp02)        # 打印字符串本身："1 + 2 * 3 / 4 + (5 ** 2 - 8)"
print(eval(exp02))  # eval 把字符串当代码执行 → 19.5
```

```javascript
// 02 eval函数.js
exp02 = "1 + 2 * 3 / 4 + (5 ** 2 - 8)"
console.log(exp02)        // 字符串本身
console.log(eval(exp02))  // 19.5
```

**离线验证**：`eval("1 + 2 * 3 / 4 + (5 ** 2 - 8)")` → `19.5`（即 1 + 1.5 + 17），与课件一致。eval 的入参是字符串，返回表达式求值结果。

**逆向意义**：eval 是代码混淆的常用载体——网站把加密逻辑整体塞进 `eval("混淆字符串")`，发布出去的源码里搜不到算法明文关键字，但运行时会动态还原并执行。

- 定位手段：Sources 面板全局搜索 `eval` 打断点，或直接 hook `window.eval` 打印入参，即可拿到被执行的真实源码。

## 二、Hook 前置知识：函数调用链

**课件文件**：`03 hook函数.html`

```javascript
function foo() {
    console.log("foo功能...")
    bar(11,22,33,44,55)
}

function bar(a, b, c, d, e) {
    console.log("bar功能...")
    console.log(a, b, c, d, e)
}

foo()
```

输出：

```
foo功能...
bar功能...
11 22 33 44 55
```

调用链：`foo → bar`，参数 11~55 依次传递给 bar 的形参 a~e。

**为什么要先讲调用链**：Hook 的本质是「替换或包装某个函数，让它在被调用时执行我们自己插入的代码」。要找准 hook 点，必须先理解谁调用谁、参数如何流动——这和第 21 节的「请求堆栈回溯法」是同一套底层认知。调用链是定位加密代码的证据链，Hook 是在证据链上主动下套。

## 三、Object.defineProperty：Hook 的底层武器

**课件文件**：`04 Object.defineProperty.js`

### 3.1 普通属性的读写（不受控）

```javascript
var zhangsan = { name: "张三", age: 18 }
console.log(zhangsan.age)   // 18
zhangsan.age = 10000        // 直接改，没人拦得住
```

### 3.2 版本 1：defineProperty 重定义 age（固定假值）

```javascript
Object.defineProperty(zhangsan, "age", {
    get: function () {
        return "yuan"     // 读 age 永远返回 "yuan"
    },
    set: function (val) {
        console.log("设置已经完成,值：", val)   // 写 age 只打印，值被吞掉
    }
})

console.log(zhangsan.age)   // "yuan"
zhangsan.age = 1000         // 打印"设置已经完成,值：1000"，但没有任何存储
console.log(zhangsan.age)   // 依然 "yuan"
```

### 3.3 版本 2：闭包变量 + 校验逻辑（完整实现）

```javascript
(function () {
    var zhangsan = { name: "张三", age: 18 }
    var x = 0                              // 闭包变量：真正的存储
    Object.defineProperty(zhangsan, "age", {
        get: function () {
            return x                        // 读：返回闭包变量
        },
        set: function (val) {
            if (val > 100) {
                console.log("Error：设置的年龄过大！")   // 拦截非法值
            } else {
                console.log("设置已经完成,值：", val)
                x = val                     // 写：存入闭包变量
            }
        }
    })

    console.log(zhangsan.age)   // 0（原值 18 被遮蔽）
    zhangsan.age = 167          // 167 > 100 → 报错，x 不变
    console.log(zhangsan.age)   // 0
})()
```

**离线验证结果**（Node v24.13.0，附设 50 的合法赋值用例）：

```
初始get: 0                       # 原属性值 18 已不可达，get 返回闭包变量 x=0
Error：设置的年龄过大！           # 167 > 100，set 里被拦截
设置167后get: 0                  # 拦截后值未更新
设置已经完成,值： 50
设置50后get: 50                  # 50 ≤ 100，成功写入 x
```

**关键结论**：

1. defineProperty 重定义后，属性读写**完全走自定义 get/set**，原值（18）被遮蔽不可达；
2. get 返回的是闭包变量 —— 拦截器与原对象完全解耦，可以自由控制读写的返回值；
3. set 内可以插入任意逻辑（打印、debugger、校验），这就是 Hook 的技术底座。

**这是 Hook 的核心武器**：`document.cookie`、`window.localStorage` 等浏览器对象本质上都由 getter/setter 支持，用 defineProperty 覆盖它们的 setter，就能在「谁设置了这个值」的瞬间断下来。

## 四、Hook Cookie：定位 cookie 的生成位置

**课件文件**：`05 hook cookie.js`

```javascript
(function(){
   'use strict'
    var _cookie = "";
    Object.defineProperty(document, 'cookie', {
        set: function(val) {
            console.log(val);      // ① 打印即将写入的 cookie
            debugger               // ② 断下，顺着 Call Stack 回溯
            _cookie = val;         // ③ 存入闭包变量，保证功能不破坏
            return val;
        },
        get: function() {
            return _cookie;        // ④ 读 cookie 返回暂存值
        },
});
})()
```

**逐行拆解**：

- IIFE 立即执行 —— 粘到控制台回车即生效；
- `_cookie` 闭包变量 —— 替代原生 cookie 存储（原存储被 setter 遮蔽）；
- setter 里三步：先打印赋值内容，`debugger` 断下，再存入 `_cookie`；
- getter 返回 `_cookie`，页面的读取逻辑完全不受影响。

**使用流程**：

1. F12 → 清掉目标 cookie → 刷新页面让 cookie 重新生成前，先在 Sources → Snippets 注入脚本（或 Console 粘贴后立刻刷新）；
2. 页面触发 cookie 写入，断在 `debugger`；
3. 看 **Call Stack** 逐层回溯，找到生成/加密 cookie 的那个函数；
4. 进函数断点，观察算法与参数。

**注意点**：
- 脚本必须在目标 cookie **生成之前**注入，否则拦截不到赋值（先清 cookie 再刷新）；
- `_cookie` 只初始化一次，页面跨域或多 document 场景需重新注入。

**逆向意义**：很多网站把签名/登录态参数写进 cookie（token、sessionid 等），Hook cookie 能直接命中「谁写了它」。

## 五、Hook Header：定位请求头签名的生成位置

**课件文件**：`06 hook header.js`

```javascript
(function (){
   let set_header  = window.XMLHttpRequest.prototype.setRequestHeader
    window.XMLHttpRequest.prototype.setRequestHeader = function (header,val){
       if (header.toUpperCase()=== "hexin-v".toUpperCase()){
           debugger
       }
       return set_header.apply(this,arguments)
    }

})()
```

**逐行拆解**：

- `let set_header = ...` —— **先备份原方法**（原型上的原始函数引用）；
- 用新函数覆盖 `XMLHttpRequest.prototype.setRequestHeader` —— 所有 XHR 实例调用时都先走新函数；
- `if (header.toUpperCase() === "hexin-v".toUpperCase())` —— 只对目标请求头断点（`hexin-v` 是 同花顺/问财 的签名头，大小写归一化避免漏判）；
- `debugger` —— 命中时断下，Call Stack 回溯即找到签名生成函数；
- `return set_header.apply(this, arguments)` —— **调用原始方法，保持请求功能照常**（`apply` 保证 this 与 arguments 透传，不留痕）。

**离线验证**（Node v24.13.0 模拟 XHR 原型链）：

```
[hook命中] 拦截到 hexin-v 头，此处可下debugger      # 条件命中，插桩生效
[原始setRequestHeader] hexin-v = abc123            # 原方法照常执行
[原始setRequestHeader] Content-Type = application/json   # 非目标头直接放行
```

**Hook 三件套模板**（本案例的标准范式）：

1. 保存原函数引用；
2. 覆盖原函数，插入插桩代码（console.log / 条件判断 / debugger）；
3. `apply(this, arguments)` 调用原函数，保证原功能不破坏。

## 六、无限 debugger：网站反调试的常见写法

**课件文件**：`07 无限debugger.js`

debugger 语句在未打开开发者工具时是空操作；一旦挂载调试器就断下。网站用「反复触发 + 隐蔽写法」制造无限断点，拖着分析者。课件列举了 6 种写法（混淆程度递进）：

```javascript
// 写法1：直接写 debugger（明文，一眼可见）
debugger

// 写法2：eval("debugger") —— 藏进字符串，搜 debugger 关键字搜不到
eval("debugger")

// 写法3：setInterval 定时触发（永不停止的循环）
setInterval(function () {
        debugger;
        console.log("hello yuan")
    }, 1000
)

// 写法4：setTimeout 递归触发（每隔 1ms 重新排一次）
setTimeout(function foo (){
    debugger;
    console.log("hello world")
    setTimeout(foo,1)
},1)

// 写法5：Function 构造器（源码里没有 debugger 关键字，只有字符串参数）
Function("debugger").call()
Function("debugger").apply()
Function.constructor("debugger").call("action")
Function.constructor("debugger").apply("action")

// 写法6：原型链 + 字符串构造（最隐蔽，连 Function 关键字都不出现）
(function (){return!![]}["constructor"]("debugger")["call"]("action"))
eval('(function (){return!![]}["constructor"]("debugger")["call"]("action"))')
```

**写法剖析**：

| 写法 | 隐蔽点 | 特征 |
|------|--------|------|
| 1 直接 debugger | 无 | 搜 `debugger` 直接命中 |
| 2 eval("debugger") | debugger 变成字符串 | 搜字符串 `"debugger"` 命中 |
| 3 setInterval | 定时器包裹 | 搜 `setInterval` / `debugger` 命中 |
| 4 setTimeout 递归 | 函数名任意（foo） | 调用栈里反复出现同一函数 |
| 5 Function 构造器 | 无 debugger 明文 | 搜 `Function` / `constructor` |
| 6 原型链写法 | 全程字符串 + 属性访问 | 搜 `"constructor"` / `"call"` |

**离线验证**：6 种写法在 Node（无调试器）中全部正常执行，输出 111~666 无异常 —— 证明 debugger 语句只影响调试器挂载状态，不改变程序逻辑本身。

**实战对抗思路**（延伸，课件未展开）：

- 定位：搜 `debugger` 搜不到时，改搜 `setInterval`、`constructor`、`Function`、`"debugger"` 字符串；
- 断点粒度：Chrome DevTools 在 debugger 行右键选 **Never pause here**（或 Add conditional breakpoint 设假条件）；
- 源头覆盖：控制台重写 `setInterval = function(){}` / hook `Function` 构造器 / 替换脚本为 Overrides 本地版本把 debugger 删掉；
- 原则：先定位源码位置，再决定在哪一层去势，避免和整个页面逻辑对抗。

## 七、总结

| 技术 | 触发点 | 定位目标 |
|------|--------|----------|
| eval | eval("字符串") 动态执行 | 混淆代码的真实源码还原 |
| Object.defineProperty | 属性 getter/setter 拦截 | Hook 的底层实现原理 |
| Hook Cookie | document.cookie 的 setter | cookie 生成/加密代码 |
| Hook Header | XHR setRequestHeader | 请求头签名（如 hexin-v）生成代码 |
| 无限 debugger | 定时器 / Function 构造器 / 原型链 | 反调试干扰，需要识别与绕过 |

**Hook 模板三步法**：① 保存原方法/原属性描述符 → ② 覆盖并插入插桩（console.log + 条件判断 + debugger）→ ③ 保证原功能照常（get 返回暂存值、`apply(this, arguments)` 调用原方法）。

**与前后课程的关系**：本节是调试工具箱的补齐 —— Day21 的「请求堆栈回溯」是被动观察调用链，本节 Hook 是主动埋点拦截（cookie/header 直接断在赋值源头）；无限 debugger 的写法认知则是后续对抗反调试（如 Day23 测试站点的调试干扰）的基础。
