## 1. 阶段①：发现——这次要逆向什么？

### 1.1 操作步骤（F12 抓包）

1. 打开目标站 `https://m.cnhnb.com/`（移动端页面按 F12 后点设备仿真按钮切手机模式）。
2. F12 → **Network** → 勾选"保留日志" → 点 **Fetch/XHR** 过滤 → 刷新页面、滑动列表。
3. 在列表里找数据接口：**`POST appapi.cnhnb.com/recq/api/transform/supply/v501/index`**（供应列表）。
4. 点开它，看三个标签页（这是全流程的分岔路口）：
   - **Response**：明文 JSON（`{"code":0,...,"datas":[...]}`）→ 响应没有加密，不用逆；
   - **Payload**：`{"pageNumber":1,"pageSize":20,"ad_ch":1}` 明文 → 请求体没有加密，不用逆；
   - **Headers**：**发现一整套 `x-client-*` 自定义请求头**——有戏！

### 1.2 三看判定结果

| 看哪里 | 本例现象 | 结论 |
| :--- | :--- | :--- |
| 响应 | 明文 JSON | 响应不加密 |
| 请求体 | 明文 JSON | 请求体不加密 |
| **请求头** | 陌生字段一堆（见下） | **要逆的就是请求头签名体系** |

```
x-client-appid:  5                      ← 固定值，应用标识
x-client-page:   /hangqing/             ← 固定值，页面路径
x-client-id:     839b765-69f5-4013-9ded-d88c0d3b7   ← 设备ID（注意格式）
x-client-nonce:  5b46a5f80526296f00b3b42efcfb23b6   ← 32位hex随机数
x-client-time:   1791620276140          ← 毫秒时间戳
x-client-sid:    S_XXXXXXXXXXXXXXX      ← 链路ID，S_ + 16位36进制
x-b3-traceid:    XXXXXXXXXXXXXXX        ← 链路追踪ID，16位36进制
x-client-sign:   17401a0edd265ba9...（96位hex）  ← ★ 核心签名
x-hn-job:        If you see these message...    ← 站方"招聘信"彩蛋
```

### 1.3 确认"哪几个字段是关键"（手动对照实验）

不用猜，动手试：用 requests 逐项目复制请求头再做减法——

| 实验 | 结果 | 说明 |
| :--- | :--- | :--- |
| 原样复制全部头 | 成功 code=0 | 抓包样本足够全 |
| 删掉 `x-client-sign` | 失败 code=500301 | **sign 是服务端强校验的字段** |
| 改 sign 任意一位 | 失败 | sign 参与校验，不能伪造 |
| 删掉 `x-hn-job` | 也失败 500301 | 彩蛋头竟然也是必需的（坑，详见第 5 章） |

**结论**：核心逆向对象 = `x-client-sign`；它由 `nonce / timestamp / deviceId`（+ 内置密钥）生成。

### 1.4 保存现场（后面验证全靠它）

抓 **3 组**完整样本记下来（nonce、time、deviceId → sign 的对应关系），后续每一步验证都拿这三组对照：

| # | nonce | timestamp | deviceId |
| :-: | :--- | :--- | :--- |
| 1 | `5b46a5f80526296f00b3b42efcfb23b6` | `1791620276140` | `839b765-69f5-4013-9ded-d88c0d3b7` |
| 2 | `d5606ed185130bbc139247ee21ba5446` | `1791620277944` | 同上 |
| 3 | `1745acd57edec85ed1933f55848774e4` | `1791620279750` | 同上 |

## 2. 阶段②：定位——签名函数在哪个文件哪一行？

两条路都走一遍：关键字搜索负责"广撒网"，启动器 + 调用堆栈负责"精确制导"。

### 2.1 手法 A：关键字搜索（5 分钟入门）

1. Sources 面板 → **Ctrl+Shift+F** 全局搜索（注意用无痕/新窗口打开，缓存才干净）。
2. 搜索关键词按优先级：
   - `x-client-sign` / `X-CLIENT-SIGN`（头名，最准）
   - `x-client-nonce`、`x-b3-traceid`（同族头名）
   - `cryptoMd5`、`cryptoSha384`（哈希函数名，命中即签名处附近）
   - `secret`、`secretType`（密钥相关）
3. 命中结果里 **优先看业务打包文件**（如 `vendors.app.js`），跳过 jquery/chunk-vendors 之类的公共库。
4. 点开命中行看上下文：寻找形如 `head["X-CLIENT-SIGN"] = ...` 的赋值代码——那就是签名函数。

### 2.2 手法 B：启动器 + 调用堆栈（本案例重点）

> **启动器（Initiator，中文版叫"发起程序"）**：Network 请求详情里的 Initiator 标签页，记录"这个请求是谁（哪个 JS 的哪个函数）发起的"，点里面的文件/函数链接可直接跳到 Sources 对应代码。

手动操作 10 步：

1. Network 里**右键目标请求 → Break on → XHR/fetch**（给它下断点：只要发这个请求就自动断住）。
2. 回到页面**触发请求**（刷新/翻页）→ 页面停住，提示 "Paused in debugger"。
3. 此刻停在 **axios 之类库的"发包代码"处**——这是调用链的最后一环（"发射点"）。
4. 看右侧 **Call Stack（调用堆栈）**：从下往上是完整调用链，形如：
   ```
   发包库 send()        ← 当前断点（栈顶）
   axios 拦截器
   业务请求函数 getList()
   ...中间层...
   签名函数 sign(t, head) / 各 get_xxx 参数函数   ← 目标在下面几层
   页面初始化逻辑
   ```
5. **逐层点击栈帧**（从栈顶往下点）：每点一层，左侧源码跳到该函数、右侧 Scope/Local 显示当时的局部变量。
6. **用"数据形态"找分界**：观察 `head` 对象的 `X-CLIENT-SIGN`——
   - 在"发包层"里它是**已成品的 96 位 hex**；
   - 越往上（越靠近源头）找，某一层里它还是 `undefined`，再往下调用几步后才被赋值；
   - **赋值发生的那一层 = 签名函数**。
7. 定位到签名函数后，**在函数体第一行打断点，重新触发**，然后 **F10 步过**逐行执行，一行行观察：
   ```
   L = cryptoMd5(nonce)                          // ① 第一段：MD5(nonce)
   B = cryptoSha1(timestamp)                     // ② 第二段：SHA1(time)
   N = cryptoMd5(nonce + deviceId)               // ③ 第三段：MD5(nonce+deviceId)
   C = cryptoSha1(secret + timestamp)            // ④ 第四段：SHA1(secret+time)
   C = C.substring(C.length - 16, C.length - 1)  //    截取：注意左闭右开（15个字符！）
   D = window.v(C, true, 16).toUnsigned().toString(10)  // 十六进制→十进制大数
   F = [L, B, N, D].reduce((t,e) => t + "!" + e) // ⑤ "!" 连接四段
   sign = cryptoSha384(F)                        // ⑥ 终值：SHA384 → 96位hex
   head["X-CLIENT-SIGN"] = sign
   ```
8. **在断点行把关键值"拿下来"**：鼠标悬停变量看值，或在 Console 里敲 `nonce`、`secret`、`C` 回显。
   - 本例的密钥 `secret = "EOi^0N5sWWHhkrF2A0gekY9U20BgnAcr"`（secretType=2 生产环境）就在这里拿到。
9. **验证子函数**：在 Console 里直接 `cryptoMd5("abc")`，对比标准 MD5 值，确认算法族。
10. **导出源码**：右键函数 → Copy function definition，或把模块整段留存（下一步补环境用）。

### 2.3 本例的真实落点：vendors.app.js 的模块 311

惠农网是 webpack 打包，签名逻辑藏在 `vendors.app.js` 的**模块 311**（一个 `function(t, head)` 函数）。手动定位特色：

- 加载的 JS 是数组式打包：`(window.webpackJsonp=...).push([[30],[ ,function(t,e,n){...}, function(t,e,n){...}, ...]])`；
- 搜 `X-CLIENT-SIGN` 命中的那段代码，数它前边有几个逗号 = 它在数组里的下标 = **模块 ID 311**；
- 模块内属性名还被 **RC4 混淆**（如 `$("0x42","&J@X")` 这种"解码函数+表"），读代码时先找到它的字符串表和解码函数，或直接在浏览器断点处看**运行时的真实变量值**（比读混淆代码快得多）。

### 2.4 调试时务必记下的信息清单

| 项 | 本例记录 |
| :--- | :--- |
| 函数入参 | `(t, head)`：t 是环境对象（含 config.env、inApp、platform），head 是请求头对象 |
| 算法族 | crypto-js 的 MD5 / SHA1 / SHA384 + long.js 大数 |
| 密钥 | `EOi^0N5sWWHhkrF2A0gekY9U20BgnAcr`（secretType=2） |
| 动态参数 | nonce=32位hex（种子=时间戳+随机）、time=毫秒时间戳、traceid=时间戳36进制 |
| 拼接细节 | 四段用 `!` 连接；substring(len-16, len-1) 取 15 字符 |
| 附加头 | x-hn-job（招聘信彩蛋）、x-client-sid、x-b3-traceid 也要带上 |

## 3. 阶段③：补环境——让原站 JS 在 Node 里跑通

### 3.1 为什么要补环境

原站代码依赖浏览器特有对象（`window`、`document`、`navigator`）和 webpack 的私有 `require`，直接复制到 Node 一跑就报 `window is not defined`。**补环境 = 缺什么造什么**，让代码在 Node 产出与浏览器一模一样的结果。

### 3.2 路线 1：整段抠出 + 打补丁（课件做法，适合模块小、逻辑清晰时）

以课件 `huiNong2.js` 为例，看它"补"了哪些东西：

```javascript
window = global;                          // ① 第一句：把 Node 的 global 当 window 用
const CryptoJS = require('crypto-js');    // ② 依赖库：npm install crypto-js 引入
```

具体清单：

| 缺失项 | 补法 |
| :--- | :--- |
| `window` | 文件头 `window = global;` |
| crypto-js（MD5/SHA1/SHA384） | `require('crypto-js')`（npm 安装同名开源库） |
| long.js（大数） | 把课件里整段源码拷进来；它内部 `t.exports = r` 导出 Long、`window.v = v` 挂载入口，签名代码里正是用 `window.v(...)` 调它 |
| 内嵌 WebAssembly | **不用管**：`try/catch` 包着，Node 支持 WASM 就加速、不支持自动退回纯 JS，结果一致 |
| 函数出口 | 末尾加 `console.log(JSON.stringify(get_header()))`，或 `module.exports = { get_header }` 供外部调用 |

**验证标准**：`node huiNong2.js` 输出 9 个头，且对 3 组固定样本（喂死 nonce/time/deviceId）算出的 sign 与抓包 **3/3 一致**。

### 3.3 路线 2：mini webpack 加载器（实战做法，不抄代码）

代码上万个模块时"整段抠"不现实——把打包文件当成**数据**来加载：

```javascript
// ① 读出打包文件文本
const src = fs.readFileSync("vendors.app.js", "utf8");

// ② 截出模块数组：从 "[[30],[" 之后的 "[" 截到最后的 "]]);" 之前
const p = src.indexOf("[[30],[");
const mods = eval(src.substring(p + 6, src.lastIndexOf("]]);")) + "]");

// ③ 8 行 mini webpack：实现 webpack 自己的 require
const cache = {};
function n(id) {
  if (cache[id]) return cache[id].exports;
  const mod = { exports: {} }; cache[id] = mod;
  mods[id].call(mod.exports, mod, mod.exports, n);
  return mod.exports;
}

// ④ 全局桥：某些模块会访问 window/self/globalThis
const g = {}; g.window = g; g.self = g; g.globalThis = g;

// ⑤ 直接取模块 311，构造入参调用
const signFn = n(311).default || n(311);
const head = { "X-CLIENT-NONCE": nonce, "X-CLIENT-TIME": time, "X-CLIENT-ID": deviceId };
const t = { config: { env: "production" }, /* inApp、platform 字段按浏览器断点看到的结构补齐 */ };
const ret = signFn(t, head);   // ret["X-CLIENT-SIGN"] 就是签名
```

（本项目的 `p45_mini_webpack.js`、`p46_call_sign311.js` 即此路线的完整实现。）

### 3.4 补环境常见的坑

| 坑 | 现象 | 解法 |
| :--- | :--- | :--- |
| `window is not defined` | 直接报错 | 文件头 `window = global;` / 建全局桥 g |
| 属性名被混淆（`$("0x42"...`） | 读不懂代码 | 用它的解码函数解出真实属性名；或断点看运行时值 |
| 入参结构不对 | 结果与浏览器不一致 | 在浏览器断点处打印 `t` 的完整结构，缺啥补啥（如 `t.config.env="production"`） |
| 模块找不到 | `n(311)` 报错 | 确认截取数组的起止下标；打印 `mods.length` 核对 |
| 结果不一致 | 差一两位 | 回到阶段②，逐一核对入参字段名与大小写 |

## 4. 阶段④：纯算——用 Python 重写算法

### 4.1 把 JS 算法"翻译成人话"

对着阶段②抄下的 6 行，逐行翻译（**这一步禁止跳步**，每行都要能对上）：

| JS 原句 | 人话 | Python |
| :--- | :--- | :--- |
| `L = cryptoMd5(nonce)` | nonce 求 MD5，32位hex | `hashlib.md5(nonce.encode()).hexdigest()` |
| `B = cryptoSha1(timestamp)` | 时间戳求 SHA1，40位hex | `hashlib.sha1(ts.encode()).hexdigest()` |
| `N = cryptoMd5(nonce + deviceId)` | 拼接后求 MD5 | `hashlib.md5((nonce+did).encode()).hexdigest()` |
| `C = cryptoSha1(secret + timestamp)` | 密钥+时间戳求 SHA1 | `hashlib.sha1((sec+ts).encode()).hexdigest()` |
| `C.substring(len-16, len-1)` | **取后 15 个字符**（左闭右开） | `C[len(C)-16 : len(C)-1]` |
| `window.v(C,true,16).toUnsigned().toString(10)` | 十五进制串→十进制大数 | `str(int(C15, 16))` |
| `[L,B,N,D].reduce((t,e)=>t+"!"+e)` | "!" 连接四段 | `"!".join([L,B,N,D])` |
| `sign = cryptoSha384(F)` | 终值，96位hex | `hashlib.sha384(F.encode()).hexdigest()` |

### 4.2 long.js 大数怎么纯算（本案例的标志性难点）

- JS 为什么用它：15 位 hex 最大约 60 bit（最大值 ≈ 1.15e18），**超过 JS 安全整数 2^53-1 ≈ 9e15**，`parseInt` 会丢精度 → 签名必错；
- Python 天生任意精度整数，**一行顶替**：`D = str(int(C, 16))`；
- 两个易错点：
  1. `substring(len-16, len-1)` **左闭右开，取的是 15 位不是 16 位**；
  2. D 必须走"大数转十进制"，不要经过 float。

### 4.3 Python 纯算核心（与 JS 逐行对照，共 6 行）

```python
import hashlib

SECRET = "EOi^0N5sWWHhkrF2A0gekY9U20BgnAcr"   # 来自断点处 secretType=2

def make_sign(nonce: str, timestamp: str, device_id: str) -> str:
    L = hashlib.md5(nonce.encode()).hexdigest()
    B = hashlib.sha1(timestamp.encode()).hexdigest()
    N = hashlib.md5((nonce + device_id).encode()).hexdigest()
    C = hashlib.sha1((SECRET + timestamp).encode()).hexdigest()
    D = str(int(C[len(C) - 16: len(C) - 1], 16))     # 后15位hex → 十进制
    return hashlib.sha384("!".join([L, B, N, D]).encode()).hexdigest()
```

### 4.4 双路验证（必做，本目录规范）

| 路线 | 做法 | 通过标准 |
| :--- | :--- | :--- |
| Node 原版 | 补环境后的 JS 对 3 组样本计算 | 3/3 与抓包一致 |
| Python 纯算 | 上面 6 行对同样 3 组样本计算 | 3/3 与抓包一致 |
| 交叉 | Node 结果 == Python 结果 == 抓包样本 | 三者全等才收工 |

## 5. 阶段⑤：实现——组装爬虫并交付

### 5.1 动态参数一次生成（Python 版）

| 参数 | 生成规则 |
| :--- | :--- |
| nonce | `secrets.token_hex(16)`（32位hex，每次随机） |
| timestamp | `str(int(time.time() * 1000))`（毫秒） |
| deviceId | **7-4-4-4-9 位 hex 格式**（`secrets.token_hex(14)` 再按位插连字符） |
| traceid / sid | 时间戳转 36 进制补 9 位 + 随机数转 36 进制补 7 位；sid 加 `S_` 前缀 |
| sign | 用 5 分钟前刚写好的 `make_sign(nonce, ts, did)` |

### 5.2 组装请求头 + 发请求（骨架）

```python
nonce = secrets.token_hex(16)
ts = str(int(time.time() * 1000))
did = rand_device_id()
headers = {
    "accept": "application/json, text/plain, */*",
    "content-type": "application/json",
    "origin": "https://m.cnhnb.com", "referer": "https://m.cnhnb.com/",
    "user-agent": H5_UA,
    "x-client-appid": "5", "x-client-page": "/",
    "x-client-id": did, "x-client-nonce": nonce, "x-client-time": ts,
    "x-client-sign": make_sign(nonce, ts, did),
    "x-b3-traceid": trace_id, "x-client-sid": "S_" + sid,
    "x-hn-job": X_HN_JOB,          # ← 必需！见 5.3
}
resp = requests.post(API_URL, headers=headers, json={"pageNumber": 1, "pageSize": 20, "ad_ch": 1})
```

### 5.3 500301 排障实录（本案例最有价值的坑）

现象：签名自测全对，但 Python 直连仍报 `code=500301`。**对照实验法**排查：

| 实验 | 操作 | 结果 | 结论 |
| :--- | :--- | :--- | :--- |
| 1 | 与浏览器请求头逐项 diff | 发现少 `x-hn-job` | 补上后仍失败，继续查 |
| 2 | 用抓包样本的 deviceId 写死 | 仍失败 | deviceId 不是本次失败主因 |
| 3 | 补齐 `x-hn-job` | 成功 | **坑 1：x-hn-job 必需**（内容为站方招聘信彩蛋） |
| 4 | 换随机 deviceId（标准 uuid4 格式） | 失败 | 格式被服务端校验拒绝 |
| 5 | 换 **7-4-4-4-9** 位 hex 的 deviceId | 成功 | **坑 2：deviceId 格式必须 7-4-4-4-9** |

**教训**：签名一致 ≠ 请求通过；服务端还有非签名因素（额外必填头、字段格式校验）。排障要用"固定其他变量、只换一项"的对照实验。

- 实测（2026-10-10）：3 页 59 条真实供应数据，每页 code=0；
