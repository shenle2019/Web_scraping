## 一、Proxy 基础：属性读写的中介层

**课件文件**：`01 proxy代理.js`

```javascript
yuan = { name: "yuan", age: 18, height: 193 }

yuan = new Proxy(yuan, {
    get: function (target, p, receiver) {
        console.log("get:::", target, p, target[p])
        return target[p]                 // 读：转发给原对象
    },
    set(target, p, newValue, receiver) {
        console.log("set:::", target, p, newValue, receiver)
        // return target[p] = newValue   // 课件注释掉的写法：赋值表达式返回恒真
        return Reflect.set(target, p, newValue);  // 规范写法
    }
})
console.log(yuan.name)   // 触发 get
console.log(yuan.age)    // 触发 get
yuan.age = 19            // 触发 set
console.log(yuan.age)    // 触发 get → 19
```

**离线验证输出**（Node v24.13.0）：

```text
get::: { name: 'yuan', age: 18, height: 193 } name yuan
yuan
get::: { name: 'yuan', age: 18, height: 193 } age 18
18
set::: { name: 'yuan', age: 18, height: 193 } age 19 { name: 'yuan', age: 18, height: 193 }
get::: { name: 'yuan', age: 19, height: 193 } age 19
19
```

**关键记录点**：

- `get(target, p, receiver)`：读取任意属性都先进陷阱，`target` 是**原始对象**（不是代理），`receiver` 是代理本身；
- `set(target, p, newValue, receiver)`：写入前先进陷阱；**必须 `return Reflect.set(target, p, newValue)`** 才能完成真实写入并满足 `[[Set]]` 语义。若写成 `target[p] = newValue`，赋值表达式返回恒真值，在原型链/继承场景下可能产生 `receiver` 不一致，所以课件注释掉它改用 `Reflect.set`；
- 若 `set` 陷阱不返回真值（或返回 falsy），严格模式下赋值会抛 TypeError；
- **逆向意义**：Proxy 是补环境调试的"监控摄像头"——把 `window`/`document` 等环境对象包一层代理，目标脚本读取了哪些环境属性、写了什么值，全部被记录，用于**报错驱动地定位缺失的环境字段**（对应第四节 SetProxy）。

## 二、Node 全局对象与 `window = global` 的桥接

**课件文件**：`02 test.js`

```javascript
console.log(global)
```

**关键记录点**：

- Node 没有浏览器里的 `window`；Node 的全局对象叫 `global`（浏览器是 `window`，ES 标准统一叫 `globalThis`，三者只是宿主不同名字不同）；
- Node 的 `global` 上挂着 `process`、`Buffer`、`setTimeout`、`console`、`require` 等，与浏览器 `window` 上挂 `document`、`navigator`、`location` 完全不同——**这就是必须"补环境"的原因**；
- 补环境脚本第一行 `window = global`：sloppy 模式下等于在全局对象上建了自引用的 `global.window = global` 属性。此后源码里所有 `window.xxx` 读写都落到 Node 全局对象上，`window` 成了 `global` 的别名；
- 紧接着的 `delete global` 见下一节。

**补环境原则（关键记录点）**：

3. **能跑通 ≠ 补全**：脚本可能只是"没检查到"某个字段，真实站点升级后可能新增检测点；
4. **用代理监控兜底**：不确定缺什么时，直接上下一节的 SetProxy。

## 四、SetProxy：用 Proxy 给环境对象装监控

**课件文件**：`xhs/env.js`（第 70-96 行）

```javascript
function SetProxy(proxyObjs) {
    for (let i = 0; i < proxyObjs.length; i++) {
        const handler = `{
          get: function(target, property, receiver) {
          if (property!="Math" && property!="isNaN"){
             if (target[property] && typeof target[property] !="string" &&  Object.keys(target[property]).length>3){
              }else{
            console.log("方法:", "get  ", "对象:", "${proxyObjs[i]}", "  属性:", property, "  属性类型：", typeof property, ", 属性值：", target[property]);}}
            return target[property];
          },
          set: function(target, property, value, receiver) {
            console.log("方法:", "set  ", "对象:", "${proxyObjs[i]}", "  属性:", property, "  属性类型：", typeof property, ", 属性值：", value, ", 属性值类型：", typeof target[property]);
            return Reflect.set(...arguments);
          }
        }`;
        eval(`try {
            ${proxyObjs[i]};
            ${proxyObjs[i]} = new Proxy(${proxyObjs[i]}, ${handler});
        } catch (e) {
            ${proxyObjs[i]} = {};
            ${proxyObjs[i]} = new Proxy(${proxyObjs[i]}, ${handler});
        }`);
    }
}

SetProxy(["window", "document", "location", "navigator","localStorage"])
```

**设计剖析**：

| 设计点 | 原因 |
|--------|------|
| handler 写成字符串 + `eval` 动态构造 | 把对象名（`"对象: window"`）直接注入日志文案——字符串模板 `${proxyObjs[i]}` 在构造时就完成替换（课件选择的实现方式） |
| 降噪条件 `target[property] && typeof != "string" && Object.keys(target[property]).length > 3` | 目标值是"键数超过 3 的对象"时不打印——避免刷屏式打印大对象；字符串/小对象/基础类型正常打印 |
| 跳过 `Math` / `isNaN` | VM 高频访问这两个全局对象，打印无意义且刷屏 |
| `set` 用 `Reflect.set(...arguments)` | 把 `(target, property, value, receiver)` 四参原样透传，保证 `receiver` 语义 |
| `eval` 里的 `try/catch` 回退 | 对象未定义时（如某些环境无 `localStorage`），catch 里先用 `{}` 建对象再包装，保证后续代码有对象可读 |

**离线验证**（简化 demo 复刻降噪逻辑）：

```text
--- 读取 small（2 键，应打印）---
[LOG] get  属性: small  类型: object  值: { a: 1, b: 2 }
--- 读取 big（4 键，应静默）---
--- 读取 name（字符串，应打印）---
[LOG] get  属性: name  类型: string  值: xhs
--- 写入 name（set 陷阱应打印）---
[LOG] set  属性: name  新值: xhs-v2
[LOG] get  属性: name  类型: string  值: xhs-v2
写后读取 name = xhs-v2
```

验证结论：4 键对象被静默、字符串和小对象正常打印、`set` 陷阱后 `Reflect.set` 使写入真实生效——与设计预期一致。

**工作流**：`跑 → 报错 → 补字段 → 用 SetProxy 监控 → 再跑`。监控日志里出现 `对象: window 属性: xxx` 说明 VM 读取了 xx 字段，如果报错就补上对应字段，循环直到脚本跑通——这就是"缺什么补什么"的可观测版本。

## 五、JSVMP：source.js 虚拟机保护结构解析

**课件文件**：`xhs/source.js`（537 行，约 10.5 万字符）

**什么是 JSVMP**：JS Virtual Machine Protection（JS 虚拟机保护）。站点把核心算法"编译"成自定义字节码，运行时用解释器（虚拟机循环）逐条还原执行。静态看源码只能看到"指令分发器"，**看不到算法明文**——比 eval 混淆、OB 混淆更高一级。

**source.js 三层结构**：

```javascript
(function () {
    function Sanji() {
        var _ace_2725e = 2147483647, _ace_a72ba = 1, ...   // 解释器主循环/指令函数
        function _ace_8cba0() { /* 从字节码取指令 → 分发执行 */ }   // 虚拟指令函数们
        ...
    }
    ;Sanji()(window, {
        "b": "BQEKAQgNBwEHAg0CAQcDDQIBBwQNAgEHBQ0C...",   // 字节码（约 10 万字符 base64 串）
        "d": [ "Q","W","E","R","T","Y","U","I","O","P",   // 常量池：自定义字母表（键盘序）
               1732584193, 271733879, 1732584194, 271733878, ...  // MD5 算法初始化常量 + T 表
               "window", ..., "isNaN", ..., "JSON", ..., "undefined", ..., "+", "-", "|", ";", ":" ]
    });
})()
```

**常量池特征（本机 grep 实测）**：

| 特征 | 含义 |
|------|------|
| 自定义字母表 `Q W E R T Y U I O P...`（标准键盘序） | 签名结果自定义编码的码表（可能用于 payload 的字符映射） |
| `1732584193, 271733879, ...` 等数值 | MD5 初始化常量（`0x67452301` 家族）与 64 个 T 表常量 → **签名内核为 MD5 家族算法** |
| 字符串 `"window"` `"isNaN"` `"JSON"` `"undefined"` | VM 的环境自检清单：挂载时逐项探测运行环境 |
| `"|"` `";"` `":"` 等运算符字符 | 参数拼接分隔符 |
| 无 `"webmsxyw"` 明文 | **API 名由 VM 运行时动态装配**，直接搜函数名搜不到（本机 grep 零命中） |

**调用形态**：`Sanji()` 返回"解释器实例"，实例再以 `(window, {b, d})` 为参数挂载——把字节码运行环境锁定为 `window`，随后在 `window` 上装配出 `_webmsxyw` 等方法。

**逆向策略（关键记录点）**：对 JSVMP **不硬剖字节码**，而是补全环境后**黑箱调用**——给 `window._webmsxyw(c, i)` 喂正确的参数，拿返回的签名。source.js 无任何网络调用（本机 grep `XMLHttpRequest|fetch|axios|require` 零命中），是纯本地计算代码，可安全离线运行。

## 六、★Node 24 运行崩溃实录：`delete Buffer` + undici 惰性物化（本机实战定位）

本节是课件在 Node 24 上跑不通时的完整排查过程，也是全篇含金量最高的踩坑记录。

### 6.1 现象

```text
$ node xhs.js
（零输出，进程直接崩溃）
```

放大堆栈后拿到：

```text
ReferenceError: Buffer is not defined
    at lib/dispatcher/client-h1.js (undici:6975)      ← var EMPTY_BUF = Buffer.alloc(0)
    at lib/dispatcher/client.js → lib/dispatcher/pool.js → lib/dispatcher/agent.js
    at lib/global.js                                   ← undici 打包模块加载链
    ...
    at Object.keys (<anonymous>)
    at Object.get (eval at SetProxy (env.js:86:14))
    at _ace_8cba0 (source.js:85)
    ...
    at source.js:531:13                                 ← Sanji()(window, {...}) 挂载点
```

### 6.2 根因链条（三条线索汇聚）

1. **删除点**：`env.js` 第 5 行 `delete Buffer`——Buffer 被删；
2. **加载链**：Node 20+（含本机 v24.13.0）把 `Headers` / `Request` / `Response` / `FormData` / `WebSocket` / `CloseEvent` / `MessageEvent` 这 7 个 Web 全局**做成惰性物化**：初次"触及"才加载 undici 打包模块（`lib/global.js → agent → pool → client → client-h1`）。而 `client-h1.js` 模块顶层执行 `var EMPTY_BUF = Buffer.alloc(0)`——此时 Buffer 已被删，抛 ReferenceError；
3. **触发器**：`SetProxy` 的 get 陷阱里有 `Object.keys(target[property])`。JSVMP 挂载时第一条虚拟指令就读 `window.window`（`source.js:85`，本机插桩日志 `[TRAP-GET] window` 实证），由于 `window.window` 自引用回代理自身，陷阱实际执行了 **`Object.keys(对 global 的 Proxy)`** → 对每个 own 键读取属性描述符 → 读到 `Headers` 惰性属性的描述符时触发物化 → 崩溃。异常从陷阱穿出、VM 未捕获 → 进程死。

**为什么之前"零输出"**：陷阱里的 `console.log` 走异步 stdout，崩溃时来不及 flush，所以看不到任何日志——排查时要换 `fs.writeSync(2, ...)` 同步写 stderr。

### 6.3 定位方法论（可复用组合拳）

| 手段 | 作用 |
|------|------|
| `Error.stackTraceLimit = 200` | 放大堆栈，从 VM 的虚拟帧里找到真实宿主帧（`SetProxy` 的 `Object.keys`） |
| get 陷阱插桩 `fs.writeSync(2, "[TRAP-GET] " + property)` | 记录 VM 读的第一个被代理属性 → 钉死触发属性 `window` |
| 子进程变体对照（8 例） | 在删除 Buffer 后，逐一测试各操作是否触发崩溃，精确定位最小触发条件 |

**变体对照表**（每例独立子进程）：

| 变体 | 操作 | 结果 |
|------|------|------|
| A | `delete Buffer` → `Object.keys(globalThis)` | OK（安全） |
| B | `delete Buffer` → **对 global 的 Proxy 做 `Object.keys`** | **THROW `Buffer is not defined`** |
| C | 先 `getOwnPropertyNames` 预加载 → B 流程 | THROW（预加载无效） |
| D | `delete Buffer` → `Object.getOwnPropertyNames(globalThis)` | OK |
| E | `delete Buffer` → `getOwnPropertyNames(代理)` | OK |
| F | `delete Buffer` → `'Headers' in globalThis` | OK（不触发物化） |
| G | `delete Buffer` → `Object.getOwnPropertyDescriptor(globalThis, 'Headers')` | **THROW（证实"读描述符即物化"）** |
| H | 先访问 `fetch` 预加载 → B 流程 | THROW（访问 fetch 不算有效预加载） |

结论：**触发条件 = 对 global 的代理做 `Object.keys`（或直接读惰性属性的描述符）**；而直接 `Object.keys(globalThis)`、`getOwnPropertyNames`、`in` 运算符都安全。变体 G 的崩溃反证了 B 的机制解释：`Object.keys(proxy)` 会对每个键做 `[[GetOwnProperty]]` → `getOwnPropertyDescriptor(global, "Headers")` → 物化。

### 6.4 修复方案（本机验证两次跑通）

在 `require` 补环境脚本**之前**预加载 undici 懒惰全局（此刻 Buffer 还在，undici 正常加载完成）：

```javascript
// fix_xhs.js 修复包装器（对课件零侵入）
// ① 预加载 undici 懒惰全局（此刻 Buffer 仍在，undici 完成初始化）
void globalThis.Headers;

// ② 课件原始流程：补环境 + 挂载 JSVMP
require("./env.js");
require("./source.js");

// ③ 原样调用签名
let c = '/api/sns/web/v1/homefeed'
let i = { /* 与 xhs.js 相同的 body */ }
console.log(get_headers(c, i))
// 输出: {"X-s":"XYW_eyJzaWduU3ZuIjoiNTEi...","X-t":1791877456185}
```

**验证过无效的方案**：`Object.getOwnPropertyNames` 预加载（变体 C）、访问 `fetch` 预加载（变体 H）——都会崩溃。

**通用启示**：

1. 补环境脚本删 `Buffer`/`process` 等 Node 核心全局**之前**，先物化 undici 全家（`void globalThis.Headers`）；或干脆保留 Buffer（多数签名脚本并不需要删）；
2. 陷阱里排查日志用 `fs.writeSync(2, ...)` 同步写，别用 `console.log`；
3. 课件跑不通先复现再归因——本次崩溃的锅是"Node 大版本升级引起的运行环境变化"，**不是签名算法本身**，算法在修复后原样跑通。

## 七、X-s / X-t 签名结构与离线验证

**入口链路**（`xhs.js`）：

```javascript
require("./env")        // 补环境
require("./source")     // 挂载 JSVMP（挂载后 window._webmsxyw 可用）

let c  ='/api/sns/web/v1/homefeed'          // 参数 1：接口路径
let i  = { cursor_score: "", num: 35, refresh_type: 1, note_index: 27, ... }  // 参数 2：请求体

function get_headers(c, i){
     return window._webmsxyw(c, i)          // 黑箱调用 VM 装配出的签名函数
}
console.log(get_headers(c, i))
```

**签名输出**（本机离线实测）：

```json
{"X-s":"XYW_eyJzaWduU3ZuIjoiNTEiLCJzaWduVHlwZSI6IngxIiwiYXBwSWQiOiJ4aHMtcGMtd2ViIiwicGF5bG9hZCI6IjQ1MDlkOGVk...","X-t":1791877456185}
```

**X-s 结构解码**（`XYW_` 前缀 + base64(JSON)）：

```text
X-t = 1791878052355  对应时间 = 2026-10-13T07:54:12.355Z   ← 毫秒时间戳（随运行时刻变化）
X-s 全串长度 = 604  前缀 = XYW_eyJzaWdu...
解码后 JSON 字段 = {"signSvn":"51","signType":"x1","appId":"xhs-pc-web"}
payload 长度 = 384  前 32 位 = 4509d8ed4632e9b986d8805a964765e4
```

| 字段 | 值 | 含义 |
|------|-----|------|
| 前缀 | `XYW_` | 签名格式标识 |
| `signSvn` | `"51"` | 签名版本（站点新版通常为 `"52"`，本课件版本为 51） |
| `signType` | `"x1"` | 签名类型 |
| `appId` | `"xhs-pc-web"` | 应用标识（与 cookie 中 `xsecappid` 对应） |
| `payload` | 384 个 hex 字符（192 字节） | 签名核心值；结合常量池中的 MD5 初始常量与完整 T 表，可判断内核为 MD5 家族算法（具体的多段组合方式由 VM 内部逻辑决定，本笔记不展开） |

**关键记录点**：X-s 的 base64 段是**明文 JSON 结构**——这是快速识别"签名版本升级"的窗口：旧代码签名失败时，先解码 X-s 看 `signSvn` 是否变化。

## 八、execjs 联调（xhs.py 关键点）

**课件文件**：`xhs.py`、`test.py`

```python
# xhs.py 核心链路
add_headers = execjs.compile(open("./xhs.js").read()).call("get_headers", "/api/sns/web/v1/homefeed", json_data)

headers["x-s"] = add_headers["X-s"]
headers["x-t"] = str(add_headers["X-t"])

data = json.dumps(json_data, separators=(",", ":"))
response = requests.post('https://edith.xiaohongshu.com/api/sns/web/v1/homefeed',
                         cookies=cookies, headers=headers, data=data)
```

**三个一致性要点（关键记录点）**：

1. **紧凑 JSON**：`json.dumps(data, separators=(",", ":"))` 去掉默认的空格（`test.py` 就是为此做的演示：`{"a":1,"b":2}` vs 默认 `{"a": 1, "b": 2}`）。**发给服务器的 body 与喂给签名函数的 body 必须是同一份字符串**，否则签名对不上；
2. **execjs 原理**：PyExecJS 默认后端是 NodeRuntime——调用本机 `node` 执行 JS 文件，`compile(js源码)` 得到上下文，`.call("函数名", *args)` 跨语言调用。本机当前未安装（`pip install PyExecJS` 即可），本次采用等价方案：**直接用 Node 跑修复包装器输出签名**，与 `execjs.compile().call()` 效果一致；
3. **签名头大小写**：`headers["x-s"]` / `headers["x-t"]` 小写键（requests 头字段大小写不敏感）；`x-s-common` 是另一个静态签名头，课件中直接复制的固定值。

**合规声明**：本笔记仅记录加密算法逆向的学习过程；所有签名验证均为**离线本地计算**；课件中的 cookie、web_session 等账号凭证不复制、不入库；不对真实站点发起任何请求（xhs.py 的 requests 部分仅作流程理解）。

## 九、总结

| 技术 | 作用 | 关键点 |
|------|------|--------|
| Proxy get/set 陷阱 | 属性读写的监控与拦截 | `Reflect.set(...arguments)` 透传；陷阱里 target 是原对象 |
| `window = global` | 把浏览器 window 名桥接到 Node 全局 | 配合 `delete global` / `delete Buffer` 抹掉 Node 特征 |
| 补环境六件套 | 让 JSVMP 以为自己在浏览器里 | window / document / navigator / location / screen / external / localStorage；报错驱动、值要真实 |
| SetProxy 代理调试法 | 可观测的"缺什么补什么" | eval 拼 handler、>3 键降噪、catch 回退 `{}` |
| JSVMP | 字节码虚拟机保护，隐藏算法明文 | 不剖字节码，补环境黑箱调用；常量池暴露算法线索（MD5 常量） |
| X-s / X-t 签名 | 小红书接口签名头 | `XYW_` + base64(JSON{signSvn/signType/appId/payload})；X-t 毫秒时间戳 |
| execjs | Python 调用 Node 执行 JS 签名 | 紧凑 JSON 一致性；body 与签名输入同一份 |
| ★delete Buffer 坑 | Node 20+ 下补环境脚本崩溃 | undici 惰性物化在 `Object.keys(proxy)` 时触发 → 预加载 `void globalThis.Headers` 修复 |

**补环境调试工作流**：直接跑 → 读报错 → 补缺失字段 → SetProxy 挂监控看 VM 读了什么 → 再跑循环收敛 → 签名通过后移除代理（监控有性能损耗）。

**与前后课程的关系**：Day25 的 eval/Hook 是"主动埋点观察调用链"，本节的 Proxy 代理是同一思想的升级——把整个环境对象变成可观测的；补环境是从"纯算复刻"（Day24）分出的工程化路线：面对 JSVMP 这类剖不动字节码的目标，**补环境黑箱调用**是性价比最高的还原方式。

**验证说明**：本笔记中 `01 proxy代理.js` 的 get/set 输出、SetProxy 降噪逻辑（demo 复刻）、env.js 补环境在 Node v24.13.0 下的完整运行（含 delete Buffer 崩溃复现、8 变体对照定位、修复包装器两次签名成功）、X-s base64 结构解码（604 字符、payload 384 hex）、source.js 常量池特征（MD5 常量、键盘序字母表、无 webmsxyw 明文）均已在本地离线验证通过，结论与课件演示一致。
