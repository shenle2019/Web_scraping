# Playwright vs 补环境 JS 逆向：两条路线的实测对比

> 本文所有数据均来自本目录脚本实测（`31_pw_vs_env_bench.py` 等），目标均为本地 mock 站。
>
> 结论先行：两者不是替代关系——**补环境赢在「轻量与可复刻」，Playwright 赢在「环境全真与开发效率」**，工程上的正解通常是「用 Playwright 快速摸清与验证，用补环境做稳定复刻上线」。

## 一、本质区别

| 维度 | 补环境 JS 逆向 | Playwright |
|---|---|---|
| 核心原理 | 用 Node **假装成浏览器**，让目标 JS / JSVMP 在 Node 里跑 | 直接启动**真浏览器**，让目标 JS 在原生环境里跑 |
| 环境来源 | 手工声明（navigator / document / cookie... 逐个补） | 浏览器原生提供（真实 Canvas / 存储 / UA） |
| 环境出错的表现 | **静默降级**：不报错，签名也可能"看着像"（本案例：cookie 不齐 → 272 位简化签名） | 环境天然正确；坑多在自动化痕迹（webdriver / Headless 特征） |
| 调试方式 | 代理 / 监控器打访问日志，对着报错逐个补 | DevTools 全套（断点 / 网络 / 控制台），所见即所得 |
| 产物形态 | 可独立部署的 Node 脚本（服务器无需浏览器） | 依赖浏览器进程（服务器需装 Chromium 或系统浏览器） |
| 反检测 | **完全可控**，可精确抹掉任何指纹 | 默认带 webdriver / HeadlessChrome 等特征，需 stealth 处理 |
| 更新成本 | 站点 JS 更新 → 换字节码资产即可（补环境接口稳定） | 页面结构 / 交互一变，自动化脚本常需跟着改 |

## 二、实测数据（31 脚本，批量 N = 50）

| 指标 | 补环境（01+02） | Playwright（30） |
|---|---|---|
| 冷启动到可签名 | **118 ms** | 672 ms |
| 单次签名（完整链路墙钟） | 118 ms（含 node 进程启动） | 46.2 ms（页面已就绪） |
| 批量 50 次平均（纯执行） | 30.00 ms/次 | **24.56 ms/次** |
| 批量 50 次平均（含驱动） | 118 ms/次（逐次重启进程） | 30.24 ms/次（逐次 IPC） |
| 产物结构 | 4 字段 / 384 位 hex | 4 字段 / 384 位 hex |
| payload 头 32（输入指纹） | 4509d8ed4632e9b9... | 4509d8ed4632e9b9... |
| 端到端 mock 站 | 200 | 200 |

读表要点：

- **纯 JSVMP 执行速度两方案同量级**（30.00 vs 24.56 ms/次）——瓶颈都在字节码解释执行本身，与"环境是真是假"无关；
- 补环境冷启动更快（118 ms，Node 进程很轻）；浏览器冷启动 672 ms，且内存占用要高一个量级（几百 MB）；
- 「含驱动」一列才是爬虫的真实成本：补环境逐条请求逐次起进程 = 118 ms/次，做成常驻签名服务后约为纯执行水平（≈30 ms/次）；Playwright 常驻页面 evaluate ≈30 ms/次；
- 补环境对批量签名友好（`--count` 进程内循环）；Playwright 要处理好同步 / 异步与事件循环。

## 三、两个实锤观察（本案例实测）

1. **payload 头 32 位两方案完全一致**（`4509d8ed4632e9b986d8805a964765e4`）
   → 输入指纹段只依赖 (path, body)，不掺入 cookie 值与环境差异。"补环境补对了"可以用数字证明，而不是"没报错就对了"。
2. **cookie 完整性规律在浏览器里同样成立**
   浏览器里一次性写 cookie 整串只落 1 条（实测 Edge/Chrome 行为）→ 同一份 JSVMP 出了 272 位简化签名。
   → "环境齐不齐"决定签名形态；Playwright 也不能保证"打开页面就万事大吉"，cookie 得自己种对。

## 四、mock 站的局限（顺带说清"服务端视角"）

本 mock 站校验三层：结构（四字段 / 384 hex）+ 时效（X-t ±300 s）+ 请求指纹白名单。
但服务端**没有密钥**，不能真算 JSVMP 签名，因此：

- 无法检测"body 被替换 + 旧签名重放"（指纹是旧 body 的合法指纹，白名单照样命中）；
- 真实小红书站能严验，是因为密钥在服务端手里——这是黑盒逆向无法突破的壁垒，也是风控的真正底牌。

## 五、怎么选（决策表）

| 场景 | 推荐 | 理由 |
|---|---|---|
| 一次性采集、页面交互复杂（登录 / 滑块 / 滚动） | Playwright | 环境全真、开发快、所见即所得 |
| 高频长期采集、服务器资源受限 | 补环境 | 轻量、可常驻、无浏览器依赖 |
| 目标算法是硬骨头（JSVMP / WASM） | 先 Playwright 验证链路，后补环境复刻 | 前者拿"正确样本"，后者做稳定产物 |
| 强反爬站点（检测 webdriver / Headless） | 补环境（或 Playwright + stealth 深度对抗） | 补环境对指纹完全可控 |
| 需要脱离浏览器分发（给同事一个小工具） | 补环境 | Node 单文件即可跑 |
