## 一、通用流程：从抓包到 Python 模拟登录

1. **抓包定契约**：确认请求 URL、方法、请求头、请求体，标出“看起来像密文/签名”的字段。
2. **改包判断必要性**：逐项删除请求头或请求体字段重发，确认哪些是服务端强校验的必须项（重点保留要破解的字段）。
3. **jadx 搜索定位**：优先搜接口 URL 的唯一路径（如 `member/login`、`partnerLogin/login`），再搜字段写入形式（如 `put("sign`）或常量名。
4. **沿调用链回溯**：接口声明 → Repository/网络层 → 业务层 login(...) → 加密工具类。jadx 的“查找用例”是主要手段。
5. **Frida hook 确认动态值**：对工具类方法（如 `getMD5`）挂 hook，打印入参与返回值，拿到静态分析难以确定的 key、随机串、时间戳等。
6. **Python 复现**：按还原出的算法生成密文/签名，构造请求；登录成功后保存 token，用于后续接口。
7. **验证思路**：用抓包得到的密文/签名与本地计算结果对照，确认算法与参数拼接顺序。

> 前提（前序课已覆盖）：HTTPS 抓包需要手机安装并信任 Charles 证书，Charles 的 SSL Proxying 要包含目标域名；否则只能看到 CONNECT。

## 二、爱安丘：AES-CBC + Base64 + Hook 取 key

### 2.1 抓包契约

- 地址：`https://app-auth.iqilu.com/member/login?e=1`
- 方法：POST，JSON
- 请求头关键项：

| 字段 | 含义/取值 |
| --- | --- |
| `encrypt` | 固定 `1` |
| `version` | App 版本，如 `1.0.5` |
| `orgid` | 地区 id，写死 `137` |
| `platform` | `android` |
| `imei` | 设备标识，可伪造 |
| `User-Agent` | 客户端标识 |

- 请求体：`phone`、`password`（密文）、`code`、`codeKey`、`key`（后三项登录场景为空串）。
- 改包结论：`Cookie`、`CQ-AGENT` 等可删除；`encrypt/version/orgid/platform/imei` 属于固定或可伪造项。

### 2.2 反编译定位链路

- 搜 `member/login` 命中接口声明：`@Headers({"encrypt:1"}) @POST("member/login") login(@Body Map<String,String> map)`。
- 对 `login` 查找用例，进入网络层封装 `login(map, callback)`。
- 再查用例，进入业务层五参数 `login(phone, code, key, codeKey, password)`：
  - 依次把 `phone/code/key/codeKey` 放入 HashMap；
  - `password` 走三目判断：空则空串，否则 `EncryptUtil.aesPassword(password)`。
- 跳到 `aesPassword` 声明，得到完整加密表达式：
  - `Base64.encodeToString(EncryptUtils.encryptAES(明文bytes, getMD5(PRIVATE_KEY + getSecret() + BaseApp.orgid).getBytes(), "AES/CBC/PKCS7Padding", "0000000000000000".getBytes()), 2)`
- 继续跟 `encryptAES → symmetricTemplate`：标准 `Cipher.getInstance("AES/CBC/PKCS7Padding")`，key 用 `SecretKeySpec`，iv 用 `IvParameterSpec`。

### 2.3 算法还原

- 明文：用户输入的密码。
- key：`MD5(PRIVATE_KEY + getSecret() + orgid)` 的 32 位十六进制字符串，**直接按字符串取字节**（32 字节，即 AES-256），不是把 hex 解码成 16 字节。
- iv：`"0000000000000000"`（16 字节 0）。
- 模式/填充：AES/CBC/PKCS7Padding（明文长度为 16 的倍数时会整块补 16 字节）。
- 输出：密文字节再做标准 Base64 编码。
- 常量：`PRIVATE_KEY = c058579161250b37`；`orgid = 137`；`getSecret()` 返回“随机字符串 + APP”，是动态/固定拼接，不能只靠静态常量猜。

### 2.4 Hook 确认 key

- 手机启动 frida-server，PC 执行 `adb forward tcp:27042 tcp:27042`、`adb forward tcp:27043 tcp:27043`。
- attach 进程名“爱安丘”，hook `com.iqilu.core.util.EncryptUtil.getMD5`：
  - 打印入参：可看到 `PRIVATE_KEY + getSecret() + orgid` 的完整拼接；
  - 打印返回值：得到 MD5 结果，即 AES 的 key。
- 课件记录的结果形态：拼接明文为 `c058579161250b37 + 一段固定随机串 + APP + 137`，MD5 结果为 `6d6656a37cdb7977c10f6d83cab168e9`（32 位 hex，作为 32 字节 key 使用）。
- 这一步的意义：`getSecret()` 的具体值无法从静态常量直接确定，hook 是最快的确认方式。

### 2.5 IMEI 的处理

- 请求头 `imei` 只是设备标识，服务端可能用于限制设备，可以直接伪造。
- 标准 IMEI 为 15 位数字：TAC（6 位，型号）+ FAC（2 位，装配代码）+ SNR（6 位，序列号）+ SP（1 位，Luhn 校验位）。
- 课件给出两种生成方式：
  - 简单版：随机 16 位十六进制字符串（抓包值也是这种形态，如 `69b80588244673ed`）；
  - 标准版：随机生成前 14 位数字，按 Luhn 规则计算第 15 位校验位。
- 结论：每次请求可随机生成，不必与真机一致。

### 2.6 登录后的 token

- 响应 `data.token` / `data.memberToken` 是 JWT，形如 `header.payload.signature` 三段。
- 前两段可 Base64 解码：
  - header：`{"typ":"JWT","alg":"HS256"}`；
  - payload：包含 `gid`、`t`（时间）、`openid`、`iss`、`nickname`、`avatar`、`orgid`、`platform` 等用户信息。
- 第三段是签名，普通抓包场景只读不改；payload 被改动后签名无法通过服务端校验。
- token 是登录态凭证，后续访问需要登录的接口时按抓包位置携带（一般在请求头），过期需重新登录获取。

### 2.7 代码包对应脚本

- `0-端口转发.py`：frida-server 的 27042/27043 端口转发。
- `1-hook-getMD5.py`：attach 爱安丘，hook `EncryptUtil.getMD5`，打印明文拼接与 MD5 结果（key）。
- `2-模拟登录爱安丘.py`：请求头字符串转字典、随机 imei、AES 加密密码、POST JSON；文件末尾保留了课件抓到的真实响应样例（含 token/memberToken）。
- `3-base64解码.py`：JWT 前两段 Base64 解码示例。
- `4-python的md5.py`：hashlib MD5 基础用法。
- `utils.py`：两种 imei 生成、AES-CBC-PKCS7 加密、`query_to_dict`、`header_str_to_dict`。

## 三、尿大夫：MD5 截取拼接 sign

### 3.1 抓包契约

- 地址：`https://api.niaodaifu.cn/v4/site/loginnew`
- 方法：POST，JSON
- 请求体字段：

| 字段 | 说明 |
| --- | --- |
| `mobile` | 手机号 |
| `password` | 明文密码（该接口未加密） |
| `channel` | 固定 `android` |
| `time` | 秒级时间戳 |
| `mechanism` | 固定 `0` |
| `platform` | 固定 `1` |
| `devisetoken` | 设备 token，改包测试可删除 |
| `sign` | 必须携带，删掉即失败 |

- 请求头无特殊校验。

### 3.2 定位过程

- 搜 `site/loginnew` 或 `put("sign`，命中 `requestParams.put("sign", SafeUtils.getSign(currentTimeMillis))`。
- 注意变量名有迷惑性：源码先执行 `System.currentTimeMillis() / 1000`，传入 `getSign` 的 `j` 实际是**秒级**时间戳，必须与请求体 `time` 一致。
- 跳入 `SafeUtils.getSign(long j)` 得到完整公式。

### 3.3 算法还原

对同一个时间戳 `j`（秒）分别计算两段 MD5 十六进制字符串，再截取拼接：

```text
v1 = md5("niaodaifu" + j)[12:30]   # 18 个字符
v2 = md5("android"  + j)[12:26]    # 14 个字符
sign = v1 + v2                     # 共 32 个字符
```

- `android` 来自 `channel` 字段，登录场景固定。
- 两段都是对“固定盐 + 时间戳”做 MD5，再取中间一段，属于常见的“截取拼接”型签名。
- Python 用 `hashlib.md5(...).hexdigest()` 后按切片取即可。
- 请求体在课件脚本中先按 query string 形式拼接，再转 dict，最后以 JSON 发送；字段顺序为 `password/mobile/channel/sign/time/mechanism/platform`。

### 3.4 代码包对应脚本

- `5-python实现x大夫的sign加密.py`：固定时间戳演示两段 MD5 截取拼接。
- `6-python实现目标.py`：尿大夫完整模拟登录（sign + JSON 请求）。

## 四、合伙人：请求头 X-Sign + MD5 密码

### 4.1 抓包契约

- 地址：`https://chinayltx.com/app/api/v1/partnerLogin/login`
- 方法：POST，`application/x-www-form-urlencoded`
- 请求头关键项：

| 字段 | 说明 |
| --- | --- |
| `X-App` | 固定 `native` |
| `X-Noncestr` | 固定 `123456`（多次抓包不变） |
| `X-OS` | 固定 `partnerApp_android` |
| `X-Req-Time` | 毫秒级时间戳 |
| `X-Sign` | 待破解签名 |
| `X-Token` / `X-UserID` | 登录场景为空 |

- 请求体：`phone`、`password`（MD5 密文）。

### 4.2 X-Sign 定位链路

- 搜 `X-Sign` 先命中常量 `PARAM_SIGN = "X-Sign"`；对常量“查找用例”可能找不到，改为直接搜常量名 `PARAM_SIGN`。
- 命中请求头组装处：`newBuilder.add(PARAM_SIGN, this.sign)`。
- 在同一类的构造逻辑中，`this.sign` 来自 `sign(sb.toString())`：
  - 若 `requestBody` 是 `FormBody`，按索引遍历所有键值对；
  - 依次拼接 `name=value`，非最后一项追加 `&`；
  - 得到形如 `phone=...&password=...` 的 body 字符串。
- `sign` 方法实现：`Md5.md5(token + reqTime + noncestr.substring(2) + bodyString).toLowerCase()`。

### 4.3 算法还原

```text
sign = md5(X-Token + X-Req-Time + X-Noncestr[2:] + "phone=...&password=...").lower()
```

- `X-Token` 登录时为空串，直接参与拼接。
- `X-Req-Time` 为 13 位毫秒时间戳，签名与请求头必须使用同一个值。
- `X-Noncestr` 请求头发送完整 `123456`，但签名只取 `substring(2)`，即 `3456`（Java substring 从索引 2 到结尾）。
- body 字符串的键值顺序必须与 FormBody 实际顺序一致（phone 在前、password 在后），且直接拼接，不做 URL 编码。
- 密码先做 MD5 小写，再参与 body 拼接与签名，两步有依赖顺序。

### 4.4 password 定位链路

- 搜 `partnerLogin/login` 或 `password`，命中 `submitLogin(@Field("phone") ..., @Field("password") ...)`。
- 查 `submitLogin` 用例 → 网络层 `loginWithToken(name, pwd)` → 业务层 `buildObservable()` 使用 `this.pwd`。
- 查 `setPwd` 的调用点，命中 `this.mLoginUseCase.setPwd(Md5.md5(str2))`，确认密码是 MD5（小写十六进制）。
- 结论：`password = md5(明文)`，与抓包密文长度（32 位）一致。

### 4.5 代码包对应脚本

- `7-x-token的生成.py`：文件名虽叫 x-token，实际演示的是合伙人 `X-Sign` 的复算（token + reqTime + noncestr[2:] + body）。
- `8 python实现合伙人登录.py`：合伙人完整登录（MD5 密码 + X-Sign + form 请求）。

## 六、关键知识清单

- **抓包定位优先级**：URL 唯一路径 > 字段写入形式（`put("sign`）> 常量名；jadx 的“查找用例”用于向上回溯调用链。
- **改包测试**：逐项删除参数判断服务端是否强校验；空字段能删则删，但必须项（如 sign）要保留。
- **AES 参数识别**：`Cipher.getInstance("AES/CBC/PKCS7Padding")` + `SecretKeySpec(key)` + `IvParameterSpec(iv)`，缺一不可。
- **key 的形态陷阱**：MD5 得到的 32 位 hex 字符串按字节使用是 32 字节（AES-256），不是 16 字节；不要多做一次 hex 解码。
- **PKCS7 填充**：按块补齐，长度恰为 16 倍数时补一整块。
- **动态值靠 hook**：`getSecret()`、随机串、时间戳等静态分析不确定时，hook 工具类方法打印入参/返回值最快。
- **MD5 截取拼接签名**：同一时间戳 + 不同固定盐生成多段 MD5，再取指定区间拼接，是常见变体。
- **请求头签名的三要素**：固定盐（token/app key）、时间戳、请求体原文；三者拼接顺序和大小写都要与源码一致。
- **时间戳陷阱**：秒与毫秒不能混用；签名用的时间戳必须与请求体/请求头中的值完全一致。
- **子串陷阱**：`noncestr.substring(2)` 只参与签名，请求头仍发送完整值。
- **表单签名顺序**：`FormBody` 的键值顺序决定 body 字符串，签名与请求必须使用同一顺序。
- **JWT 结构**：`header.payload.signature`，前两段 Base64 可读，签名段一般不参与构造；token 过期需重新登录。
- **IMEI 可伪造**：标准 15 位（Luhn 校验）或随机 16 位 hex 都可作为设备标识。
- **壳的影响**：应用市场版本通常加壳，jadx 看不到 Java 代码；课件使用官网无壳版本，脱壳在后续课程。
- **强制更新绕过**：断网启动进入登录页，再恢复网络（不同版本操作路径略有差异）。

## 七、坑位与经验

- 抓不到包时：重启 Charles、把手机代理改成错误地址再改回、重新配置代理；前提是证书已信任且 SSL Proxying 已开启。
- `getSecret()` 这类“随机字符串 + 固定后缀”的值不要猜，hook 一次即可确认；hook 结果要做多次登录对照，确认是否固定。
- 尿大夫的时间戳变量名是 `currentTimeMillis`，但源码已除以 1000，实际为秒；照抄变量名会算错。
- 合伙人签名里 `noncestr` 取了子串，但请求头仍发完整值；只改其中一处会直接失败。
- 合伙人密码先 MD5 再拼进 body，签名基于“已加密的密码”，顺序不能反。
- 爱安丘的 `password` 是“AES 密文再 Base64”，不是单纯 Base64；先 Base64 解码看到的字节不是明文。
- 登录接口返回的 token 可能是多个字段（如 token/memberToken），以实际抓包和响应为准。
- jadx 搜索常量 `X-Sign` 命中的是声明处；找不到用例时，直接搜常量名（如 `PARAM_SIGN`）往往能找到使用处。
