## 1. 为什么是"四接口"

只抓搜索接口会卡死：请求体里 `did`、`edata` 在 APK 里搜不到源码，`did` 是上游接口返回的。顺着依赖往上捋，得到一条必须按序执行的链：

| 顺序 | 接口 | 方法 | 作用 | 产出/依赖 |
| --- | --- | --- | --- | --- |
| 1 | `mp.appvipshop.com/apns/device_reg` | GET | 注册设备（首次启动才走） | 无强产出，服务端记录设备 |
| 2 | `vcsp-api.vip.com/token/getTokenByFP` | GET | 取 vcsp 侧临时凭证 | 返回 `vcspToken`，供第 3 步 |
| 3 | `mapi.appvipshop.com/vips-mobile/rest/device/generate_token` | POST | 换设备身份 | 请求体含 `edata`；返回 `did` |
| 4 | `mapi.appvipshop.com/vips-mobile/rest/shopping/search/product/list/v1` | POST | 关键字搜索 | 需要 `did` + 全参数签名 |

判断依赖关系的手法很土但有效：在 Charles 里把 `did` 往上翻所有前置响应，`generate_token` 的响应里正好有它；再把 `edata` 反查源码，落到一个"某接口返回值 + 本地加密"的组合，于是又挖出 `getTokenByFP`。

补充一个决策经验：`device_reg` 的 `authorization` 头删掉也能请求成功，`skey` 也可以不带——**但别据此认定不用破**。它们在第 3、4 步的签名里都要参与，接口 1 能过不代表链能走通。

## 2. 抓包阶段就要定好"破哪些"

搜索请求体 60 多个字段，逐个啃不现实。先按"是否每次都变"分流：

| 参数 | 观察结果 | 结论 |
| --- | --- | --- |
| `api_key` | 每次一致 | 固定值，直接抄 |
| `skey` | 每次一致 | 固定值，直接抄 |
| `mars_cid` | 每次一致，形如 UUID | 设备标识，UUID 生成 |
| `session_id` | `mars_cid + "_shop_android_" + 毫秒时间戳` | 可本地拼 |
| `did` | 每次一致，源码搜不到 | 上游接口返回 |
| `timestamp` / `page_id` / `lastPageProperty` | 含时间 | 本地生成 |
| `authorization` | 每次变，`OAuth api_sign=40位hex` | 核心签名，必须破 |

另外做个"改包实验"确认签名覆盖面：删请求头直接报 `Invalid API signature`；删请求体任意一个字段同样不通过。这条实验很关键，它把"签名只覆盖部分字段"的侥幸心理提前排除掉了。

## 3. 接口一：`device_token` 的溯源套路

搜索 `device_token` 会命中十几处，但殊途同归，都收敛到一个取值方法。完整链路：

```
sb.append("&device_token=") → c.Q().m()          取内存字段
  → u0(String) 里 this.f73030x = str             赋值点，同时写进 3 个配置单例
    → 调用方 hk.c.Q().u0(Utils.i(context))        唯一真正的来源
      → Utils.i：先查 SP(xml) → 再 DeviceUuidFactory → 最后 UUID.randomUUID()
```

两个通用手法在这里体现得很干净：

1. **找赋值点而不是找读取点**。读取点有一堆，赋值点只有一个 `u0`。
2. **遇到"多入口"就查调用链**。用"查找用例"会发现调用方很多，但继续往下看两层，全部归到同一个函数；此时可以停手，不必逐个验证。

结论：`device_token` 就是一个 UUID，首次生成后落 SP + 内存，重装或清数据才会换。对应 `mars_cid` 也是 UUID（两个值在抓包里往往相同，因为注册时同一个 UUID 被复用）。

## 4. 接口一/二：`authorization` 的真身是双重 SHA1

### 4.1 Java 层定位链

从请求头写入点往回退，会经过一串"看着像混淆、其实只是包装"的方法：

```
addHeader("authorization", "OAuth api_sign=" + b.b(...))
  → b.b() → a(...)
    → VCSPSecurityBasicService.apiSign(context, treeMap, str)
      → VCSPSecurityConfig.getMapParamsSign(context, map, str, false)
        → getSignHash(...)
          → gs(context, map, str, z)      // 反射
            → KeyInfo.gs(...)             // 反射壳
              → native gsNav(context, map, str, z)   // 进 so
```

关键判断：`TreeMap` 参数说明"签名对象是排序后的请求参数字典"，不是原始 query 串。

### 4.2 so 层：静态注册 + 两次 SHA1

`libkeyinfo.so` 只有 32 位（`armeabi-v7a`），IDA 用 32 位打开，符号是标准静态注册名 `Java_com_vip_vcsp_KeyInfo_gsNav`。函数体很短：校验 JNI 异常后交给 `Functions_gs`。`Functions_gs` 里能读到两次 `j_getByteHash`，而 `getByteHash` 内部就是 `SHA1Reset / SHA1Input / SHA1Result`。

所以整个签名是：

```
tmp      = sha1( salt + sort_join(params) )
api_sign = sha1( salt + tmp )
salt     = aee4c425dbb2288b80c71347cc37d04b
```

`sort_join` 是"按 key 的 ASCII 升序，`k=v` 用 `&` 连接"。Java 的 `TreeMap` 与 Python 的 `sorted(dict)` 在这件事上等价。

### 4.3 为什么这里必须 hook 而不是"看着像就写"

`getByteHash` 的入参是把 `salt + 排序串` 拼出来的一整段字符串，其中 `rom` 字段带空格、括号、斜杠，`dinfo` 是 JSON。手写很容易在"要不要 URL 编码""空格怎么处理"上猜错。课件是在 `getByteHash` 上挂 `Interceptor`，`onEnter` 存 `args[2]`、`onLeave` 读 `Memory.readCString`，把真实入参和返回值一起打出来，一眼就对上了盐的位置和拼接方式。

### 4.4 同一套算法，第二个盐

`getTokenByFP` 的请求头是 `vcspauthorization: vcspSign=...`，走的是同一条 `gsNav` 路径，只是明文固定为 `vcspKey=4d9e524ad536c03ff203787cf0dfcd29`、盐换成 `da19a1b93059ff3609fc1ed2e04b0141`：

```
tmp      = sha1( da19a1b93059ff3609fc1ed2e04b0141 + "vcspKey=4d9e..." )
vcspSign = sha1( da19a1b93059ff3609fc1ed2e04b0141 + tmp )
```

因为"明文里的 `vcspKey` 永远不变"，`vcspSign` 自然是固定值，可以写死。这是本案例里最省力的一处，但**判断依据要记牢：签名输入是否随请求变化**——不变化就可以固化。

## 5. 接口三：`edata` 的产生链（本案例最核心的一段）

### 5.1 从常量反查到 native

`edata` 在源码里是常量名 `EDATA`，找它的使用点会落到 `GobalConfig.encodeStr(context, sb, ...)`，再往下：

```
GobalConfig.encodeStr → VCSPSecurityConfig.encodeStr → es()
  → KeyInfo.es()（反射壳） → native esNav(Context, String, String, String, int)
```

### 5.2 so 里在"用 JNI 反射做 Java 加密"

`Functions_es` 反编译出来没有自研算法，全是 JNI 调用：

```
FindClass("javax/crypto/Cipher") + getInstance("AES/CBC/PKCS5Padding")
FindClass("javax/crypto/spec/SecretKeySpec") + <init>([B, String)     // key = v20
FindClass("javax/crypto/spec/IvParameterSpec") + <init>([B)           // iv  = v32
init(1, key, iv) → doFinal(v41) → base64_encode → NewStringUTF
```

这段值得单独记：**native 层不一定有自研算法**。看到 `FindClass`/`GetMethodID`/`NewObject`/`CallObjectMethod` 这一套，说明加密实际跑在 Java 层，只是被 so 当工具调。此时不用死磕汇编，反过来 hook Java 标准类的构造方法就能把 key/iv 掏出来。

反过来也提醒一点：只在 Java 层 hook `SecretKeySpec` 时，可能会发现"hook 一次出三四个 key"，因为 App 里其它模块也在用 AES。必须与 `esNav` 的调用时序对齐，才能确定哪一组属于 `edata`。

### 5.3 key = md5(盐) 的二进制，不是 hex

读 `Functions_es`：`v19 = j_getMD516(env, salt, len)`，随后 `NewByteArray(16)` + `SetByteArrayRegion(..., 16, v19)` 得到 `v20`。所以：

```
key = md5_digest("aee4c425dbb2288b80c71347cc37d04b")   // 16 字节二进制
    = cd d1 7a b2 9b 84 b3 25 52 dd cf bb 4a bf 02 25
```

hook 打在 `getMD516` 上能看到入参是那串 32 字符盐、返回 16 字节；同一份值在 Java 层 `SecretKeySpec` 打出来是 `cdd17ab29b84b32552ddcfbb4abf0225`。**这两者不是一回事**：前者是 16 字节，后者是 32 字符的 hex。Python 里必须用 `hashlib.md5(...).digest()`，用 `hexdigest()` 会得到 32 字节，直接导致密钥长度错、加密结果全废。

另外，key 是 16 字节 → 实际是 **AES-128-CBC**，不是 256。写代码时按 `AES.MODE_CBC` + 16 字节 key 走即可。

### 5.4 iv 是"随机字符串"，不是随机字节，而且前置拼接

`v59` 初始化 4 个 8 字节为 0（32 字节缓冲区），随后 `rand16Str(v59)` 往里填值；再 `NewStringUTF(v59)` → `getStringByteArray` → `IvParameterSpec`。hook `rand16Str`（`onEnter` 存 `args[0]`、`onLeave` 读 16 字节）可以确认：每次都不一样，内容是 16 个十六进制字符。

于是 `edata` 的组装是：

```
edata = base64( iv_ascii(16 字节) + AES_CBC_PKCS5(plaintext, key, iv) )
```

对照 hook 到的 `base64_encode` 入参首 16 字节正好是 ASCII 的 `b04c6ab2831713b9...`，后面紧跟密文。**这条"iv 明文前置"是解密/复刻时的关键约定**：只发密文，服务端就没法解；iv 跟着密文走，密钥就可以长期固定。

这种"key 固定 + iv 每次变"的组合，比"key/iv 都下发"更常见，遇到时不要因为 iv 变就以为要逆随机数算法——它本来就是本地随机的。

### 5.5 明文就是 `esNav` 的入参

`v41 = j_Utils_getStringByteArray(env, a2)`，`a2` 就是 `esNav` 收到的字符串。所以不用猜明文格式：hook `esNav` 打印入参，和 hook `Cipher.doFinal` 的入参对照，两者一致即可确认"没有二次加工"。

明文内容是 `data_dict` 的排序拼接串，其中 `dinfo` 这个 JSON 已经先做过 `quote_plus`。也就是说，**签名串里的值可能是"已编码过的值"**，这一点和第 4 节的 `authorization` 又不一样（那里的 `rom` 是原始值）。判断依据永远是 hook 出来的真实入参，不是字段长相。

`dinfo` 各字段含义（课件给了注释，很实用）：

| 字段 | 含义 | 字段 | 含义 |
| --- | --- | --- | --- |
| `ah4` | 网络类型 `wifi` | `as1` | 安卓版本（如 11） |
| `ah5` | 分辨率 `1440_2712` | `as4` | android_id |
| `ah6` | CPU 最大频率 | `as7` | SDK 版本（如 30） |
| `ah7` | CPU 核数 | `ac1` | device_token（UUID） |
| `ah8` | 内存大小 | `ah9` | 机型（如 `Pixel 2 XL`） |

### 5.6 `generate_token` 的两层签名容易混

一个请求里有**两套**独立的东西：

- 请求体：`api_key / did / edata / eversion / skey / timestamp`，其中 `did` 是空（等它返回），`edata` 是上一节的加密结果
- 请求头：`api_sign` 覆盖的是**请求体这 6 个字段**的排序拼接串，盐仍是 `aee4c425...`，算法同第 4 节

而 `edata` 内部加密的是另一份字典（`app_name / app_version / client_type / dinfo / mars_cid / phone_model / session_id / sys_version / vcspKey / vcspToken`）。**外层签名 ≠ 内层明文**，写代码时如果只维护一份 dict 会互相污染。

返回的 `did` 形如 `0.0.<32位hex>.<6位hex>`，服务端生成，本地只负责接住复用。

抓到的样例：

```
vcspToken = NGQ5...fHx8.3869a5558ebdb2e1df72774a22b213be
```

base64 解开前半段是 `4d9e524ad536c03ff203787cf0dfcd29|||1695461616|||`，即 `vcspKey ||| expireTime |||`，点号后面是 32 位 md5 片段。知道结构后排错会快很多：过期时间对不上就先怀疑本地时间/缓存，而不是怀疑签名。

## 7. 反调试与 hook 时机：两次踩坑都在这

### 7.1 `hook` 就闪退 → 先找"多出来的 so"

用 spawn 方式 hook `KeyInfo.getNavInfo`，一挂就崩。复用"hook `dlopen`/`android_dlopen_ext` 打印加载路径"这招，会看到列表末尾多出一个可疑库：

```
/data/app/~~xxx==/com.achievo.vipshop-xxx==/lib/arm/libmsaoaidsec.so
```

删掉这个 so（需要 root 改 `/data/app` 下文件）后 hook 恢复正常。这个思路可以固化成流程：**新 App hook 闪退，第一步不是换 frida 版本，而是先把加载的 so 全打出来，看有没有安全 SDK**。

### 7.2 so 延迟加载 → 三种 hook 时机的取舍

`libkeyinfo.so` 不是启动即加载，`Module.findExportByName` 在启动早期返回 `null`。课件把三种做法都写了，值得对照记：

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| spawn 直接 hook | `frida -f` 启动即挂 | so 还没加载，`addr` 为空，报错 |
| 手动 attach | `frida -UF -l`，在点"同意"那一刻执行 | 时机靠手速，太早太晚都失败 |
| 延迟 hook | 先挂 `dlopen`/`android_dlopen_ext`，路径命中 `libkeyinfo.so` 后 `setTimeout(…, 10)` 再挂目标函数 | 稳定，推荐 |

`setTimeout` 那 10ms 是等 so 完成初始化（`JNI_OnLoad`、重定位），不是玄学。

此外，课程里多次强调"清数据再跑"：设备注册、`skey`、`edata` 都跟首次启动流程绑定，带着旧缓存抓包容易看到上一次的固定值，误以为算法没跑。

## 9. 坑与要点清单

1. **签名覆盖全参数**：删任一字段即失败，别试图裁剪请求体"简化"。
2. **排序用 ASCII 升序**：Java `TreeMap` = Python `sorted()`；键名大小写敏感。
3. **编码状态要按字段区分**：`authorization` 的明文里 `rom` 是原始值（带空格括号）；`edata` 的明文里 `dinfo` 是 `quote_plus` 后的值。以 hook 结果为准。
4. **AES key 用 `digest()`**：`cd d1 7a ...`（16 字节）≠ `cdd17ab2...`（32 字符 hex）。
5. **iv 是 16 个十六进制字符的字符串**：`''.join(random hex × 16)`，且要 `encode()` 成 16 字节参与 CBC。
6. **`edata` 首 16 字节是 iv**：base64 解码后先切 16 字节，再解剩下的密文。
7. **`getMD516` 输出噪声大**：单 hook 它无法定位，需与 `esNav`、`SecretKeySpec` 三点联动、按时序对齐。
8. **native 不一定是自研算法**：出现 `FindClass`/`CallObjectMethod` 一整套，说明是 JNI 调 Java；转去 hook Java 标准类更快。
9. **hook 闪退先查安全 so**：`libmsaoaidsec.so` 是典型；删之前先确认设备已 root 且能改 `/data/app`。
10. **so 延迟加载**：优先用 `dlopen` 拦截 + 延时再 hook，不要赌启动时机。
11. **清数据再抓包**：设备标识、`skey` 都是首启生成并缓存的，旧缓存会给出"假固定值"。
12. **固定值要复用而不是重造**：`device_token`/`mars_cid` 一旦生成就贯穿整链；每次随机新 UUID 会导致 `did` 与设备对不上。
13. **课件示例代码有两处瑕疵**（复用时要改）：`"device_model": "".format(build_model)` 实际得到空串；`session_id` 里的毫秒时间戳写死成 `1669730552506`。另外同一份代码里 `osv=10`、`sys_version=29`，与 `Pixel 2 XL / Android 11` 的 `dinfo` 不一致——设备画像字段最好统一成一套，别混搭。
14. **`vcspToken` 会过期**：`expireTime` 就在 token 里，链跑不通时优先怀疑它。

## 10. 这个案例的关键知识清单

- **依赖反推**：目标接口缺的参数，先判断"本地生成 / 上游返回"，再顺着上游继续挖，最终得到 4 接口的执行顺序。
- **改包实验定边界**：删字段 + 删头，快速确认签名覆盖面，避免后续误判。
- **找赋值点 / 找唯一收敛点**：`device_token` 的溯源模板（读点很多 → 赋值点唯一 → 调用来路收敛）。
- **双重 SHA1 加盐签名**：`sha1(salt + sha1(salt + sorted_kv))`，`TreeMap` 排序，盐可能不止一套（`api_sign` 与 `vcspSign` 各一个）。
- **JNI 静态注册 so 的读法**：`Java_包名_类名_方法名` → `Functions_xx` → 关键子函数；`getByteHash` 里认出 `SHA1Reset/Input/Result`。
- **JNI 反射做 Java 加密的识别**：`FindClass(Cipher/SecretKeySpec/IvParameterSpec) + NewObject + CallObjectMethod`。
- **AES-CBC 的工程约定**：key = `md5(盐)` 的二进制；iv 随机 16 字符并前置拼接；`base64(iv + cipher)` 整体作为 `edata`。
- **hook 时机工程学**：spawn / attach / dlopen 延迟 hook 三种方式与适用场景；`setTimeout` 等待 so 初始化。
- **反调试应对**：hook 即崩 → 枚举已加载 so → 定位并移除安全库。
- **可固化原则**：签名输入不变的（`vcspSign`）直接写死；输入随请求变的（`api_sign`）必须实现算法。
