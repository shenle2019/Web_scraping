## 一、Frida 部署要点（day04 版本）

- 电脑端与手机端 frida-server **版本必须一致**，课件使用 16.3.3 全家桶：
  `pip install frida --upgrade`（16.3.3）+ `pip install frida-tools --upgrade`（12.4.3）
- 手机端流程：查架构（`adb shell getprop ro.product.cpu.abi` → arm64-v8a）→ 下载对应
  frida-server → `adb push` 到 `/data/local/tmp/` → `adb shell` + `su` 进入 →
  `chmod +x frida-server-16.3.3-android-arm64` 加执行权限
- 启动服务端：切到 `/data/local/tmp` 后直接运行 `./frida-server-16.3.3-android-arm64`，
  终端"卡住"即为启动成功（前台运行）；报错时优先重启手机，或 `adb shell setenforce 0`
- 端口转发（电脑端）：`adb forward tcp:27042 tcp:27042` 与 `27043` 一起做，
  可用 `subprocess.getoutput()` 由 Python 代劳；不转发则连不上 remote device
- 验证连通：`frida.get_remote_device()` → `get_frontmost_application()` 能拿到前台
  app 的 identifier / name / pid（如 tv.danmaku.bili 哔哩哔哩）即通

常见问题（课件标注）：
- `su` 提示 inaccessible or not found → 手机未 root
- `su` 提示 Permission denied → 手机上拒绝了 root 授权弹窗
- frida-server 无 x 权限时运行不了，必须 `chmod +x`

## 二、attach 与 spawn：两种注入方式的场景区分（本篇核心）

两者注入的都是同一套 JS（Java.perform + Java.use + implementation 替换），
区别在"注入时机"与"目标进程状态"。

### attach（附加到已运行进程）
- 机制：app 手动打开 → `rdev.attach("进程名或包名")` → 注入
- 适用：hook 点是**用户操作触发**的（登录按钮点击后才执行 encodeMD5）
- 操作顺序：app 保持前台运行 → 运行脚本 → 脚本挂起等待 → 手机端触发操作 → 控制台打印

### spawn（由脚本重启并注入）
- 机制：`pid = rdev.spawn(["包名"])` 先让 app 以暂停态启动 → attach(pid) 注入 →
  最后必须 `rdev.resume(pid)` 放行，否则 app 卡在启动页
- 适用：hook 点是**app 一启动就执行**的（初始化、加固校验、早期注册的加密函数）
- attach vs spawn 一句话：**点击按钮才执行的用 attach；一启动就执行的用 spawn**

### JS 脚本的两种载体
- Python 载体：js 写在 `session.create_script(scr)` 的三引号字符串里，`script.load()` 注入
- 纯 JS + CLI 载体：把 hook 逻辑存成 hook.js，用 frida-tools 命令行执行
  - attach 模式：`frida -UF -l hook.js`（U=USB 设备，F=前台 app）
  - spawn 模式：`frida -U -f com.che168.autotradercloud -l hook.js`
  - 退出：输入 q 回车

### hook 代码的固定骨架（三种载体通用）
```
Java.perform(function () {
    var Cls = Java.use("包名.类名");          // 1. 用反编译得到的全类名找类
    Cls.方法名.implementation = function(参数...) {  // 2. 替换方法实现
        // 3. 打印入参（明文）
        // 4. this.方法名(参数) 调原函数，可打印返回值（密文）
        // 5. return 原返回值或篡改值（篡改可用于登录绕过测试）
    };
});
```

### hook 在逆向流程中的定位
反编译搜到的加密位置只是"嫌疑对象"（静态推理），**hook 打印才是运行时证据**：
手机端操作 → 控制台真的打印出参数与结果 → 证明该函数确实参与了加密链路。
day04 案例验证对象：车智赢 `com.autohome.ahkit.utils.SecurityUtil.encodeMD5`，
hook 拿到的明文与密文可与抓包密文对照（对照思路见 day03 案例实操库）。

## 三、常见加密算法分类与 Python 还原

### 分类（逆向遇包先归类，再决定还原策略）
1. 单向加密（摘要算法）：MD5、SHA 系 —— 不可逆
2. 对称加密：AES、DES —— 可逆，加解密同一密钥
3. 非对称加密：RSA、DSA —— 可逆，公钥加密 / 私钥解密（或私钥签名 / 公钥验签）
4. 补充算法：Base64 —— 不是加密，只是编码（常与上面三种叠加使用）

### 各算法的还原要点

- **MD5**：`hashlib.md5()` + `update(明文.encode())` + `hexdigest()` 得 32 位小写 hex；
  常见坑：app 端可能有加盐、大小写、多次摘要，以 hook 实拿密文为准
- **SHA1**：`hashlib.sha1()` 用法同 MD5，输出 40 位 hex
- **DES**：`pycryptodomex` 的 `Cryptodome.Cipher.DES`；分组 64 位、密钥 56 位（每第 8 位
  为校验位），课件示例 key=`88888888`、ECB 模式；**补位需用与 app 相同的填充方案**
  （示例用 "=" 补齐 8 的倍数，解密后再截掉——真实 app 多为 PKCS5/PKCS7）
- **RSA**：`rsa.newkeys(1024)` 生成公私钥；encrypt/decrypt 之外还要会两件事：
  `rsa.sign(明文, 私钥, "MD5")` 私钥签名、`rsa.verify(明文, 签名, 公钥)` 公钥验签
  （明文改一个字符验签即失败——说明签名绑定了内容，逆向时签名参数往往就是它）
- **Base64**：`base64.b64encode` / `b64decode`；URL-safe 变体（`-_` 替代 `+/`）要注意

## 四、完整抓包逆向案例：金树林 app

目标链路：发送验证码 → 注册 → 登录 → 登录后查询商品。
域名：`miappshop.jshulin.com`，UA 为 uni-app 的 WebView 特征 UA。

### 4.1 发送验证码
- `GET /memberLogin/phoneCode`，参数 `phone` + `serviceType`
- **serviceType 区分业务**：6 = 登录用码；5 = 注册用码（两个场景码不同，别混用）

### 4.2 注册
- `POST /memberLogin/memberRegister`，JSON 体：phone、fid（空串）、password、phoneCode
- 必须先拿到对应 serviceType=5 的短信验证码再提交
- 密码字段明文字段直接提交（此 app 未在传输层加密密码）

### 4.3 登录
- `POST /memberLogin/login`，JSON 体：username（手机号）+ password
- 成功响应 `code:10000`，data 里返回 **token（极简 JWT）+ tokenLong（长效）+ userInfo**
- JWT 三段式可解出 aud（会员ID）、exp/iat（过期/签发时间）、userId、username
- 后续请求鉴权方式：**请求头 Mobile-Token 携带登录返回的 token**，而非 Cookie

### 4.4 登录后查询商品
- `POST /pro/searchByPage`，JSON 体：cityNo、keyword、limit、page、orderByContent、enabled
- 鉴权头：`Mobile-Token: <登录 token>`；不带 token 或 token 过期则查不到数据
- 业务流程脚本化的顺序依赖：**验证码 → 注册 → 登录拿 token → 带 token 查询**，
  验证码需要人工输入或接入接码平台

### 4.5 接码平台（批量注册自动化思路）
- 机制：平台提供手机号并代收发短信，通过 API 取回验证码，省去人工输入环节，
  可串成"取号 → 发码 → 取码 → 注册"全自动循环
- 课件只给入口汇总（免费不稳定、收费带 API），提示自行甄别、别被骗
- 边界提示：批量注册类自动化涉及平台风控与合规风险，仅作原理了解

### 4.6 抓包转代码的两个效率工具（utils.py）
- `header_str_to_dict`：把 Charles 复制出的"制表符分隔、按行排列"的请求头字符串
  转成 dict——先按 `\n` 切行、去掉首尾空行，再按 `\t` 切 key/value
- `query_to_dict`：把 `a=1&b=2` 形式的 URL 参数串一行字典推导转 dict
- URL 编解码：`urllib.parse.quote('上海')` → `%E4%B8%8A%E6%B5%B7`；
  `unquote` 反向还原（拼 GET 参数时中文必须先编码）

## 五、关键知识清单

1. frida 双端版本必须一致；frida-server 要 `chmod +x` 后前台运行，配合 27042/27043 端口转发
2. attach = 已运行 + 用户操作触发点；spawn = 脚本唤起 + 启动即执行点（别忘了 resume）
3. hook 三载体同一骨架：Python 字符串注入 / JS 文件 + `frida -UF -l` / `frida -U -f 包名 -l`
4. hook 的意义：把"反编译静态猜测"升级为"运行时实证"，顺带拿明文和密文对照
5. 加密四分类：单向（MD5/SHA 不可逆）、对称（AES/DES 同密钥）、非对称（RSA 公私钥）、
   Base64 只是编码；还原 DES 关键在填充方案，还原 RSA 关键在签名/验签
6. 金树林案例的接口链：phoneCode(serviceType 5/6) → memberRegister → login 拿 JWT →
   Mobile-Token 头鉴权查询；token 是 JWT，可解出 userId/username/过期时间
7. 工具函数：请求头字符串转 dict、URL 参数串转 dict、quote/unquote——抓包到脚本的搬运工
