## 1. 静态分析 vs 动态调试

| | 做法 | 强项 |
| --- | --- | --- |
| 静态分析 | jadx 反编译 apk + IDA 反编译 so，配合 frida hook | 全局看结构、找关键字、批量定位 |
| 动态调试 | 在指定代码位置下断点，让 App 跑起来，停在断点处逐步看寄存器/变量 | 看运行时的真实值、走分支、验证猜想 |

动态调试分两个层级，对应两种代码：

- **dex 调试**：调 APK 里的 Java 代码，语言是 **smali**；
- **so 调试**：调 APK 里的 C/C++ 代码，语言是 **arm 汇编**。

两层的目标一致：把「猜」变成「看」。静态分析里拿不准的值（某个参数怎么来的、某分支走没走），到断点上直接读。

## 2. 前置一：smali 语法

### 2.1 为什么必须先学

`java → APK(dex) → DVM/ART 虚拟机` 是安卓的正常链路；逆向时 `dex → smali → Java` 是反编译链路。下断点是在 **smali 层**下，看不懂 smali 就无法判断该断哪一行、断点处是个什么值。

速成办法：自己写 Java 用 **IntelliJ IDEA + java2smali 插件**转出来对照看，比啃文档快。

### 2.2 文件头与寄存器

- `registers` 声明该方法用到多少个寄存器；
- 局部变量寄存器 `v0、v1、v2...`；
- 参数寄存器 `p0、p1、p2...`（p0 通常是 this，静态方法则直接从参数开始）；
- **DVM 只支持 32 位；ART 支持 64 位并兼容 32 位，Android 5.0 之后 ART 逐步取代 DVM**——这决定了你看到的寄存器布局和指令宽度。

### 2.3 方法与调用

| 分类 | 包含 | 调用指令 |
| --- | --- | --- |
| direct methods | 构造方法、私有方法、静态方法 | `invoke-direct`、`invoke-static` |
| virtual methods | 普通成员方法 | `invoke-virtual` |

有返回值时用 **`move-result`**（基本类型）或 **`move-result-object`**（对象）接住，紧跟在 invoke 之后。

### 2.4 字段

- `iget / iput`：对象成员变量的读 / 写；
- `sget / sput`：静态成员变量的读 / 写；
- 后缀规则：带 `-object` 表示操作的是对象类型，不带则是基本类型，`boolean` 用 `-boolean` 后缀（如 `sget-boolean`）。

这条规则和前面 unidbg 补环境里的「静态字段按类型分三个 override」是同一件事的两种视角。

### 2.5 条件跳转速查

| 指令 | 含义 |
| --- | --- |
| `if-eq / if-eqz` | 等于 / 等于 0 则跳转 |
| `if-ne / if-nez` | 不等于 / 不等于 0 则跳转 |
| `if-lt / if-ltz` | 小于 / 小于 0 |
| `if-le / if-lez` | 小于等于 / 小于等于 0 |
| `if-gt / if-gtz` | 大于 / 大于 0 |
| `if-ge / if-gez` | 大于等于 / 大于等于 0 |
| `goto` | 无条件跳转到标签 |
| `switch` | 分支跳转（对照 case 值） |

改包时最常动这里：把 `if-eqz`（结果为 0 才跳）改成相反条件，或者干脆 `goto` 跳过校验。

### 2.6 常量与类型字母

| 指令 | 用途 |
| --- | --- |
| `const/4` | 4 位整数常量 |
| `const/16` | 16 位整数常量 |
| `const` | 32 位整数常量 |
| `const-wide` | 64 位整数常量 |
| `const-string` | 字符串常量 |

类型字母：`V` void、`Z` boolean、`B` byte、`S` short、`C` char、`I` int、`J` long、`F` float、`D` double、`L包/类;` 对象、`[` 数组（`[I` = int[]）。这套字母表和 JNI 签名完全一致，unidbg 那边也是同一套。

官方指令表：`https://source.android.com/docs/core/runtime/dalvik-bytecode`。

## 3. 前置二：调试权限

安卓默认不允许随便调试，满足下面之一才行：

1. **系统属性 `ro.debuggable=1`**（默认 0）——推荐；
2. 目标 App 的 `AndroidManifest.xml` 里 `application` 标签带 `android:debuggable="true"`——可以用 MT 管理器改完重新签名。

### 3.1 Magisk 模块改属性（推荐）

```
# 先确认当前值
adb shell getprop ro.debuggable      → 0

# 刷模块：MagiskHidePropsConf-v6.1.2.zip 传到手机 → 面具里刷入 → 重启

# 改值
adb shell
props
  选 5 - Add/edit custom props
  选 n - New custom prop
  输入 ro.debuggable（模块会提示这是 sensitive prop，输入 y 确认）
  输入新值 1
  选择生效阶段：1 - Default（也可 post-fs-data / late_start service / Both）
  最后输入 y 重启

# 复查
adb shell getprop ro.debuggable      → 1
```

不想要了就回 `props` 里把这条自定义属性删掉。

### 3.2 AOSP 三档编译选项（理解为什么 userdebug 能调）

| 选项 | ro.secure | ro.debuggable | adb | 说明 |
| --- | --- | --- | --- | --- |
| eng | 0（关安全检查） | 1 | 默认开，adb 有 root | 开发版 |
| userdebug | 1 | **1** | 默认开，adb 有 root | 有 root 有调试，调试首选 |
| user | 1 | **0** | 默认关，无 root | 生产版 |

之前 AOSP 专题课里故意在 userdebug 基础上强制设 `ro.debuggable=0`，要开调试就把那个强制动作去掉。

## 4. dex 调试：三种工具，五步流程

| 方式 | 备注 |
| --- | --- |
| **JEB** | 课件推荐；5.19 版本 **JDK8 跑不起来，要装 JDK17** |
| jadx v1.4.7 | 免费，够用 |
| Android Studio + smalidea 插件 | 另一种选择 |

### 4.1 jadx 流程

1. 用 jadx 打开 APK（反编译）；
2. 点工具栏的 debug 图标并运行 App；
3. 弹出设备/进程列表，选目标 App 的包名双击；
4. 等它生成可调试的 smali 代码；
5. 在 smali 行上打断点，App 跑到就停下，看寄存器与局部变量。

### 4.2 JEB 流程

1. 反编译 APK；
2. 在目标 smali 行上 `Ctrl + B` 下断点；
3. 点调试按钮，连上设备跑起来。

两者都要求第 3 节的条件先满足（否则进程列表空或附加失败）。

### 4.3 改包：smali 的实际用途

学会 smali 之后，不一定要调试，直接改字节就能改行为，工具是 **MT 管理器**（手机上操作）：

- 案例一：**油联合伙人 v1.4**，改页面显示内容；
- 案例二：**识货 v7.20.1**，让更新弹框不弹出来。

通用步骤：APK 传到手机 → MT 管理器打开 → 定位到目标 smali 行改指令/常量 → **重新签名**。因为改完原签名就失效了，不重签装不上（也跑不起来）。这也是理解「签名校验」最直观的入口：开发 → 签名 → 运行时校验。

## 5. so 调试：先自己造一个靶子

真实 App 的 so 带壳带混淆，不适合当第一个调试对象。课件自己写了 `SoDebug` 工程（`com.nb.sodebug`）：

- 用 Android Studio 的 **Native C++ 模板**创建；
- 界面一个按钮，点击触发 `Utils.demo()`；
- `Utils.java` 静态块 `System.loadLibrary("utils")`，方法 `public static native int demo();`
- `utils.c` 里就是 `age=19 + size=99` 返回结果（故意简单，方便看清寄存器）；
- `CMakeLists.txt` 把 `utils.c` 编成 `libutils.so`。

两个工程细节：

- `extractNativeLibs`：设成 true 时，安装后 so 会被解压到 App 安装目录（方便 adb 取出来丢给 IDA）；设 false 则 so 留在 APK 里直接映射。
- 安装：`adb install xxx.apk`；若报 testOnly 相关错误用 `adb install -t xxx.apk`。

有了靶子，后面的断点位置、寄存器值都是可预期的，调试流程才学得会。

## 6. IDA 附加调试（attach 模式）

**特点**：App 先正常启动，等 so 加载完再附加进去，断点下在「已经运行的进程」上。适合断点位置**靠后**（比如点按钮后的计算）。

### 6.1 步骤

1. 手机安装 App 并**启动**，先点一下相关功能让 so 加载进内存（关键，so 没加载就没法在它上面下断）；
2. 把 IDA 安装目录 `dbgsrv\` 下的 `android_server` / `android_server64` 推到手机：

```
adb push D:\Service\IDA7.5\dbgsrv\android_server   /data/local/tmp/as75
adb push D:\Service\IDA7.5\dbgsrv\android_server64 /data/local/tmp/as75-64
```

3. 给执行权限：

```
adb shell
su
cd /data/local/tmp/
chmod 755 as75
chmod 755 as75-64
```

4. 按位数启动（默认监听 23946）：

```
./as75-64
# IDA Android 64-bit remote debug server(ST) v7.5.26 ... Listening on 0.0.0.0:23946...
```

5. 电脑端端口转发：`adb forward tcp:23946 tcp:23946`（课件里也有 `tcp:9001`）；
6. IDA 选对应位数的版本打开，`Debugger → Attach` 选进程；
7. 在 IDA 里定位到目标 so（模块列表里找 `libutils.so`），切到汇编视图，**F2 下断点**；
8. 手机上点按钮触发，IDA 就停在断点，**F8** 单步走。

### 6.2 选 as75 还是 as75-64

看两个因素：**手机 CPU 位数** × **APK 里 so 的目录**。

| 手机 CPU | App 的 lib 目录 | 用哪个 server |
| --- | --- | --- |
| arm64-v8a（64 位） | arm64-v8a | `android_server64`（as75-64） |
| arm64-v8a（64 位） | armeabi-v7a | `android_server`（as75，32 位） |
| 32 位 | armeabi-v7a | `android_server` |

原则：**跟 APK 里实际加载的那个 so 的位数走**，64 位系统也能跑 32 位 so。

### 6.3 两个小坑

- **先让 so 加载**：附加调试的前提是 so 已经在内存里，先点一遍功能再 attach。
- **JDK 版本影响 IDA 里 so 成员的显示**：课件特意把 JDK 切成 **1.8** 再开 IDA（注意这和 JEB 要 JDK17 是相反的要求，两个工具别混用同一个 JDK）。

## 7. IDA 启动调试（spawn 模式）

**特点**：App 还没跑起来就先挂上，断点下在「启动阶段」。适合断点位置**靠前**（so 一加载就执行、初始化里的校验）。

流程比 attach 多一个「假启动 + 放行」的环节，需要 DDMS 配合。

### 7.1 步骤

1. 手机安装 App，**不要启动**；
2. 推 `android_server` / `android_server64` 到 `/data/local/tmp/`，`chmod 755`（同 6.1）；
3. 启动 server：`./as83`（8.3 版本命名），并 `adb forward tcp:23946 tcp:23946`；
4. **以调试模式假启动 App**：

```
adb shell am start -D -n com.nb.sodebug/com.nb.sodebug.MainActivity
```

`-D` 表示等调试器挂上才继续，App 此时会卡在启动界面（白屏/黑屏）；

5. 打开 **DDMS**，能看到目标进程（8700 端口是它的 jdwp 调试端口）；
6. IDA 里先 `adb` 打开目标 so（解压 APK 取出 so 用 IDA 分析），在目标汇编行 **F2 下断点**，然后 attach 到进程；
7. **用 jdb 放行**：

```
jdb -connect com.sun.jdi.SocketAttach:hostname=127.0.0.1,port=8700
```

8. App 继续启动，走到断点停下，F8 逐步调试。

### 7.2 为什么必须用 DDMS 掺一脚

`am start -D` 之后进程处于「等待调试器」状态，只有挂上调试器（jdb 通过 jdwp 端口）它才会继续。IDA 负责 native 断点，DDMS/jdb 负责把 Java 层这个「暂停开关」打开。

### 7.3 版本坑

**IDA 7.5 做启动调试会崩溃，换 `IDA_Pro_v8.3_Portable`。** 附加调试用 7.5 没问题，所以课件里两个版本并存不是重复。

## 8. DDMS 与常见故障

DDMS（Dalvik Debug Monitor Service）是安卓开发环境自带的虚拟机调试监控服务，这里主要用来**看进程列表**和配合 spawn 模式放行。

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 进程列表空的 | `ro.debuggable=0` | 按第 3 节改成 1 |
| 进程名全显示成 `?` | adb 缓存/连接问题 | 保持 DDMS 开着，`adb kill-server` → `adb start-server` |
| DDMS 开着时新装的 App 读不到名字 | 同上 | 同样重启 adb |

配套的系统命令：

```
# 看端口被谁占了（Windows）
netstat -ano | findstr 8700
# 杀掉占用进程
taskkill /pid <PID> /f

# 看手机上 App 的进程 ID
adb shell ps -ef | grep com.nb.sodebug
# 或
adb shell ps | findstr com.nb.sodebug
```

## 9. 坑清单

1. **把 smali 当成 Java 看**：方法分 direct/virtual，调用指令不同，`move-result` 必须紧跟 invoke，看错一行就断错位置。
2. **没开调试权限就去连**：DDMS 列表空、IDA 附加失败，九成是 `ro.debuggable=0`。
3. **attach 时 so 还没加载**：在模块列表里找不到目标 so，先回手机点一遍功能。
4. **32/64 选错 server**：APK 里是 armeabi-v7a 却启 `android_server64`，附加后看不到目标模块。
5. **忘 `chmod 755`**：`./as75` 报 Permission denied。
6. **忘端口转发**：IDA 连不上 `127.0.0.1:23946`。
7. **JDK 版本打架**：IDA 要 1.8（否则 so 成员显示异常），JEB 5.19 要 17（JDK8 起不来），开工前先确认当前切的是哪个。
8. **IDA 7.5 做启动调试崩溃**：换 8.3。
9. **spawn 模式忘 jdb 放行**：App 一直卡在启动界面，以为断点没生效。
10. **改完 APK 不重签名**：装不上或运行即崩。
11. **改 smali 只改一行**：条件跳转改了但配套的 `const` 值没改，逻辑仍不对。
12. **把 `[` 数组类型看成对象**：`[I` 是 int[]，不是 `Ljava/lang/Integer;`。

## 10. 关键知识清单

- 静态分析靠反编译+hook 猜，动态调试靠断点看真值；两者互补，不是替代关系。
- 动态调试两个层级：**dex 调试（smali）** 与 **so 调试（arm 汇编）**。
- smali 核心：`registers` 声明寄存器数，`v` 局部 / `p` 参数；方法分 `direct`（构造/私有/静态，`invoke-direct`/`invoke-static`）与 `virtual`（`invoke-virtual`）；返回值用 `move-result` / `move-result-object`；字段 `iget/iput`（实例）、`sget/sput`（静态），`-object`/`-boolean` 表类型。
- 跳转表：`if-eq/ne/lt/le/gt/ge`（两寄存器比较）与 `if-eqz/nez/ltz/lez/gtz/gez`（与 0 比较），`goto` 无条件，`switch` 按 case 值。
- 常量：`const/4`、`const/16`、`const`、`const-wide`、`const-string`；类型字母 `V Z B S C I J F D L [ ` 与 JNI 签名同源。
- 调试权限两条路：系统属性 `ro.debuggable=1`（Magisk + MagiskHidePropsConf 改，或 AOSP 用 userdebug 编译），或 App manifest 里 `android:debuggable="true"`。
- AOSP 三档：eng（debuggable=1 且 secure=0）、userdebug（debuggable=1，调试首选）、user（debuggable=0）。
- dex 调试三工具：JEB（推荐，JDK17）、jadx 1.4.7、AS+smalidea。
- IDA 两种调试模式：**attach（先启动后附加，断靠后的逻辑）** vs **spawn（先断点后启动，断启动阶段）**。
- IDA 远程调试固定套路：push `android_server(64)` → `chmod 755` → 启动（默认 23946）→ `adb forward` → IDA attach/等启动 → F2 断点、F8 单步。
- server 位数跟 **APK 里 so 的位数**走，不跟手机位数走。
- spawn 模式三件套：`am start -D` 假启动 + IDA 断点/附加 + `jdb -connect ... port:8700` 放行；IDA 7.5 会崩，用 8.3。
- DDMS 三个典型故障都指向 adb 状态：无列表查 `ro.debuggable`，显示 `?` 或新应用读不到名就 `adb kill-server` + `start-server`。
- 排障命令：`netstat -ano | findstr 端口`、`taskkill /pid <PID> /f`、`adb shell ps -ef | grep 包名`。
- smali 的实战出口是改包：MT 管理器改指令 → 重签名 → 安装，用来改页面显示、去更新弹框这类需求。
- 后续深化方向（录播）：汇编与 C 语言对照、反调试、LLVM 混淆。
