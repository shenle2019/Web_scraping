## 一、这个案例在知识线上的位置

day12 认识 JNI 与 so，day13 把静态注册/动态注册和"在 so 里定位函数"讲透。day14 是第一次把完整链路压在**第三方 App** 上：不是自己写的 demo，没有源码可对，只能靠抓包、反编译、Hook 三条线索互相印证。

课件给的标准六步，就是后面所有商业 App 案例的骨架：

1. 选一个合适的历史版本装到手机；
2. 抓包；
3. 分析登录请求，确定**哪几个参数需要破**；
4. jadx 反编译，读 Java 代码；
5. 关键字定位 + **Hook 验证**；
6. Python 还原算法。

与 day11 那套"逆向自己的 App 五步"（编译→装机→抓包→jadx→Python 复刻）同构，差别只在第 1 步：拿不到源码，得挑一个**能装、能抓包、没上强加固**的旧版本。

## 二、目标与抓包环境

- 目标：车智赢+（二手车之家商家端）的登录。
- 版本：课件正文用的是 **3.22.0**，课堂录像与目录里的安装包是 **3.56.0**。两版字段集不同（见第十节第 1 条），对照代码前先确认 appversion。
- 装机：`adb install` 安装 apk。
- 抓 HTTPS 的前置：电脑端 Charles 开 `SSL Proxying Settings`，手机端配系统代理；手机要能信任 Charles 证书（root 机装进系统证书区）。

## 三、抓包结论：只有三个参数要破

请求：`POST https://dealercloudapi.che168.com/tradercloud/sealed/login/login.ashx`

请求体字段（以 3.56.0 为例）：

| 字段 | 值 | 性质 |
| --- | --- | --- |
| `_appid` | atc.android | 固定 |
| `appversion` | 3.56.0 | 固定（跟随版本） |
| `channelid` | csy | 固定 |
| `username` | 手机号 | 我们的输入 |
| `pwd` | 32 位十六进制 | **要破** |
| `udid` | Base64 串 | **要破** |
| `_sign` | 32 位大写十六进制 | **要破** |
| `signkey` / `type` | 空 | 3.56 新增，空值但参与签名 |

两个判断动作值得记住：

- **先验证请求头**：改一改请求头重发，照样能通 → 说明校验不在头里，压力全在 body。省掉一整条排除线索。
- **看 _sign 的作用域**：它对整个请求体签名，改任意字段签名都会失配 → `_sign` 必须在其它字段都确定之后才能算。

于是这三个参数之间有了**依赖顺序**：`pwd`（最简单，先破）→ `udid`（`_sign` 的输入之一，必须先确定）→ `_sign`（最后算）。整节课的推进顺序就是按这个依赖来的，不是为了讲解方便随便排的。

## 四、jadx 定位登录代码

三种手法课件都用了：

1. **搜 URL 片段**：搜 `login.ashx` 或完整地址，直接落到请求构造处。
2. **搜参数名**：搜 `pwd`，看谁在往请求里塞这个字段。
3. **右键"查找用例"**：定位到 `LOGIN_URL` 常量后，查谁引用它，双击进去。

最终拿到的构造链是 `builder.tag(...).method(POST).signType(1).url(LOGIN_URL).param("username", ...).param("pwd", SecurityUtil.encodeMD5(str3))`。

这一行里有两个后续要用到的信息：`pwd` 走了 `SecurityUtil.encodeMD5`；`signType(1)` 的 `1` 就是后来 `signByType(i, treeMap)` 里的 `i`——**它不是随手写的常量，而是签名盐的选择器**。

## 五、pwd：一层裸 MD5

抓到的 `pwd` 是 32 位十六进制，形态上就是 MD5。跳声明看 `encodeMD5` 的实现，确认三件事：

- `MessageDigest.getInstance("MD5")` 标准算法；
- `update(bytes)` 只喂了一次明文，`digest()` 也没带参数 → **没加盐**；
- 手工把 16 字节摘要转 hex：用字符表 `0-9A-F`，`(b >>> 4) & 15` 取高 4 位、`b & 15` 取低 4 位，最后 `toLowerCase()`。

课件给了一句判断口诀，值得直接背下来——**看有没有加盐，只查两处**：`update()` 时是否多喂了一次盐，`digest()` 是否带参数。这版代码两处都干净，所以 `pwd = md5(明文)` 小写。

一条容易被忽略的细节：`encodeMD5` 返回的是**小写**，而 `_sign` 最终是**大写**（`signByType` 里又 `toUpperCase` 了一次）。同一个工具函数在两处用法大小写不同，写 Python 时搞反就是全错。

混淆痕迹也在这儿第一次出现：`cArr[b & bx.m]` 里的 `bx.m` 就是 `15`，被混淆器提成了常量引用。读反编译代码遇到这类"莫名其妙的外部常量"，先按位运算语义猜它的值（这里是与低 4 位掩码），再回 `bx` 类里确认。

**Hook 验证**：`Java.use("com.autohome.ahkit.utils.SecurityUtil")` 替换 `encodeMD5`，打印入参与返回值，能打出"明文 → 密文"就说明这条路径确实在登录时走到了。

## 六、_sign：先定位置，再解算法

### 6.1 搜到了不等于找到了

搜 `_sign` 得到 5 个结果，前 4 个都是同一句：

```java
treeMap.put("_sign", toSign(context, treeMap));
```

看起来像正主。但 Hook `com.autohome.ahkit.AHAPIHelper.toSign` 后**一行都没打印**——登录流程根本没走它。

这是本课最重要的方法论：**关键字搜索只能给候选，是否命中要靠 Hook 验证**。反编译里同名的方法、看起来更"正统"的封装，完全可能是老版本遗留或者别的业务线在用。

排除之后剩两个候选：`LaunchModel.lambda$initRequestCommonParams$0(int, TreeMap)` 和 `getRequestParams(TreeMap)`。Hook 前者，打印出来——确认命中。

顺带一个认知：`lambda$initRequestCommonParams$0` 这种名字是 **lambda 表达式脱糖后生成的合成方法名**，不是源码里写的、也不是混淆加的。jadx 里看到 `lambda$` 前缀不要绕路，Frida 可以直接用这个名字 Hook。

### 6.2 这个方法干了什么

Hook 打印的结果把输入输出摆得很清楚：

- 进去时字典只有 `pwd`、`username`、`signkey`、`type`（就是我们在界面上输入的东西加空字段）；
- 出来时多了 `_appid`、`appversion`、`channelid`、`udid`、`_sign`。

源码逻辑对得上：缺 `_appid` / `channelid` / `appversion` / `udid` 就逐个补进 TreeMap，`udid` 来自 `AppUtils.getUDID(Context)`，有 `userkey` 再补一个，`checkNullParams` 检查一遍，最后一行才把 `SignManager.INSTANCE.signByType(i, treeMap)` 的结果塞进 `_sign`。

注意最后一行执行时，`_sign` **还不在**字典里——所以参与签名的永远是"除 `_sign` 以外的全部参数"。这一点决定了 Python 里的组参顺序：先算完所有字段，再算 sign，最后把 sign 加进去发请求。

### 6.3 signByType 的算法

结构就四步，没有花招：

1. 按 `i` 选盐：`i = 0` 用 `KEY_V1`（默认），`i = 1` 用 `KEY_V2`，`i = 2` 用 `KEY_SHARE`，`i = 3` 用 `KEY_AUTOHOME`；
2. `StringBuilder` 先 `append(盐)`，再遍历 `paramMap` **逐个 append(key) 和 append(value)**，最后再 `append(盐)`；
3. 对整串做 `encodeMD5`；
4. `toUpperCase(Locale.ROOT)` 返回。

登录走的是 `signType(1)`，所以盐是 `KEY_V2` = `W@oC!AH_6Ew1f6%8`（Hook 一下 `signByType` 打印 `i` 就能确认是 1，不用猜）。

三个关键点：

- **为什么 Python 要用 `sorted()`**：`paramMap` 是 `TreeMap`，`keySet()` 遍历顺序是 key 的自然序（ASCII）。换成 HashMap，顺序不确定，同一份参数每次 sign 都不同。TreeMap 在这里的唯一作用就是"给签名提供一个稳定顺序"——反过来说，**看到参数用 TreeMap 装，就要想到"签名按 key 排序拼接"**。
- **拼接无分隔符**：`key` 直接接 `value`，没有 `=`、没有 `&`。所以 `_appid` + `atc.android` 会连成 `_appidatc.android`。
- **空值也要拼**：`signkey`、`type` 为空，拼接结果里仍然会出现 `signkey`、`type` 这两个键名（后面跟空字符串）。3.22 版没有这两个字段，漏掉或误加都会导致 sign 错。

## 七、udid：一串设备信息过 3DES

### 7.1 明文结构

`AppUtils.getUDID(Context)` 只有一行，把三段用 `|` 拼起来交给 `SecurityUtil.encode3Des`：

```
IMEI | System.nanoTime() | SPUtils.getDeviceId()
```

分隔符来自 `HiAnalyticsConstant.REPORT_VAL_SEPARATOR`，跳声明就是一个 `"|"`。这类"常量藏在另一个类里"的字段，跳一次声明就能定死，不用猜。

### 7.2 三段各自怎么造

**第一段：IMEI**。源码给了四级降级，值得完整理解，因为它决定了我们能用什么替代：

1. 先从 SharedPreferences 读（装过一次就有了）；
2. 读不到就 `TelephonyManager.getDeviceId()` 取真 IMEI（Android 10 之后普通应用已拿不到）；
3. 还拿不到就用 WiFi MAC 经 `UUID.nameUUIDFromBytes(...)` 生成；
4. 再不行用 AndroidID + UUID 生成；
5. 连读取电话状态的权限都没有，直接返回字符串 `"sssss"`。

课件贴出的代码里有个值得留意的现象：MAC 分支算完 `imei` 之后，**紧接着被下一行无条件覆盖**成 `getIMEIbyAndroidIDandUUID()` 的结果——这段 MAC 逻辑实际是死代码。读反编译结果时遇到这种"算完立刻被覆盖"的赋值，别照着还原，先判断哪个分支真正生效。

我们的四种替代方案（课件都给了）：直接 `uuid4()`、直接用 `"sssss"`、去手机上 `/data/data/<包名>/shared_prefs/` 把已存的 imei cat 出来、或者 Hook `SPUtils.getIMEI` 取值。这四种是按"可靠性从高到低"排的：能抠出真值就别造。

**第二段：`System.nanoTime()`**。Android 上是**开机到现在的纳秒数**，与桌面 JVM 里那个任意基准的 `nanoTime` 语义不同。课件的做法是在 `5.1e12 ~ 7.1e12` 之间随机取一个——能通过，说明这个登录链路对时间合理性没有强校验。

**第三段：`SPUtils.getDeviceId()`**。从 xml 里读，默认空串。这里演示了逆向里很通用的一个动作：**找到一个"读"的位置后，用"查找用例"去找"写"的位置，再看写的位置的数据从哪来**。追下去发现写入点是 `SPUtils.saveDeviceId(regDeviceResult.deviceid)`，而 `deviceid` 来自 App 首次启动时请求 `/tradercloud/v100/push/regdevice.ashx` 的后端返回——也就是"服务端下发设备号，App 存进 xml 长期复用"。

结论：这个值实测固定（课件记的是 `381632`），而且**直接留空也能通过**。能用固定值或空串的地方就不要花时间去复现它的生成逻辑。

### 7.3 3DES 的参数

`encode3Des` 的实现三句话：

- `key = AHAPIHelper.getDesKey(context)`——由 so 提供；
- `Cipher.getInstance("desede/CBC/PKCS5Padding")`；
- `iv = "appapich"`，是类里的 `private static final` 常量。

所以 key 和 iv **都是固定的**，只要拿到这两个值，整个 udid 就能离线复算。这也解释了这个 App 的防护强度：算法是标准的，密钥写死在 so 里，属于"提高门槛"而不是"真正不可破"。

输出形态：`cipher.doFinal(...)` 之后走 `encode(bArr).toString()`。课件没展开 `encode` 的实现，但从抓包结果带 `+`、`/`、`==` 判断是 **Base64**（不是 hex）。这一条很关键——写成 hex 会得到一个完全不同的字符串，而且长度也不一样。

Python 侧对应的四个要点：`from Crypto.Cipher import DES3`、`DES3.MODE_CBC`、手写 PKCS5/7 填充（补到 8 的倍数）、`base64.b64encode`。另外 **key 要切前 24 字节**：字符串看着是 32 个字符，但 DESedeKeySpec 只取前 24 字节，Python 不切片会直接抛异常。

### 7.4 三段式验证法

课件对 udid 和 des 的处理顺序，是一套可复用的验证流程：

1. Hook `getDesKey` → 拿到 key 的明文；
2. 用 Python 离线加密一段明文 → 得到密文；
3. Hook `encode3Des` → 同时拿到"传入的明文"和"返回的密文"，和自己算的对比。

两边一致，算法就算还原完了。比"发一次请求看返回码"快得多，也不受风控、网络、账号状态干扰。

## 八、so 里找 des key：IDA 七步

虽然 hook 已经能拿到 key，课件还是走了一遍 so，目的是确认"这个 key 是写死的常量，不依赖服务端"。

1. 从 apk 里取出 `lib/arm64-v8a/libnative-lib.so`；
2. IDA 打开 → `Exports`（导出符号）→ `Quick filter` 搜 `java`；
3. 双击 `Java_com_autohome_ahkit_jni_CheckSignUtil_get3desKey`——**静态注册的好处在这里体现：符号名直接指向对应方法**；
4. 按 `F5` 出伪 C；
5. 右键 `Hide casts`（隐藏强制类型转换），噪音去掉一大半；
6. `File → Load file → Parse C Header file`，选 `jni.h`（或 `jni_md.h`）；
7. 把 `__int64 a1` 右键 `Convert to struct *` → 选 `JNIEnv_`。

做完第 7 步，`sub_xxx(a1, ...)` 会变成 `a1->functions->NewStringUTF(a1, DES3_KEY)`——一眼就能看出"它在原样返回一个常量"。这就是 `jni-include` 目录存在的意义：**不导头文件，IDA 不知道 `a1` 是 `JNIEnv*`，伪 C 里只剩一串函数指针偏移**。

伪 C 里有两段逻辑值得记：

- `if (!strstr(checkState, "yes"))` → `checkPackage(a1, a3)` → 把结果写进 `checkState`，之后再调用就走缓存。这是**首次调用才做包名/环境校验**的轻量防篡改雏形，说明这个函数不只是"取 key"，还兼职看门。
- 最后 `return a1->functions->NewStringUTF(a1, DES3_KEY)`，双击 `DES3_KEY` 落在 `.rodata`，值就是 `appapiche168comappapiche168comap`。

## 九、整合脚本的骨架

最终脚本就六段，顺序不能乱：

1. `md5()`、`des3()` 两个算法函数；
2. 造 `imei`、`nano_time`、`device_id`，先算出 `udid`；
3. 组参数字典：`pwd = md5(明文)`、`udid = des3(...)`、其余固定字段；
4. 按 key 排序拼串 → 前后各加盐 → `md5` → `upper()`；
5. 把 `_sign` 加入字典；
6. `requests.post(url, data=dict, verify=False)`。

`verify=False` 加关掉 urllib3 告警，是抓包环境（自签证书）的产物，跟业务无关——但既然请求能通、返回正确，就不用去折腾证书链。

## 十、口径偏差与坑

1. **两条版本线并存**：正文基于 3.22.0（抓包 `appversion=3.22.0`，6 个参数），课堂录像基于 3.56.0（8 个参数，多 `signkey`、`type`，且为空）。对照时先看 appversion，再决定参数字典里要不要那两个空字段。
2. **课件小标题重复**：`4.2.1` 出现两次（md5 算法 / hook 密码）、`4.3.1` 出现两次、`4.4.6` 出现两次且 `4.4.6.2` 也重复。按标题找，别按编号找。
3. **`bx.m` 就是 15**：MD5 转 hex 的低 4 位掩码被混淆成常量引用，不认出来会以为还有别的含义。
4. **`getIMEI` 里的 MAC 分支是死代码**：算完立刻被下一行的 AndroidID+UUID 覆盖。
5. **课堂笔记 4.3.1 的 Hook 脚本贴了重复两份**（第一次写完没删，紧接着又粘一遍），直接跑会重复 Hook 同一方法。实际用一份即可。
6. **`encode(bArr)` 的实现课件没给**：从结果形态判断是 Base64。照 hex 写会让 udid 完全对不上。
7. **3DES 的 key 只有前 24 字节生效**：源码字符串 32 字符，Java 的 `DESedeKeySpec` 只取前 24 字节；Python 不切片会直接报错。
8. **`pwd` 小写、`_sign` 大写**：两者都来自 `encodeMD5`，但 `_sign` 多了一步 `toUpperCase`，写脚本时容易在最后漏掉。
9. **空值字段必须参与签名**：`signkey`、`type` 为空也要拼"键名 + 空串"，这是 3.56 版与 3.22 版 sign 不同的主要原因。
10. **`System.nanoTime()` 的量级要对**：Android 是开机以来的纳秒（10¹² 级）。课件用同量级随机值即可通过，但这个接口是否做时间合理性校验，课件没有给出对照实验，别把它当通用结论。
11. **`attach("车智赢+")` 用的是应用显示名**：attach 失败时先 `frida-ps -U` 查实际进程名，或直接改用包名。
12. **`_sign` 类方案的通律**：参与签名的参数集必须与实际发出的字段**完全一致**，多一个少一个都会错；`_sign` 自己永远不参与计算。

## 关键知识清单

- **六步流程**：选版本 → 抓包 → 定需破参数 → jadx → 关键字 + Hook 验证 → 还原算法。
- **三参数依赖**：`pwd` 独立；`udid` 是签名的输入，必须先定；`_sign` 覆盖全字段，最后算；`_sign` 自身不参与。
- **pwd**：裸 MD5（无盐），转 hex 后小写；判断加盐只看 `update()` 与 `digest()` 两处。
- **签名算法**：`TreeMap` 按 key 排序 → `key+value` 无分隔符拼接 → 前后各加一次盐 → MD5 → 大写。盐由 `signType` 的 `i` 选择，登录用 `i=1` 对应 `W@oC!AH_6Ew1f6%8`。
- **TreeMap 的意义**：为签名提供稳定顺序；Python 里对应 `sorted(dict.keys())`。
- **udid**：`3DES/CBC/PKCS5Padding`，`key` 为 so 里的固定常量（前 24 字节生效），`iv = "appapich"`，输出 Base64；明文是 `IMEI|nanoTime|deviceId`。
- **设备标识的降级链**：sp 缓存 → 真 IMEI → MAC 转 UUID → AndroidID+UUID → 兜底 `"sssss"`；MAC 那段被覆盖，实际是死代码。
- **deviceId**：xml 里读，写入来自首次启动的 `/tradercloud/v100/push/regdevice.ashx` 返回，固定值且可为空；方法是用"读"找"写"，再追数据来源。
- **IDA 读 JNI so 的七步**：导出搜 `java` → F5 → Hide casts → Parse C Header（`jni.h`）→ `a1` 转 `JNIEnv_` → 看到 `a1->functions->NewStringUTF()` → 双击常量落 `.rodata`。
- **静态注册的红利**：`Java_com_autohome_ahkit_jni_CheckSignUtil_get3desKey` 这种符号名，让"从 Java 方法直接跳到 C 实现"成为一步操作。
- **验证方法论**：Hook 中间值 → 本地复算 → Hook 同点对比，三步比发请求试错快且稳；关键字搜索出的候选必须 Hook 验路径。
