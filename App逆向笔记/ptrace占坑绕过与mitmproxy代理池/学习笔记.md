## 1. 案例全景

四块内容，前两块是逆向，后两块是把请求"洗"得像真人：

| 模块 | 解决什么 | 关键手法 |
| --- | --- | --- |

## 2. 抓包与改包结论

### 2.1 短信登录（新版主线）

```
POST https://vega.huoyunren.com/v2/isnb-openapi-proxy/auth/router
query: method / phone / accessid / g7timestamp / app / ua
       / appclientversion / referer / sign
body : phone, captcha（验证码登录时）
```

`method` 是业务路由，同一个地址干两件事：

| 场景 | method |
| --- | --- |
| 发短信 | `ntocc-contract.contract.sendVerificationCode` |
| 验证码登录 | `ntocc-contract.contract.loginOrRegisterByPhoneAndCode` |

请求头里 `x-b3-traceid`（一长串 hex）、`from: driver`、`x-g7-source`（一段 JSON，标明 native/android/sxb）、`user-agent: okhttp/3.14.9`。

### 2.2 改包结论

删掉 `x-b3-traceid`、`referer`、`accessid` 后接口仍通，**只有 `sign` 删不得**。这条判据把工作量从"整包分析"缩到"只破一个参数"。

`referer` 的来历也查清了：Java 里 `s()` 方法先从 SP 读 `vega_referer`，读不到才返回默认常量 `d507c00281c733bd693e5049ea33ad7e`。所以抓包看到的一直是同一个值——**它是缓存，不是动态签名**。

## 3. sign：HmacSHA1(路径 + 时间戳)

### 3.1 定位

直接搜 `sign` 命中太多，课件改搜 **`g7timestamp`**——这个字段名是业务自造的，一搜就落到拼 query 的那段代码：

```
sb.append("&sign=");
sb.append(new GatewaySign4Customer().a(EnvUtil.m37779d().f7738j, str2, valueOf, str));
```

`EnvUtil.m37779d().f7738j` 就是 key，**不在签名类里，而在环境配置类里**——这是本次定位最值得记的一点：签名类里看不到硬编码密钥时，往调用它的入参追。

### 3.2 算法

签名方法内部只有两件事：

```
明文 = str2 + "\n" + str3 + "\n/" + str4     // 方法 + 换行 + 时间戳 + 换行 + 斜杠 + 路径
摘要 = Base64( HmacSHA1(key, 明文) )
sign = Uri.encode(摘要)                       // 还要做一次 URL 编码
```

四个入参实测含义：

| 位置 | 值 | 说明 |
| --- | --- | --- |
| 1 | `1KMrg0dfufc0wpnXEJacEQX1YEUYA0Ja` | key，多抓几次不变 |
| 2 | `POST` | 请求方法 |
| 3 | `1694450485059` | 毫秒时间戳，与 query 里的 `g7timestamp` 同值 |
| 4 | `inside.php` 或 `v2/isnb-openapi-proxy/auth/router` | 请求路径，**不带前导斜杠**（代码里自己补 `"/"`） |

hook 返回 `5VnGRNih2xWwXIF3QeuAYdD7j%2F4%3D` 这种形态，正好印证最后一层 `Uri.encode`：Base64 里的 `/` 变 `%2F`、`=` 变 `%3D`。Python 侧的等价做法是 `quote_plus`。

### 3.3 版本带来的两个变量

- 类名：v4.0.9 是 `cmt.chinaway.com.lite.q.p0`（内部用 `s0`），v4.7.8 是 `cmt.chinaway.com.lite.s.q1`（内部用 `t1`）
- 路径：`inside.php` → `v2/isnb-openapi-proxy/auth/router`

算法与 key 都没变，变的只是"从哪进"和"拼什么路径"。所以升级版本后**先重新 hook 一遍这四个参数**，别急着改代码。

## 4. 旧版 mobile / password：RSA 分段 + 自定义十六进制

这部分只在 v4.0.9 有效，课件明确标"旧版本不能用了"，但加密手法本身值得记。

### 4.1 定位

搜 `password` → 找到用 retrofit2 发请求的 `LoginResponseEntity` 相关类 → 发现多个调用点里密码都走 `n1.a(obj)` → 直接 hook `n1.a` 验证位置正确。

### 4.2 三段处理

```
1) RSA/ECB/PKCS1Padding 加密，公钥由同类的 b() 方法返回
2) 明文超过 117 字节就分段，每段单独 doFinal，结果拼进 ByteArrayOutputStream
3) Base64 编码 → 再去掉换行 → 最后丢给 c() 变成一串大写十六进制
```

几个细节：

- **117 不是随手写的**：1024 位密钥、PKCS1 填充要占 11 字节，一次最多喂 128-11=117 字节。换密钥长度，这个数要跟着变
- `Base64.encodeToString(..., 0)` 带换行，所以后面有 `.replace("\n", "")`。Java 侧用 flag=2（NO_WRAP）就没这一步，两种写法都见过
- `c()` 方法看着像"与运算后右移"的加密，实际只是**把每个字节拆成两个十六进制字符**（高 4 位、低 4 位各查一次 `0123456789ABCDEF`）。它是编码，不是加密——`& 240 >> 4` 和 `& 15` 就是取高低半字节

hook `n1.a` 能看到明文手机号进去、一长串 hex 出来；手机号和密码**各调一次**，所以两个字段的密文结构一样、内容不同。

## 5. ptrace 占坑：frida attach 不进去

### 5.1 现象与判据

`rdev.attach("司小宝")` 报 `ProcessNotFoundError: process not found`，但 App 明明开着。

区别两种报错：

| 报错 | 含义 |
| --- | --- |
| `unable to find process with name '司小宝'` | App 没启动 / 名字不对 |
| `ProcessNotFoundError: process not found` | App 在跑，但**被 ptrace 占坑了** |

判据在手机里：

```
adb shell → su → ps -A | grep lite
```

正常 App 只有一条主进程（不带 `:`）。司小宝跑起来会多一条名字像内核线程的进程 `__skb_recv_...`——**这就是占坑进程**。反过来看车智赢只有一条，所以它能正常 attach（课件拿它做了对照实验）。

`frida-ps -U -a` 只能列"正在运行的应用"，看不到这些子进程，别在这里找。

### 5.2 原理

frida 的注入依赖 `ptrace`，而一个进程**只能被 ptrace 一次**。App 启动时自己先 `PTRACE_TRACEME` 附加自己（占坑），后面 frida 再来就没位置了。这是主动反调试，不是检测 frida 特征，所以换 hluda 那种改名方案无效。

### 5.3 三种解法

| 解法 | 做法 | 代价 |
| --- | --- | --- |
| 杀占坑进程 | `kill` 掉 `__skb_recv_...` 那条再 attach | 课件这次试了没成功；且有的 App 杀了会连带主进程 |
| **spawn 抢跑** | `frida -U -f 包名 -l 脚本.js`，让 hook 在占坑进程起来之前就位 | 最省事，本次实际走通的路 |
| 改 AOSP | 编 `bionic/libc/bionic/ptrace.cpp`，让普通 App 自己附加自己时直接返回成功 | 要刷机，成本最高但一劳永逸 |

AOSP 那段的思路可以单独记：在 `ptrace` 包装函数里加判断——当 `getuid() > 10000`（普通 App）且 `req == PTRACE_TRACEME` 时直接 `return 0`（假装占坑成功，实际没占）；`PTRACE_ATTACH` 时若调用者是被 attach 进程的子进程也放行。核心是**只对 App 自己人放行假成功**，不影响系统调试。

## 6. 免费代理池（proxy_pool + Redis）

用途：批量请求时换出口 IP。课件把收费/免费的区别说得很直白——收费的稳定，免费的开源方案能用但不稳。

搭建链路：

```
git clone jhao104/proxy_pool → pip install -r requirements.txt
→ 装 Redis（msi 装完即用，resp 是客户端）
→ 改 setting.py：HOST/PORT、DB_CONN=redis://127.0.0.1:6379/0、PROXY_FETCHER=[...]
→ 起两个进程：proxyPool.py schedule（抓取+校验+入库）、proxyPool.py server（对外 API）
→ GET http://<host>:5000/get/?type=http  拿一个随机可用代理
```

三个要点：

1. **两个进程都要起**。`schedule` 负责爬代理、验证、写 Redis；`server` 只负责从 Redis 里挑一个给你。只起 server 会一直返回空
2. `PROXY_FETCHER` 是"启用哪些抓取源"的名单，对应 `fetcher/proxyFetcher.py` 里的 `freeProxyXX` 方法。免费源经常挂，名单要按当次可用性调
3. 官方还挂了个 demo（`demo.spiderpy.cn/get/`），不想自己搭可以直接调，但稳定性和归属都不保证

## 7. mitmproxy：能改包的代理

### 7.1 与 Charles 的区别

Charles 是"看"，mitmproxy 是"看 + 改 + 二次开发"。课件举的例子很到位：Charles 能把某个 url 的请求过滤出来看，但做不到"截获后把返回内容置空、真实内容存库、异常发邮件"——这类要写代码的定制，mitmproxy 挂个 Python 脚本就行。

### 7.2 三个命令

| 命令 | 用途 |
| --- | --- |
| `mitmproxy` | 终端交互界面，**Windows 上跑不了** |
| `mitmweb` | 浏览器界面，看包分析用它 |
| `mitmdump` | 纯命令行，配 `-s 脚本.py` 做定制，`-q` 关日志 |

### 7.3 手机侧

只配代理 → 只能抓 HTTP；要抓 HTTPS 得装证书：手机访问 `mitm.it` 下载 → **move cert 装成系统证书** → 重启。少了 move cert 这一步，Android 7+ 上抓到的就是一堆 CONNECT。

### 7.4 脚本的两个钩子

一个 mitmproxy 脚本就是两个函数：

- `request(flow)`：请求发出前，可读可改 query、path、body、header
- `response(flow)`：响应回来时，可读可改 `text` / `content` / `json()`

课件在 `response` 里直接把返回内容改成 `{"returncode":2040007,"message":"对不起"}`，演示"服务端返回什么由我说了算"。

### 7.5 上游代理：每个请求换一个出口

这是把代理池接进来的关键一行机制：

```
flow.server_conn.via = ServerSpec(("http", (ip, port)))
```

流程是：`request` 钩子里先向代理池 API 要一个代理（`/get/?type=http`），拆出 ip 和 port，然后把这条连接的"上游"指过去。于是**手机 → mitmproxy → 随机代理 → 目标站**，目标站看到的 IP 每次都不一样。

启动参数（课件那条长命令逐项都有原因）：

| 参数 | 作用 |
| --- | --- |
| `-p 8080` | 监听端口 |
| `-s 脚本.py` | 挂自定义脚本 |
| `--set block_global=false` | 允许非本机设备连进来（手机要走电脑的代理） |
| `--set upstream_cert=false` | 上游 HTTPS 不校验证书，避免自签证书把链路卡死 |
| `--set connection_strategy=lazy` | 延迟建连，改成动态上游时必须 |
| `-q` | 关掉默认日志，只看自己 print 的 |

## 8. 代码整合的两条链

- **旧版密码登录**：`g7timestamp` → `sign(ts)` → body 里 `mobile`/`password` 各自 RSA+hex → POST `inside.php`
- **新版短信登录**：`sign(ts)` → 发短信（method=sendVerificationCode，phone 在 query）→ 拿 `captcha` → 再算一次 `sign`（**时间戳必须换新**）→ 登录（method=loginOrRegisterByPhoneAndCode，body 带 phone/captcha）

要注意的是 **`sign` 与 `g7timestamp` 必须成对**：每次请求都重算时间戳和签名，不能拿上一次的 sign 复用。课件两条链里都是"取时间戳 → 立刻算 sign → 立刻发请求"的写法。

## 9. 坑与要点清单

1. **搜 `sign` 命中太多就换业务字段**：`g7timestamp` 这种自造名是最短的入口。
2. **key 可能不在签名类里**：本次在 `EnvUtil.m37779d().f7738j`，签名方法只是接收入参。
3. **`Uri.encode` 不能省**：Base64 的 `+ / =` 在 query 里必须转义，Python 用 `quote_plus`。
4. **路径要自己补前导斜杠**：代码是 `"\n/" + str4`，传进来的第四参不带 `/`。
5. **版本升级先重新 hook**：类名（`q.p0` → `s.q1`）和路径（`inside.php` → `auth/router`）都变，算法不变。
6. **两种 attach 报错含义不同**：找不到名字是没开 App，`ProcessNotFoundError` 是被占坑。
7. **`frida-ps -U -a` 看不到占坑进程**，必须 `adb shell` 里 `ps -A` 才看得见 `__skb_recv_...`。
8. **杀占坑进程不一定行**，课件这次就没成功；spawn 抢跑更可靠。
9. **ptrace 占坑不是 frida 特征检测**，换 hluda 无效，得换注入时机或改系统。
10. **RSA 分段长度跟着密钥长度走**：1024 位 → 117 字节/段。
11. **`c()` 是十六进制编码，不是加密**：`& 240 >> 4` 与 `& 15` 只是取高低半字节。
12. **Base64 后要去换行**：Java `encodeToString(..., 0)` 带 `\n`，不删会污染后续 hex。
13. **`referer` 是 SP 缓存值**，读不到才用默认常量，别当成动态签名去逆。
14. **代理池两个进程都要起**，只起 server 会一直拿不到代理。
15. **免费代理不稳定**，生产用要么买，要么在脚本里做失败重试。
16. **`mitmproxy` 命令在 Windows 不可用**，用 `mitmdump` / `mitmweb`。
17. **手机不装证书只能抓 HTTP**，HTTPS 需要 `mitm.it` + move cert + 重启。
18. **动态上游必须加 `connection_strategy=lazy`**，否则连接在改 `via` 之前就建好了，代理不生效。

## 10. 本案例关键知识清单

- **签名定位的两种入口**：直接搜签名类名（命中多）与搜业务自造字段（`g7timestamp`，命中唯一）。
- **HmacSHA1 + Base64 + URL 编码**的三层结构，以及"方法\n时间戳\n/路径"这种把请求元信息拼进明文的常见范式。
- **密钥藏匿位置**：签名类接收入参，真正的 key 在环境配置工具类里，hook 入参比读代码更直接。
- **RSA 分段加密的定量关系**：密文块上限 = 密钥字节数 − 填充开销（1024 位 → 117）。
- **"看起来像加密"的编码**：半字节拆分的十六进制转换常被误读成位运算加密。
- **ptrace 占坑的本质**：一个进程只能被 ptrace 一次，App 先自我附加，frida 就进不来。
- **占坑的三个解法梯度**：杀进程（可能失败）→ spawn 抢跑（低成本首选）→ 改 AOSP `ptrace.cpp`（一劳永逸）。
- **代理池的最小闭环**：抓取校验进程 + Redis 存储 + API 进程，客户端按次取用。
- **mitmproxy 的核心价值在脚本**：`request`/`response` 两个钩子把"抓包工具"变成"可编程中间人"。
- **动态上游代理的实现点**：改写 `server_conn.via`，并让连接策略延迟到改写之后。
- **业务限制的通用分析套路**：像"最多 5 台设备登录"这类限制，多半是服务端存 token 数量做的判断，不是本地校验——找限制点要在服务端状态上找，而不是在客户端代码里找。
