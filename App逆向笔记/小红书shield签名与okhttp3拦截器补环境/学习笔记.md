## 2. 定位：Java 层搜不到，就往 C 层找

### 2.1 思路

jadx 里搜 `shield` 没有有价值结果 → 猜测字符串是 so 生成的 → **验证方法：hook `NewStringUTF`**。

`NewStringUTF` 是 C 层把字节/字符数组变成 jstring 回给 Java 的必经出口，凡是 so 造出来的字符串都会从这里过一道。所以它是「C 造的字符串」的通用探针。

### 2.2 探针脚本的写法（固定套路，值得背下来）

```js
// 1 枚举 libart.so 符号找 NewStringUTF（排除 CheckJNI 版本）
var symbols = Module.enumerateSymbolsSync("libart.so");
for (var i = 0; i < symbols.length; i++) {
    if (symbols[i].name.indexOf("NewStringUTF") >= 0 && symbols[i].name.indexOf("CheckJNI") < 0) {
        addrNewStringUTF = symbols[i].address; break;
    }
}
// 2 hook 它，按特征前缀过滤，避免刷屏
Interceptor.attach(addrNewStringUTF, {
    onEnter: function (args) {
        var s = args[1].readCString();      // 第 2 个参数才是 C 字符串
        if (s && s.indexOf("XYAAAAAQAAAAEAAAB") != -1) {
            console.log(s);
            // 3 打 native 调用栈 → 定位 so 与偏移
            console.log(Thread.backtrace(this.context, Backtracer.ACCURATE).map(DebugSymbol.fromAddress).join('\n'));
            // 4 打 Java 调用栈 → 定位是哪一层 Java 调的
            console.log(Java.use("android.util.Log").getStackTraceString(Java.use("java.lang.Throwable").$new()));
        }
    }
});
```

### 2.3 探针给出的三个结论

| 输出 | 得到的信息 |
| --- | --- |
| 字符串形如 `XYAAAAAQAAAAEAAABTAAAAUz...` | 这就是 shield，且它从头到尾都是一个固定前缀 + Base64 样式主体 |
| `0xb65149b7 libshield.so!0x109b7` | 生成它的 so 是 **libshield.so**，偏移 `0x109b7` |
| Java 栈顶 `com.xingin.shield.http.XhsHttpInterceptor.intercept(Native Method)` | 调用方是 `XhsHttpInterceptor.intercept`，而且是 **native 方法** |

所以整条链是：`native intercept(Chain, long)` → so 里算 shield → 回 Java 用 `Builder.header("shield", ...)` 塞进请求头。

### 2.4 探针的通用价值

- 任何「Java 里搜不到、怀疑在 so 里拼字符串」的场景，都可以先挂 `NewStringUTF` 看前缀特征，一次就能锁定 so + 调用点。
- 前缀 `XYAAAAAQAAAAEAAAB` 是拿来做过滤条件的，比「打印所有字符串」可靠得多。

## 3. okhttp3 拦截器为什么是破点

### 3.1 拦截器模型回顾

```java
new OkHttpClient.Builder().addInterceptor(i1).addInterceptor(i2).build();  // 链式
// 每个拦截器的 intercept 里：
Request req = chain.request().newBuilder().header("sign", "xxx").build();
Response resp = chain.proceed(req);   // 交给下一个拦截器
```

拦截器是「洋葱」：每个 intercept 都能改请求头，然后 `proceed` 把控制权交给下一层。所以只要找到源头那一层，就知道谁加了字段。

### 3.2 Request 对象的结构（补环境的地图）

`Request` 是 `final class`，字段 `url / method / headers / body / tags`，只能通过内部类 `Builder` 造出来：

- 用法一：`new Request(builder)`；
- 用法二：`new Request.Builder().url(...).addHeader(k,v).build()`（实际开发用法）；
- 读数据：`request.method()`、`request.url()`（HttpUrl）、`request.headers()`（Headers）、`request.body()`（RequestBody）。

### 3.3 从源码反推出的补环境重点

C 层要往请求头加 shield，只能在 so 里回调 Java：

```java
chain.request().newBuilder().header("shield", 加密串).build();
```

关键细节（课件强调）：**要补的是 `header`，不是 `addHeader`**。`addHeader` 在 okhttp 内部最终会走到 `header` 的同一条路，so 里到底调哪个要看实际报错，但真正承载「加字段」动作的是 `header(String,String)`/`headers`。这是读 okhttp 源码得到的，不是猜的。

## 4. 验证：hook 前后对比请求头

### 4.1 证明 shield 是 intercept 里加进去的

```js
XhsHttpInterceptor.intercept.overload('okhttp3.Interceptor$Chain', 'long').implementation = function (chain, j2) {
    var request = chain.request();
    console.log(request.url().toString());
    console.log(request.headers().toString());      // 执行前：没有 shield
    var body = request.body();
    if (body) { var b = Buffer.$new(); body.writeTo(b); console.log(b.readString(Charset.forName("utf8"))); }
    return this.intercept(chain, j2);
};
```

执行前打印出的头只有 `X-B3-TraceId`、`xy-common-params`、`User-Agent`，执行完这层拦截器后多出 `shield` 和 `xy-platform-info` —— 结论成立。

### 4.2 「下一层」怎么看：洋葱模型的坑

`chain.proceed(request)` 内部就是在跑下一个拦截器，所以**在 intercept 返回之后看 response 没有意义**（那是整条链跑完的结果，看不到当前这一层的中间态）。正确做法是：

1. hook `OkHttpClient$Builder.addInterceptor` 把所有拦截器打出来（`JSON.stringify(inter)` 能看到 `$className`）；
2. 在列表里找到 `com.xingin.shield.http.XhsHttpInterceptor`，它的**下一项**就是目标；
3. 本例下一项是 `p.d0.v1.e0.n0.h`，hook 它的 `intercept(Chain)` 就能看到已经带上 shield 的请求。

课程里打印出的拦截器顺序（节选，注意同一 App 会注册多套 client，所以会出现重复项）：

```
... p.d0.g1.j.a
    com.xingin.shield.http.XhsHttpInterceptor     ← 当前层
    p.d0.v1.e0.n0.h                               ← 下一层（能看见 shield）
    ...
```

这是排查「某字段到底哪一层加的」的通用方法：**不靠猜，靠打出整条链再 hook 相邻节点做前后对比**。

## 5. 类结构：三个 native 方法是链式的

```java
public class XhsHttpInterceptor implements Interceptor {
    public long cPtr;
    static { initializeNative(); }                        // 比构造方法更早执行
    public static native void initializeNative();

    public XhsHttpInterceptor(String str, a<Request> aVar) {
        this.cPtr = initialize(str);                      // 构造时拿到句柄
    }
    public native long initialize(String str);

    public native Response intercept(Interceptor.Chain chain, long j2);   // 用句柄干活
}
```

执行顺序（照 Java 的真实生命周期）：

1. `initializeNative()` —— 静态块，类加载时跑；
2. `initialize("main")` —— 构造方法里跑，返回 `cPtr`；
3. `intercept(chain, cPtr)` —— 真正生成 shield 的地方。

课件给了一条很实用的判断原则：**先只跑 intercept，看结果能不能用；能用就不用管前两步，不能用再倒回来补前两步。**本例必须从第一步跑起 —— so 在 `initializeNative` 里做初始化，跳过会缺上下文。

## 6. 第一步：initializeNative

```java
DvmClass cls = vm.resolveClass("com/xingin/shield/http/XhsHttpInterceptor");
cls.callStaticJniMethodObject(emulator, "initializeNative()V");
```

这一步报了 4 个环境缺失，全是「so 要读 Java 侧的静态字段/工具方法」：

| 签名 | 补法 | 说明 |
| --- | --- | --- |
| `java/nio/charset/Charset->defaultCharset()Ljava/nio/charset/Charset;` | `ProxyDvmObject.createObject(vm, Charset.defaultCharset())` | 纯 JDK，直接补 |
| `com/xingin/shield/http/ContextHolder->sDeviceId:Ljava/lang/String;` | 返回 `"c90832a6-bfb9-3e46-a3dd-f5a939a4bdd2"` | 静态字段，值靠 hook 拿 |
| `com/xingin/shield/http/ContextHolder->sAppId:I` | 返回 `-319115519` | 同上 |
| `com/xingin/shield/http/ContextHolder->sExperiment:Z` | 返回 `true` | 同上 |

三类静态字段要重写不同的方法（这是新知识点）：

| 字段类型 | 重写 |
| --- | --- |
| 对象/字符串 | `getStaticObjectField(BaseVM, DvmClass, String signature)` |
| int | `getStaticIntField(...)` |
| boolean | `getStaticBooleanField(...)` |

取值的办法就是 hook 一发：

```js
var ContextHolder = Java.use('com.xingin.shield.http.ContextHolder');
console.log(ContextHolder.sAppId.value, ContextHolder.sDeviceId.value, ContextHolder.sExperiment.value);
```

### 6.1 sDeviceId 到底是什么（课件额外追踪的结论）

反编译找到赋值点 `ContextHolder.a(context, str, i2, z2, aVar)`，再往上追设备号的生成逻辑，落到：

- 先读 `pre_device.xml` 的 `device_id`；
- 读不到就用系统信息算 UUID，仍失败则 `UUID.randomUUID()`；
- 结果回写 xml。

也就是说它**就是设备唯一号**，不是某种加密结果，所以这里写死一个合法 UUID 完全够用 —— 前提是请求时用的 `xy-common-params` 里的 `deviceId` 与它一致，否则服务端能对出矛盾。

## 7. 第二步：initialize

```java
long cPtr = cls.callStaticJniMethodLong(emulator, "initialize(Ljava/lang/String;)J",
                                        new StringObject(vm, "main"));
```

### 7.1 参数怎么来的：hook 不到就延迟 hook

参数是一个字符串，但普通的「attach 进程后立刻 hook」拿不到——**手点得快，so 可能还没加载**。解法是等 so 加载完再挂 hook：

```js
function do_hook() {
    setTimeout(function () {
        Java.perform(function () {
            var I = Java.use('com.xingin.shield.http.XhsHttpInterceptor');
            I.initialize.implementation = function (str) { console.log("str=", str); return this.initialize(str); };
        });
    }, 10);          // 延迟一点点，等类/so 就绪
}
// hook dlopen / android_dlopen_ext，看到 libshield.so 加载完成后再 do_hook()
Interceptor.attach(Module.findExportByName(null, "dlopen"), {
    onEnter: function (a) { this.path = ptr(a[0]).readCString(); },
    onLeave: function (r) { if (this.path.indexOf("libshield.so") !== -1) do_hook(); }
});
```

结果：`str = main`，多次 hook 都一样 → 直接写死 `"main"`。

「加载完成后再 hook」这个模式在别的 App 上也通用：把 `libshield.so` 换成目标 so 名即可。

### 7.2 补环境三项

| 签名 | 补法 |
| --- | --- |
| `android/content/Context->getSharedPreferences(Ljava/lang/String;I)Landroid/content/SharedPreferences;` | 打印第 1 个参数得到 xml 名（`s.xml`），返回 `vm.resolveClass("android/content/SharedPreferences").newObject(null)` 空壳 |
| `android/content/SharedPreferences->getString(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;` | 按 key 分支返回：`main` 就给默认值，`main_hmac` 就给真值 |
| `com/xingin/shield/http/Base64Helper->decode(Ljava/lang/String;)[B` | `new ByteArray(vm, Base64.decodeBase64(input))` |

要点：

- SharedPreferences 的「真值」是从真机上扒的：`/data/data/com.xingin.xhs/shared_prefs/s.xml`，读到 `main` 和 `main_hmac` 两条再补进来。这是「先 hook 找 key，再取真实存储值」的套路。
- 小红书自己写的 `Base64Helper.decode` 看着像魔改，课件通过反编译读码 + hook 比对确认它就是标准 Base64 —— 这类「自己封装的编解码」一定要先确认有没有改表，凭名字假设会白跑一天。
- 注意这一层里 `getSharedPreferences` 只给空壳、却要能 `getString`，所以空壳对象的方法都要在 `callObjectMethodV` 里自己接管。

## 8. 第三步：intercept（补环境重头戏）

```java
cls.callStaticJniMethodLong(emulator,
    "intercept(Lokhttp3/Interceptor$Chain;J)Lokhttp3/Response;",
    vm.resolveClass("okhttp3/Interceptor$Chain").newObject(null),   // 空壳 Chain
    cPtr);                                                          // 上一步的句柄
```

返回值是 `Response`，但课件用的是 `callStaticJniMethodLong` 且不取返回值 —— **结果是从补环境的 `header` 里打印出来的**，这是本案最省事的取结果方式（比构造 Response 再解析简单得多）。

### 8.1 关键准备：引入 okhttp 当「夹具」

so 会一路回调 okhttp3 的 `Request/HttpUrl/Headers/RequestBody`，unidbg 里没有这些实现，所以要自己 new 一个真的。做法是 maven 引 okhttp（课件用 **3.4.2**），在 `main` 里按命令行参数拼一个 `Request` 存成静态字段，补环境里直接把这个对象喂回给 C。

```xml
<dependency>
  <groupId>com.squareup.okhttp3</groupId>
  <artifactId>okhttp</artifactId>
  <version>3.4.2</version>
</dependency>
```

这一步的思路值得记住：**当 so 需要一个复杂的框架对象时，与其一个个伪造方法，不如用真实库 new 一个真对象，再把它包成 DvmObject 交出去。**

### 8.2 补环境 19 项清单

| # | 签名 | 补法 | 重写点 |
| --- | --- | --- | --- |
| 1 | `okhttp3/Interceptor$Chain->request()Lokhttp3/Request;` | 返回全局 `request` 包成的对象 | callObjectMethodV |
| 2 | `okhttp3/Request->url()Lokhttp3/HttpUrl;` | `request.url()` | callObjectMethodV |
| 3 | `okhttp3/HttpUrl->encodedPath()Ljava/lang/String;` | `httpUrl.encodedPath()` | callObjectMethodV |
| 4 | `okhttp3/HttpUrl->encodedQuery()Ljava/lang/String;` | `encodedQuery()`，为 null 时返回 `""` 而不是 null | callObjectMethodV |
| 5 | `okhttp3/Request->body()Lokhttp3/RequestBody;` | `request.body()`（GET 为 null 也要返回对象） | callObjectMethodV |
| 6 | `okhttp3/Request->headers()Lokhttp3/Headers;` | `request.headers()` | callObjectMethodV |
| 7 | `okio/Buffer-><init>()V` | `dvmClass.newObject(new Buffer())` | **newObjectV** |
| 8 | `okio/Buffer->writeString(Ljava/lang/String;Ljava/nio/charset/Charset;)Lokio/Buffer;` | 调真实 `writeString`，返回 dvmObject 自身 | callObjectMethodV |
| 9 | `okhttp3/Headers->size()I` | `headers.size()` | **callIntMethodV** |
| 10 | `okhttp3/Headers->name(I)Ljava/lang/String;` | `headers.name(vaList.getIntArg(0))` | callObjectMethodV |
| 11 | `okhttp3/Headers->value(I)Ljava/lang/String;` | `headers.value(vaList.getIntArg(0))` | callObjectMethodV |
| 12 | `okhttp3/RequestBody->writeTo(Lokio/BufferedSink;)V` | 调真实 `writeTo`，抓 IOException | **callVoidMethodV** |
| 13 | `okio/Buffer->clone()Lokio/Buffer;` | `buffer.clone()` | callObjectMethodV |
| 14 | `okio/Buffer->read([B)I` | `buffer.read((byte[]) vaList.getObjectArg(0).getValue())` | **callIntMethodV** |
| 15 | `okhttp3/Request->newBuilder()Lokhttp3/Request$Builder;` | `request.newBuilder()` | callObjectMethodV |
| 16 | `okhttp3/Request$Builder->header(Ljava/lang/String;Ljava/lang/String;)Lokhttp3/Request$Builder;` | 调真 `header`，**key == "shield" 时打印 value** | callObjectMethodV |
| 17 | `okhttp3/Request$Builder->build()Lokhttp3/Request;` | `builder.build()` | callObjectMethodV |
| 18 | `okhttp3/Interceptor$Chain->proceed(Lokhttp3/Request;)Lokhttp3/Response;` | 返回 `newObject(null)` 假 Response（后面没人用） | callObjectMethodV |
| 19 | `okhttp3/Response->code()I` | 返回 `200` | callIntMethodV |

### 8.3 三项技巧

1. **结果出口就在第 16 项**：`header` 里判断 key 是不是 `"shield"`，是就把 value 打出来，前缀 `shield=`。之后再在 Python 里 `lstrip("shield=")` 去掉。比构造 Response 简单一个量级。
2. **假对象要「够用就行」**：`proceed` 给空壳 Response、`code()` 给 200，因为 so 拿到 Response 后只读个状态码，从不再往下用。判断标准是「so 后面还读不读它」。
3. **别漏 `newObjectV` / `callIntMethodV` / `callVoidMethodV`**：第 7、9/14/19、12 项分别属于这三个重写点，全都塞进 `callObjectMethodV` 是无效的（签名对不上，永远进不去）。

## 9. 重写点速查表（本案实证）

| 签名特征 | 重写哪个方法 |
| --- | --- |
| `xxx->方法(args)L对象;`（实例） | `callObjectMethodV` |
| `xxx->静态方法(args)L对象;`（静态） | `callStaticObjectMethodV` |
| `xxx->方法()I` | `callIntMethodV` |
| `xxx->方法()Z` | `callBooleanMethodV`（或用 `callBooleanMethod`） |
| `xxx->方法(args)V` | `callVoidMethodV` |
| `xxx-><init>()` | `newObjectV` |
| `类->静态字段:类型` | `getStaticObjectField` / `getStaticIntField` / `getStaticBooleanField` |

## 10. 参数化与打包

`main` 收 4 个参数：`method`、`url`、`common_params`、`body`。按 method 分支构造 `Request`：

- `post`：`RequestBody.create(MediaType.parse("text/plan;charset=utf-8"), body)` + `.method("post", body)` + `content-type: application/x-www-form-urlencoded` 头；
- 其它（get）：只加 `xy-common-params`，body 传字符串 `"null"` 占位。

然后 `initializeNative()` → `initialize("main")` → `intercept(cPtr)`。

终端调用（**每个参数都用双引号包住**，因为 URL 和 common_params 里全是 `&`）：

```
java -jar unidbg-0.9.7.jar get "https://...check_code?zone=86&phone=xxx&code=xxx" "fid=...&device_fingerprint=...&t=..." "null"
```

Python 端：

```python
cmd = f'java -jar  unidbg-0.9.7.jar  {method} "{url}" "{common_params}" "{body}"'
out = subprocess.check_output(cmd, shell=True, cwd="unidbg_0_9_7_jar")
shield = out.strip().decode("utf-8").split("\n")[-1].lstrip("shield=")
```

两个注意点：

- `split("\n")[-1]` 仍然必要，前面的日志一律丢掉；
- `lstrip("shield=")` 是**按字符集合**剥离，不是按前缀。shield 以 `X` 开头刚好躲过，但这个写法本身有风险，严格应写 `removeprefix` 或 `[7:]`。课件原样用了它，属于「能跑但脆」的写法。

## 11. 联调接口与风控表现

| 接口 | 说明 |
| --- | --- |
| `GET /api/sns/v1/system_service/vfc_code` | 发短信验证码 |
| `GET /api/sns/v1/system_service/check_code` | 校验验证码（参数最少，最适合调试 shield） |
| `POST /api/sns/v4/user/login/password` | 密码登录 |
| `GET /api/sns/v1/note/feed` | 拉评论/笔记 |

请求头三件套必须齐：`xy-common-params`（原样抓包值）、`xy-platform-info`（`platform=android&build=xxx&deviceId=xxx`）、`shield`（unidbg 算出来的）。

风控相关（课件记录的现象，供了解边界，不做绕过研究）：

- 密码登录会弹**滑动验证**，需要手动过；
- 拉评论等高频行为会被判定异常，出现**强制下线**；
- 结论：shield 只是「请求合法性」的第一道门，账号维度的行为风控是另一层，签名通了不等于能随便刷。

## 12. 坑清单

1. **只跑 intercept 不看前两步**：so 在 `initializeNative` 里做初始化，`initialize` 给出 cPtr，直接跳最后一步会缺上下文或崩溃。
2. **普通 hook 拿不到参数**：so 未加载时挂 hook 拿不到 `initialize` 的入参，必须用「等 dlopen 完成的延迟 hook」。
3. **静态字段补错方法名**：`sDeviceId`（String）、`sAppId`（int）、`sExperiment`（boolean）分属三个 override，写错永远进不去分支。
4. **漏 `newObjectV`**：`okio/Buffer-><init>` 必须走 `newObjectV`，塞进 `callObjectMethodV` 无效。
5. **补 `addHeader` 而不是 `header`**：so 里实际走 `Builder.header`，从 okhttp 源码能确认，先读源码再补环境比盲试快。
6. **`proceed` 返回 null**：`chain.proceed` 补成返回 null，so 后面读 `code()` 会崩；给空壳 Response + `code()=200` 才稳。
7. **`encodedQuery()` 返回 null**：GET 无 query 时 so 可能直接拼接，返回 `""` 比 null 安全。
8. **deviceId 前后不一致**：补的 `sDeviceId` 必须与 `xy-common-params` 里的 `deviceId` 相同，否则服务端对不上。
9. **Base64 是否被魔改没确认**：`Base64Helper.decode` 名字像改过，实际是标准 Base64；不确认就自己实现会算错。
10. **`lstrip("shield=")` 的语义陷阱**：按字符集剥离，不是去前缀。
11. **把 response 当中间态**：拦截器是洋葱，`proceed` 之后拿到的是整条链的结果，想看下一层必须 hook 下一层。
12. **风控当成 bug**：签名对了照样可能 4xx/被踢下线，那是账号风控，不是 shield 算错。

## 13. 关键知识清单

- 定位「Java 搜不到的字符串」：hook `Module.enumerateSymbolsSync("libart.so")` 里的 `NewStringUTF`（排除 CheckJNI），按特征前缀过滤，同时打 native backtrace（得 so + 偏移）和 Java 栈（得调用类）。
- 小红书 shield 链路：`XhsHttpInterceptor.intercept(Chain, long)`（native，so = `libshield.so`）→ 内部算 shield → 回调 `Builder.header("shield", 值)`；同时加 `xy-platform-info`。
- 类结构决定执行顺序：`static{initializeNative()}` → 构造里 `initialize(str)` 拿 cPtr → `intercept(chain, cPtr)`；先只跑最后一步，不通再补前两步。
- 静态字段补环境要分类型：`getStaticObjectField` / `getStaticIntField` / `getStaticBooleanField`；值用 frida 读 `ContextHolder.sXxx.value` 拿。
- `sDeviceId` 本质是设备 UUID（读 `pre_device.xml` 的 `device_id`，没有就 UUID 生成后回写），写死合法 UUID 即可，但必须与 `xy-common-params` 的 deviceId 一致。
- 延迟 hook 通用范式：hook `dlopen`/`android_dlopen_ext` → 判断 so 名 → `setTimeout` 后再 `Java.perform` 挂 `implementation`。
- SharedPreferences 补法：`getSharedPreferences` 给空壳，`getString` 按 key 给值，真值从真机 `/data/data/<包名>/shared_prefs/*.xml` 扒。
- okhttp3 全家桶补环境 19 项，核心是用 maven 引入真实 okhttp（3.4.2）new 一个 Request 当夹具，而不是逐个伪造方法。
- shield 结果的出口：`Request$Builder->header` 里判断 key 为 `"shield"` 时打印，Python 端取 stdout 最后一行再去前缀。
- 拦截器洋葱模型：某字段哪一层加的，靠「打印全部拦截器列表（hook `OkHttpClient$Builder.addInterceptor`） + hook 相邻节点的 intercept」做前后对比。
- 重写点按签名后缀选：`L对象;` → callObjectMethodV，`I` → callIntMethodV，`V` → callVoidMethodV，`<init>` → newObjectV，静态 → callStaticObjectMethodV。
- 打包与 Python：`main(String[] args)` 收 method/url/common_params/body 四个字符串，`&` 和空格靠双引号，Python `check_output` + `split("\n")[-1]`。
- 边界认知：shield 只解决请求合法性，账号行为风控（滑动验证、强制下线）是另一层。
