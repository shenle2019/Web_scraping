## 一、这个案例在知识线上的位置

前面几天都是在"接口能正常抓、正常发"的前提下解决加密与签名。day15 第一次把三道**访问关卡**摆在取数之前：

1. App 强制更新，老版本进不去；
2. Frida 一挂就闪退；
3. 挂上代理，Charles 里只剩图片。

这三关不过，后面反编译、Hook、还原算法都无从谈起。课件把它们串成一条完整链路：**先让老版本能跑 → 再让 Frida 能挂 → 再让包能抓 → 最后才谈接口**。第四道关才是加密，而这关的最优解不是硬破，而是找一个"服务端接受明文"的口子。

## 二、目标与版本选择

目标是识货 App 的**商品搜索 → 商品详情**。课件给了三个安装包，能力完全不同：

| 版本 | 更新行为 | 搜索接口 | 详情接口 |
| --- | --- | --- | --- |
| 7.20.1 | 强制更新，弹窗关不掉，需绕过 | 老接口，明文、无需请求头，可直接搬 | 老接口，明文进明文出，但要带一堆头，用一会儿弹图片验证码 |
| 7.53.0 | 弹窗可关闭 | — | — |
| 7.73.0 | 无需更新 | 走网关 + 风控头，较难 | `public/detail`，只要 `goods_id`，无验证码 |

课件最后的结论是**混用**：搜索走 7.20.1 的老接口，详情走 7.73.0 的新接口。这不是设计，是漏洞——新旧两代接口同时在线，各自的校验强度不同，拼起来就绕过了各自的短板。

选版本的通用判断：老版本接口简单好破，但会被加验证码、被弃用；新版本接口有网关与风控头。遇到两难，先看目标接口在新老版本上是否都还活着，再决定混用。

## 三、第一关：绕过强制更新

### 3.1 两种更新，两种态度

- **选择更新**：弹窗有取消按钮，点掉继续抓包即可，接口均可用。
- **强制更新**：必须升级，否则用不了。绕过之后必须验证接口是否还活着——能返回数据说明老接口没下线，才值得继续；返回错误就得换版本。

### 3.2 车智赢：断网法

版本校验代码挂在启动流程里，App 一启动就请求服务端最新版本号并与本地比对，差距过大则强制更新。做法是：断网 → 进 App → 联网，校验请求失败、代码不执行，弹窗不再出现。这招依赖"校验只在启动时跑一次"。

### 3.3 识货：断网无效，改 Hook 弹窗

识货一联网就重新执行版本校验，断网法失效。改从反编译入手：jadx 里搜「新版本」定位弹窗调用，命中 `com.azhon.appupdate.dialog.UpdateDialog`——第三方升级库 AppUpdate 的对话框类。Hook 它的 `show` 方法，函数体留空（不调原方法），弹窗就弹不出来。

这里有个必须讲清的细节：**attach 来不及，必须 spawn**。

- `attach` 是进程起来之后再挂，此时弹窗已经渲染，钩子挂上也没用；
- `spawn` 是进程刚创建、主逻辑还没跑就停住，先注入脚本再 `resume`，弹窗代码执行时钩子已就位。

代价是首次安装的 App 有隐私协议弹窗，如果 Hook 脚本在 App 从未手动跑过的情况下直接 spawn，界面会卡死进不去。所以顺序是：先手动启动一次、同意协议，再上 spawn 脚本。

## 四、第二关：Frida 反调试

### 4.1 现象与三类对抗

现象很好认：不挂 Hook，App 正常；一挂脚本，App 立刻闪退。这是加固方检测到 Frida 后主动终止进程。课件列了三条路线：

1. **删 so**：安全团队写了一个与业务无关的 so，专职检测 Hook，命中就杀进程；把 so 删掉即可。本课走这条。
2. **ptrace 占坑**：反过来先占住调试接口，让 Frida 挂不上。
3. **Frida 加强版 server**：改特征、改端口、改名，绕开静态特征检测。

### 4.2 通用定位法：Hook dlopen

不知道该删哪个 so，就用一个对所有 App 都通用的小脚本：Hook 底层 `dlopen` 与 `android_dlopen_ext` 两个导出函数，`onEnter` 里读第一个参数的 C 字符串，把 App 运行过程中加载的 so 路径依次打印出来。

判断依据是**时序**：so 是懒加载的，打印到某个 so 之后进程立刻退出，那它就是检测点。识货命中的是 `libmsaoaidsec.so`（移动安全联盟 OAID 相关的安全库，与商品业务无关）。这也解释了为什么可以删——它只做检测，删掉不影响功能。

定位方法的边界：只对"独立检测 so"这一类有效，检测逻辑写进业务 so 或 Java 层时，删 so 就无从下手。

### 4.3 删 so 的操作

so 在设备上的路径随每次安装变化，不能照抄课件的路径，要从打印结果里取：

`/data/app/~~<随机串>==/com.hupu.shihuo-<随机串>==/lib/arm64/libmsaoaidsec.so`

进 `adb shell` → `su` → `cd` 到该 `lib/arm64` 目录 → `rm -rf` 掉这个 so。删完先手动启动一次 App，能正常用就说明它确实与业务无关；然后再跑之前的绕过更新脚本，两关一起过。

## 五、第三关：代理检测

### 5.1 为什么挂了代理反而抓不到

Android 里用 OkHttp 发请求，如果在构建客户端时写了 `.proxy(Proxy.NO_PROXY)`，这个客户端就**无视系统代理**直连。Charles 靠系统代理截流量，自然一条业务包都看不到，只剩未走该客户端的图片等静态资源。

### 5.2 绕过思路：抓更底层

系统代理这一层被跳过，就下沉到 socket 层抓。手机上装一个 VPN 类工具接管全部流量，再转发给 Charles 的 SOCKS 端口。课件给了三个工具：

| 工具 | 特点 | 注意 |
| --- | --- | --- |
| SocksDroid | 本课主用，接管 socket 后转发给 Charles | 需在 Charles 里开 SOCKS 代理并记端口 |
| Drony | 可只转发指定 App 的请求 | 英文版适配模拟器与低版本安卓，繁体版给手机；加载不出 WiFi 就废了，不稳定 |
| ProxyDroid | 全局代理转发 | 用前必须删掉手机上的系统代理 |

### 5.3 配置顺序（SocksDroid）

1. 手机装 SocksDroid（`adb install`）；
2. Charles 开 SOCKS 代理，记下端口；
3. SocksDroid 里填电脑 IP 与那个 SOCKS 端口，启动；
4. **手机端把系统代理删掉**——留着会和 SocksDroid 抢流量，两边都抓不全。

这一步的隐含前提是证书信任仍然有效，抓的是 HTTPS 明文；SocksDroid 只解决"流量绕开系统代理"，不解决证书。

## 六、抓包结论：搜索与详情两代接口

### 6.1 搜索

**老接口**：`POST https://sh-api.shihuo.cn/daga/search/goods/v1`

| 位置 | 内容 |
| --- | --- |
| query | `minVersion=15670`、`clientCode={holder}`、`v=7.20.1`、`channel=myapp`、`device=Pixel 2 XL`、`platform=android`、`timestamp` |
| body | `{"keywords":"...","page":"1","pageSize":"20"}` |
| 请求头 | 只有 `user-agent` 有意义，其余可删 |

UA 里带了一段 `sh-dv-sign[v1|10418e17...]`，看着像签名，实测写死即可通过，不必还原——这是"看似要破、实则不必破"的典型。课件判断：这个接口改包即可直接请求，不需要逆向。

**新接口**：`POST https://sh-gateway.shihuo.cn/v3/sh-api/daga/search/goods/v1`

多了一层网关，且必须带全套请求头：`sh-token`、`sh-id`、`sh-sign`、`sk`、`sh_session`、`shreqid`、`abtest-control`、`osv`、`network`、`appid`、`cookie` 等。不带头的返回是：

```json
{"status":457,"msg":"请检查是否使用了代理或VPN哦"}
```

这句很关键：**服务端也在做代理检测**。抓包旁路只能让包出来，服务端认不认是另一回事；这里靠把风控头原样带上来过。课件把这些头全部写死，没有去还原 `sh-sign`。

### 6.2 详情

老版本有两个详情接口，不同商品走不同入口，但都能用：

- `GET /v4/services/sh-goodsapi/app_swoole_zone/commonDetail/v1`
- `GET /v4/services/sh-goodsapi/app_swoole_shoe/preload/single`

参数只有 `goods_id` 与 `v`，但必须带与搜索同一套风控头。

这里有个反直觉的发现：这两个接口在抓包里请求体、响应体都是 Base64 形态的密文，但**明文进就明文出，密文进才密文出**。服务端不强制加密，加密只是客户端自作主张。课件因此不去破 so 里的算法，直接发明文。

代价是风控：连续访问会弹图片验证码，反复不输入会封掉这台设备，接口在手机上也一起失效。所以老详情只适合验证，不适合量产。

新版本详情绕开了这一切：`GET /v4/services/sh-goodsapi/public/detail`，只要 `goods_id` 与 `v=7.73.0`，明文、无验证码、无需请求头（课件整合脚本里连 headers 都没传）。

## 七、Hook 找加密：一条从猜想到证伪的路径

课件在写最终方案前，先把"找加密点"的完整思路走了一遍，四个脚本依次否掉三个假设。这段比结论更值得记。

### 7.1 假设一：Map 里塞密文

最常见的写法是 `map.put("data", 加密(明文))`，所以 Hook `java.util.TreeMap.put`，只在 key 为 `"data"` 时打印。识货没走这条路，无输出。顺带一提，`sh-id` 这类头也可能是 map.put 塞进去的，可以顺手一起打。

### 7.2 假设二：StringBuilder 拼串

换 `java.lang.StringBuilder.toString`，把拼好的整串打出来，与抓包比对，一样就说明走了拼接。结果打印量巨大、没对上。实操中还踩了个坑：`frida -UF ... -o string.txt` 没有落下任何内容，输出文件是空的——`console.log` 在带 `-o` 的场景下不保证落盘，需要改用 `send`。这跟参数化脚本里用 `on_message` 收消息是两条不同的路。

### 7.3 假设三：Base64 编码

Hook `android.util.Base64.encodeToString` 的 `('[B','int')` 重载，能打出"加密了-->密文"。这一枪打中了，但只证明 App 调用了 Base64，无法定位到**是哪段业务代码**调的，等于拿到线索没拿到位置。

### 7.4 换思路：先列出所有拦截器

既然请求体是被统一处理的，那就该在 OkHttp 这一层找。Hook `okhttp3.OkHttpClient$Builder.addInterceptor`，把每个传进去的拦截器对象打出来，得到一份清单：

- `com.shizhi.shihuoapp.library.imageview.loader.c.b$a`（图片加载）
- `com.shizhi.shihuoapp.library.net.h.a` / `.b` / `.d` / `.g` / `.h`（网络层若干）
- `cn.shihuo.modulelib.utils.f1.a$a`（模块库工具类，匿名内部类）
- `cn.shihuo.modulelib.startup.core.c.a` / `.b`（启动模块）

清单里同一类名反复出现，是多个 OkHttpClient 实例各挂一套，不是重复打印。

### 7.5 逐个跳过，看谁在加解密

验证手法不是读代码，而是**把某个拦截器"摘掉"再跑**。写法上以 URL 过滤（只处理详情接口），然后分两步：

1. 先保留原逻辑 `this.intercept(chain)`，确认钩子确实命中；
2. 改成 `chain.proceed(chain.request())`，即跳过这个拦截器本身、直接把请求交给后续链。

结果：跳过 `cn.shihuo.modulelib.utils.f1.a$a` 之后，请求以明文发出、服务端照常返回明文数据。**加密和解密都在这个拦截器里**，而它调的是 so，逻辑复杂到课件选择不看，留待后续 unidbg 直接跑。

这一步的副产品比主产品值钱：它证明服务端不校验密文，因此"跳过拦截器"本身就是一个可用的绕过方案，不必还原算法。

### 7.6 方法论小结

四个脚本对应四层猜想：数据结构（Map）→ 字符串处理（StringBuilder）→ 编码（Base64）→ 网络栈（Interceptor）。逐层下沉，直到能"改行为"而不只是"看到值"。判断标准始终是：**能不能让这段逻辑不执行，而请求依然成功**。

## 八、代码整合

最终方案两段：

1. **搜索**：老接口 `sh-api.shihuo.cn/daga/search/goods/v1`，一个写死的 UA + 七个 query 参数 + JSON body，取出 `goods_id`；
2. **详情**：新接口 `sh-gateway.shihuo.cn/v4/services/sh-goodsapi/public/detail`，`goods_id` + `v=7.73.0`，无头、无验证码。

配套的 `utils.py` 里只有一个通用函数 `header_str_to_dict`：把从 Charles 复制的「键 TAB 值」多行文本转成 dict，靠 `\t` 切分、掐掉首尾空行。注意两点：复制时必须是 TAB 分隔（空格会切错），文件上半段还留着别家 App 的 Header 示例与 `query_to_dict`，与本案无关。

## 九、坑与口径偏差

1. **7.20.1 现在不弹更新框了**：课件记录该版本已被官方忽略，绕过更新的脚本可能用不上；但老接口仍在，代价是几分钟一次验证码。
2. **spawn 前必须先手动跑一次 App**：隐私协议弹窗会挡住 spawn 后的界面，卡死。
3. **so 路径不可照抄**：`/data/app/~~<随机>==/` 与包名后的哈希每次安装都变，要从 dlopen 打印结果里取。
4. **删 so 后要复验**：App 能正常启动、能正常进详情，才说明这个 so 与业务无关；不能启动就换 ptrace 占坑或加强版 server。
5. **课堂笔记 6.4.2 第一个脚本有 bug**：`var res = this.intercept(chain)` 被注释掉，却仍然 `return res`，返回 `undefined` 会让链路崩掉。对照讲义版能看出来——抄脚本时要检查 return 的变量是否还在。
6. **新版本搜索的参数自相矛盾**：请求头里 `app-v` 是 7.20.1，query 里 `v` 是 7.53.0、`minVersion` 是 19612，三者不在同一版本线上。这是从抓包直接复制的结果，能通，但不能当作版本规则的证据。
7. **`457` 不是抓包失败**：`{"status":457,"msg":"请检查是否使用了代理或VPN哦"}` 是服务端风控，缺头就报这个，不要误判成证书问题。
8. **老详情会封设备**：验证码反复不输入，这台机器的接口权限会被收走，手机上也一起用不了。测一次算一次。
9. **`verify=False` 是环境产物**：关掉自签证书校验，跟业务无关，脚本能通就不用去修证书链。
10. **`console.log` 与 `-o` 落盘**：钩子打印量大时 `-o` 文件可能为空，可靠做法是 `send` + 脚本端 `on_message` 收。

## 关键知识清单

- **三关顺序**：能启动（绕更新）→ 能注入（绕 Frida 检测）→ 能抓包（绕代理检测）→ 才谈接口。
- **强制更新两种解法**：断网启动（车智赢，校验只跑一次）；Hook 弹窗（识货，联网即重校验），命中第三方库 `com.azhon.appupdate.dialog.UpdateDialog.show`。
- **spawn 与 attach 的分界**：要在目标代码执行**前**生效就用 spawn；单纯读数可以用 attach。
- **Frida 反调试三类**：删检测 so、ptrace 占坑、加强版 server。
- **定位检测 so 的通用脚本**：Hook `dlopen` / `android_dlopen_ext` 打印加载路径，闪退前最后一个即检测点；识货是 `libmsaoaidsec.so`。
- **代理检测原理**：OkHttp `Proxy.NO_PROXY` 绕开系统代理；绕过靠 VPN 类工具下沉到 socket 层（SocksDroid / Drony / ProxyDroid），且必须先删系统代理。
- **服务端也在检测**：缺风控头时返回 `status=457`，旁路抓包解决不了这一层。
- **接口混用**：老版本搜索（免头、明文）+ 新版本 `public/detail`（免头、免验证码、明文），是版本并存留下的口子。
- **加密的两个反直觉结论**：老详情明文进明文出；跳过加密拦截器后请求照样成功——服务端不强制密文。
- **找加密的四层猜想**：Map.put → StringBuilder → Base64 → OkHttp Interceptor，逐层下沉，最后用 `chain.proceed()` 摘掉拦截器来验证。
- **验证标准**：能定位不算完，能让它**不执行且请求成功**才算破。
- **Hook 脚本通用性**：拦截器 Hook、dlopen Hook、Base64 Hook 三个脚本与 App 无关，换个目标可直接复用。
