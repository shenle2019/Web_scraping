## 1. 案例全景

这个案例的难点不在签名，而在**入口**。全套接口没有 `sign`，请求头也没有特殊字段，卡人的是三个前置问题：

| 障碍 | 表现 | 本章对应 |
| --- | --- | --- |
| 短信登录要先过图形验证码 | 不识别就发不出短信 | 第 4、5 节（OCR） |
| frida 一跑 App 就退出 | 换 frida-server 才 hook 得住 | 第 7 节（hluda） |
| jadx 打开代码极少 | 反编译不出业务逻辑 | 第 8 节（脱壳） |

业务流程本身很简单：登录拿 `token` → 带 `token` 调预约接口。真正值得记的是"验证码怎么自动化"和"环境被盯着怎么办"。

## 2. 五个接口一览

全部在 `newappuser.jiuxian.com` 下，除页面地址外都是明文参数：

| 用途 | 方法 | 路径 | 关键参数 |
| --- | --- | --- | --- |
| 密码登录 | POST | `/user/loginUserNamePassWd.htm` | `userName`、`passWord`、设备参数 |
| 取图形验证码 | GET | `/messages/graphCode.htm` | `mobile`、`type=4` → 返回 base64 图片 |
| 校验图片码并发短信 | GET | `/messages/mobileCode.htm` | `code=图片码`、`type=1` |
| 短信登录 | POST | `/user/loginMobileFast.htm` | `mobile`、`verifyCode=短信码` |
| 预约 | GET | `/reservation/preReservation.htm` | `actId`、`productId`、`token`、`channel=1` |

公共参数（五个接口基本一致）：`appKey`、`deviceIdentify`、`appVersion=9.1.13`、`areaId`、`channelCode=0`、`cpsId=tencent`、`deviceType=ANDROID`、`deviceTypeExtra=0`、`equipmentType=Pixel 2 XL`、`netEnv=wifi`、`screenReslolution=1440x2712`、`supportWebp=1`、`sysVersion`、`pushToken`。

三个参数看着像签名的原料：`appKey`、`deviceIdentify`（值一模一样，形态像 UUID）、`pushToken`（一长串 base64 风味字符串）。**课件做了改包实验，三个全删，接口照常返回**——结论是它们只是埋点/设备标识，不参与校验。

这条实验的价值比结论大：遇到新接口，先删可疑参数看服务端报什么，比直接进 jadx 找签名快得多。

## 3. 密码登录

- 成功响应里 `token` 在 `result.userInfo.token`，预约接口就用它
- `appKey` 与 `deviceIdentify` 都取 `str(uuid.uuid4())`，每次运行新生成即可
- `passWord` 是**明文**提交，没有加密
- `success` 字段是字符串 `"1"` / `"0"`，不是布尔

### 3.1 token 的形态

样本 `6494ac1cd90b462fbd3c953a69a70861210440860`，看着像 40 位，实际是 **32 位 hex + uid 直接拼接**（`6494ac1cd90b462fbd3c953a69a70861` + `210440860`，同响应里 `uid` 正好是 `210440860`）。写正则或截断时按"32 位 + 数字尾巴"处理，不要当纯 UUID。

### 3.2 环境坑

- **Python 3.11.9 跑不通这套登录脚本，3.9 可以**（课堂实测：3.11.3 以下可以）。课件判断是解释器自身源码改动导致，先降版本，别在版本上死磕
- `areaId` 抓包是 `500`、代码写 `2707`，两者都能登录（地区 id 影响商品与库存，不影响登录鉴权）
- `sysVersion` 抓包 `11`、代码里写 `10`，同样能过

## 4. 短信登录流水线

四步，缺一不可：

```
1) graphCode.htm?type=4  →  result.imgCode（base64 图片）
2) base64 解码存本地     →  OCR 识别出 4 位码
3) mobileCode.htm?code=识别结果&type=1  → 服务端校验，通过才下发短信
4) loginMobileFast.htm?mobile=..&verifyCode=短信码  →  拿 token
```

三个必须记住的机制：

1. **图片码错了短信根本不会发**。第 3 步失败返回 `errCode 1200013`（验证码输入错误）或 `1200003`（验证码错误或已过期），短信通道根本没触发。所以"取图 → 识别 → 校验"要放在循环里，失败就重新取图，而不是拿同一张图反复试
2. **`type` 是两套值**：取图 `type=4`，发短信 `type=1`。抄错一个数字直接不通过
3. **同一套设备参数贯穿全程**：`appKey` / `deviceIdentify` 三个接口用同一组 uuid，中途换值相当于换了一台设备，服务端会话对不上

识别成功的响应是 `{'result': '', 'errCode': '', 'success': '1'}`，用 `success == "1"` 判断，别用真值判断。

## 5. 三种 OCR 方案对比

| 方案 | 装什么 | 能识什么 | 局限 |
| --- | --- | --- | --- |
| **ddddocr** | `pip install ddddocr` | 带干扰线的验证码，识别率高 | 模型加载慢；纯验证码场景最省事 |
| **pytesseract** | Tesseract-OCR 引擎 + `pytesseract` + `Pillow` | 印刷体文字（`lang='chi_sim+en'` 可中英混排） | 带干扰线的验证码直接废；引擎没进 PATH 就 `TesseractNotFoundError` |
| **muggle_ocr** | 源码 `setup.py install` 或 pip；依赖 `opencv-python` + `tensorflow-intel` | `ModelType.OCR` 单行文字 / `ModelType.Captcha` 4-6 位**无干扰线**验证码 | 有干扰线不行；tensorflow 依赖重、装起来费劲 |
| 收费打码 | 超级鹰 / 云打码 | 任意 | 花钱、走第三方接口 |

课件对这个 App 的结论很明确：**图片码带干扰线，走 ddddocr**；pytesseract 和 muggle_ocr 只作为"图片转文字"的能力演示（样本是 `oneline.png`、`wz.png` 这类干净图）。

muggle_ocr 的两种模型要分清：`OCR` 认单行印刷体（排版还得规整、不能有大片空白），`Captcha` 认 4-6 位验证码且对干扰线敏感——不是"装一个模块什么都能认"。

### 5.1 课堂踩到的两个问题

- 短信登录"时而可以，时而报 SSL 错误"，加了 `verify=False` 也没压住，课件选择放着不追
- 取图接口的请求头里带了 `user-agent: okhttp/3.14.9` 与 `Accept-Encoding: gzip`，是照抓包抄的；这类"看起来没用"的头在风控严的站点上有时是必需项，抄全更稳

## 6. 预约茅台

- 参数：`actId`（活动 id）、`productId`（商品 id）、`token`（登录拿）、`channel=1`，另有 `lati` / `longi` 经纬度（代码里硬编码一组上海坐标）
- 重复预约返回 `errCode 1200601`，"您已预约成功，不需重复预约"——这是幂等提示，不是失败
- 课件给的现实判断：**抢购不是手快就行**，后端有随机/风控逻辑；这套代码只做到"批量预约"，抢购代码没写（定时任务留给后面）
- 另一类玩法是"只预约、等抽奖"（i茅台、各种第三方小程序），只做预约、抽中再通知，成功率低但省事

## 7. frida 反检测与 hluda

### 7.1 检测面

课件把 frida 检测分成两代：

| 类型 | 手法 | 之前的解法 |
| --- | --- | --- |
| 加载期 | `dlopen` 时枚举 so，发现检测库就退出 | 删掉检测 so（得物/识货那种） |
| 运行期 | 找 frida 的进程名、文件名特征，命中直接杀 App | **本案例属于这类** |

酒仙 App 是第二种：frida-server 一跑，App 直接退出或 hook 不上。它的判据不是某个 so，而是"frida 运行时在系统里留下的痕迹"。

### 7.2 解法：换 frida 的实现

`strongR-frida-android`（产物叫 **hluda**）就是官方 frida 的补丁版：跟随上游一一对应版本，改动运行时的进程名/文件名特征，让基于特征检测的 App 认为"没装 frida"。

用法上就是替换 `frida-server`：

```
push 到 /data/local/tmp/ → chmod 777 → 直接执行
```

课件里的判断依据很实用：**同一条 hook 脚本，跑 frida-server 抓不到，换 hluda 就抓到了**，说明卡点在特征检测，不在脚本。

### 7.3 版本必须严格对齐

- hluda 的版本要与电脑端 `frida` python 模块**一一对应**，不一致会 attach 失败
- 课件在两处给的版本号不一致：正文写 `16.2.1`，课堂笔记写 `16.4.10`；而目录里实际附带的文件是 `hluda-server-16.2.1-android-arm64.xz`。**以手里的文件为准**，再让 pip 装同版本 frida
- 只提供 arm64 版 → 手机得是 64 位架构

另外，这套方案只对"检测 frida 特征"的 App 有效。检测端口、检测注入行为、检测内存映射的更狠方案，换名字是挡不住的。

## 8. 加壳与脱壳

### 8.1 怎么判断加了壳

`jadx` 打开酒仙 apk，业务代码少得离谱 → 基本可以断定加壳。壳的特征包常见的是腾讯、邦邦、360 这几家。

### 8.2 加壳原理

```
正常 apk：java(→dex) + so + 资源
加壳 apk：dex 被塞进 so（apk 里 dex 很小、so 很大）
运行时：壳 so 先加载 → 把 dex 从 so 里解出来 → 落到内存 → 交给 ART 执行
```

代价是启动变慢。课件的观察挺准：大厂一般不加壳（用强加密正面刚），小公司没强加密能力，就用加壳牺牲速度换安全。

### 8.3 脱壳思路与工具谱系

既然运行时内存里一定有完整的 dex，那就在它展开之后 dump 出来。方案分四类：

| 路线 | 做法 | 特点 |
| --- | --- | --- |
| 手动脱壳 | 动态调试跟踪 dex 的内存偏移，手动 dump | 难，要懂寄存器/汇编，还得对抗反调试、反读写 |
| xposed 系 | `Fdex2` hook `ClassLoader.loadClass`；`dumpDex` | 通用性好，需要 xposed 环境 |
| frida 系 | `frida-dexdump`（本课用） | 装好即用，最省事 |
| 自研脱壳机 | AOSP 刷机后定制 | 最彻底，成本最高 |
| 商业工具 | armPro 等 | 花钱 |

### 8.4 frida-dexdump 用法

1. 电脑端 `pip install frida-dexdump`
2. 手机端起 frida-server（或 hluda）+ 端口转发
3. `frida-dexdump -U -f 包名`；加 `-d` 是深度脱壳
4. 拿到的 dex 用 jadx 打开

坑：一次性把多个 dex 全拖进 jadx 会报错，原因是其中某个 dex 损坏或不属于这个 App，一个坏文件拖垮整个工程。做法是逐个拖、删掉报错的那个，剩下的都能反编译出对应片段。

## 9. 坑与要点清单

1. **先做"删参数"实验再决定要不要逆**：本案例 `appKey` / `deviceIdentify` / `pushToken` 全删也能通，省掉整条逆向链。
2. **`screenReslolution` 是服务端的拼写错误**，照抄，别"顺手纠正"成 `Resolution`。
3. **`success` 是字符串 `"1"`**，`if resp['success']` 恒为真，必须 `== "1"`。
4. **token 尾巴带 uid**，不是纯 32 位 hex，按固定长度切会切坏。
5. **图片码与短信码是两次校验**：图片码错，短信根本不会发，别在短信环节干等。
6. **验证码要循环重取**，失败就换一张图，不要拿同一张反复提交。
7. **`type` 两套值**：取图 `4`、发短信 `1`。
8. **设备参数全程同一组**：三个接口共用 `appKey` / `deviceIdentify`，中途换值等于换设备。
9. **`pytesseract` 报 `TesseractNotFoundError`** 是引擎没装或没进 PATH，不是代码错。
10. **`muggle_ocr` 不抗干扰线**，只能做干净图片的单行识别，别当通用验证码方案。
11. **Python 3.11.9 跑不通，降 3.9（或 3.11.3 以下）**，课件判断与解释器源码改动有关。
12. **短信登录偶发 SSL 错误，`verify=False` 压不住**，课件未解决，属于遗留问题。
13. **课件 `chomd 777` 是笔误**，正确是 `chmod 777`，照抄会报错。
14. **预约代码里 `deviceTypeExtra` 的值混了个制表符**（`'	0'`），肉眼看不出来，复制时注意。
15. **hluda 版本必须与 pip 的 frida 模块完全一致**，且本课只给 arm64 版。
16. **换 hluda 只解特征检测**，端口/注入行为级别的检测换名字没用。
17. **加壳 App 必须先脱壳再静态分析**，直接看 jadx 会误判"这 App 就这么点代码"。
18. **jadx 一次性拖多个 dex 报错**是坏 dex 污染工程，逐个拖、删坏的。

## 10. 本案例关键知识清单

- **无签名接口的突破口在"删参数"**：先确认哪些参数真的参与校验，再决定投入多少逆向成本。
- **短信登录是四段式**：取图 → OCR → 图片码换短信 → 短信码换 token，每段都有独立错误码。
- **图形验证码的三条技术路线**：ddddocr（抗干扰线首选）、pytesseract（印刷体文字）、muggle_ocr（干净单行/无干扰线验证码），代价与能力成反比。
- **token 的实际结构**：32 位 hex + uid 拼接，与"纯随机串"的直觉不同。
- **frida 检测的两代形态**：加载期扫 so（删 so 可解）与运行期扫进程名/文件特征（换 hluda 可解）。
- **hluda 的本质**：官方 frida 的反检测补丁版，版本与上游一一对应，必须与本地 frida 模块对齐。
- **加壳的本质**：dex 藏进 so，运行时解到内存再执行——所以内存是脱壳的取数点。
- **脱壳方案谱系**：手动 dump、xposed hook `ClassLoader.loadClass`、frida-dexdump、自研脱壳机、商业工具，按成本与通用性取舍。
- **反编译结果异常少，先怀疑加壳**，不要以为是混淆或者代码被抽走。
- **环境版本本身就是坑**：Python 解释器版本、frida 双端版本、OCR 引擎路径，任一不匹配都能让"看起来对的代码"跑不通。
