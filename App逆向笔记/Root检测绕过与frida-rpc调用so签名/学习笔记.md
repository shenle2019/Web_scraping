## 1. 案例全景

这个案例和前几个不一样：**逆向还没开始，App 就先不让进**。大姨妈做了 root 检测，检测到就直接弹窗退出，登录页都到不了。所以整节课是两层：

| 层 | 目标 | 手段 |
| --- | --- | --- |
| 前置 | 让 App 认为手机没 root | antiroot 脚本 / Shamiko 模块 / hook 检测函数 / AOSP 改 su 名 |
| 主体 | 还原登录三参数 | `device`（SHA1）、`password`（AES）、`sign`（native，走 frida-rpc） |

三个参数的难度是递进的，刚好对应三种处理策略：

- `device`：Java 层算法，纯拼接 + SHA1 → 反编译读懂后本地实现
- `password`：Java 层标准 AES → 反编译读懂后本地实现
- `sign`：native 实现（`libCrypt.so`）→ **不硬破**，交给 frida-rpc / 自建 APK / unidbg

## 2. Root 检测原理

检测逻辑很朴素：**去固定路径找一个叫 `su` 的文件，找到就算 root**。

课件列出的检测路径（不同 root 工具落点不同，面具通常落在 `/system/bin/su`）：

```
/system/bin/su          /system/xbin/su         /system/sbin/su
/data/local/bin/su      /data/local/su          /data/local/xbin/su
/sbin/su                /su/bin/su              /system/sd/xbin/su
/system/bin/failsafe/su /system/xbin/busybox    /system/xbin/daemonsu
/system/app/Superuser.apk
```

自查命令：`adb shell` → `su` → `cd /system/bin` → `ls | grep su`。

关键前提：**普通 App 有权限 stat 这些路径**（`/system/bin` 是可读目录），所以"藏文件"比"藏进程"更有效——这也是 Shamiko 这类方案能生效的原因。

大姨妈的具体实现（反编译 `MiscUtil`）：

- `isRooted()`：遍历 6 个目录拼上常量 `su`，`File.exists()` 命中后再 `ls -l` 看权限串里 `root` 出现次数，多于一次才判定为 root
- `isSimulator()`：靠 `Build.FINGERPRINT`、`Build.MODEL`、`Build.SERIAL`、`Build.MANUFACTURER`、运营商名等特征判虚拟机
- 调用处：`if (!MiscUtil.isSimulator(this) && !MiscUtil.isRooted())`，两个都为 false 才放行

顺带一条排查经验：搜索字符串建议搜**弹窗文案**（如"威胁您的"）而不是搜 `isRooted`，UI 文案的命中路径最短，能直接落到判定分支。

## 3. 四种绕过方案对比

| 方案 | 做法 | 优点 | 局限 |
| --- | --- | --- | --- |
| 一、开源 antiroot 脚本 | 用 `AshenOneYe/FridaAntiRootDetection` 的 `antiroot.js`，`frida -U -f 包名 -l hook.js` | 通用，Java/C 层都 hook，换 App 可复用 | 依赖 frida，首次要试兼容性 |
| 二、Shamiko 模块 | 刷入 `Shamiko-v0.5.2-120-release`，重启，在面具里勾"配置排除列表"，必要时再隐藏面具应用 | 不依赖 frida，最接近"真机无 root" | 需要 Magisk + Zygisk；对检测 Magisk 包名的 App 还要额外改包名 |
| 三、hook 检测函数 | 反编译定位 `isRooted`/`isSimulator`，直接 `return false` | 精准，顺带能继续做后续 hook | 换个 App 就得重找，且只能挡已知检测点 |
| 四、AOSP 刷机 | 自编译系统，把 `su` 改名（如 `su1`） | 从根上消失，可定制脱壳机 | 成本最高，课程标为后续内容 |

方案二有三个容易被忽略的细节：

1. **排除列表要配，但"强制排除"不能开**。Shamiko 的 README 写得很直接：它读的是 Magisk 的 denylist 配置，但前提是 **denylist enforcement 关闭**。开了强制排除，Shamiko 反而不工作。
2. **白名单模式**：建空文件 `/data/adb/shamiko/whitelist` 可切白名单，免重启生效，但官方明确说性能与内存开销明显，只建议测试用；且开启后只有此前已授权 root 的 App 能拿 root，要授权新 App 得先关白名单。
3. **银行类 App 还会查"装没装面具"**：光刷模块不够，还要在面具设置里把自身应用隐藏（改随机包名），让它对其它 App 不可见。课件这一段是截图走流程，要点就一个——隐藏面具应用本身。

方案三的 hook 清单（本案例实际用到的三个点）：

| 类 | 方法 | 返回值 | 作用 |
| --- | --- | --- | --- |
| `com.yoloho.libcore.util.MiscUtil` | `isRooted()` | `false` | 挡 root 判定 |
| `com.yoloho.libcore.util.MiscUtil` | `isSimulator(ctx)` | `false` | 挡模拟器判定 |
| `com.mobile.auth.gatewayauth.manager.SystemManager` | `checkEnvSafe()` | `null` | 挡阿里号码认证 SDK 的"手机不安全"提示 |

第三个点容易漏：它不是 root 检测主体，而是**第三方 SDK 自己又做了一次环境检查**，不处理会一直弹吐司干扰操作，但不一定拦你进页面。遇到"能进去但老弹提示"，就往 SDK 方向找。

课件里还有个现场备注："hook 不成功就卸载重装"。这类启动即判定的 App，首次运行的判定结果可能被缓存（SP/文件），清数据或重装能排除缓存干扰。

脚本有两种跑法，本质一样：

- 命令行：`frida -U -f com.yoloho.dayima -l root.js`（spawn 启动）或 `frida -UF -l root.js`（附着已运行进程）
- Python 驱动：`spawn` → `attach(pid)` → `create_script` → `load` → **`resume(pid)`**。`resume` 最容易漏，漏了 App 一直卡在挂起状态，看着像"hook 没生效"

端口转发用 `subprocess.run` 跑两条 `adb forward tcp:27042/27043`，把环境准备也塞进脚本，省得每次手动敲。

## 4. 登录接口与三个破点

```
POST https://uicapi.yoloho.com/user/login
query: device, ver, screen_width, screen_height, model, sdkver,
       platform, releasever, channel, latt, lngt, networkType, token, userStatus
body : username, password, sign, androidid, mac, imei, density, brand
```

请求头没有特殊签名，破点全在参数上：

- `device`（query）：设备指纹，40 位 SHA1
- `password`（body）：AES 密文 + Base64
- `sign`（body）：`device + 路径 + 手机号 + 密码密文` 的 native 摘要

## 5. `device`：五段拼接 + SHA1

### 5.1 调用链

搜索 `device` 命中太多，课件换了个入口：搜 `releasever` 或 `userStatus`，直接落到 OKHttp 拦截器里的 `addQueryParameter("device", URLEncoder.encode(PeriodAPIV2.getInstance().getDeviceCode(), "UTF-8"))`。

`getDeviceCode()` 是懒加载：字段为空就调 `setDeviceCode()`，算完缓存。真正的算法就在 `setDeviceCode()`：

```
str  = TelephonyManager.getDeviceId()            // IMEI，新系统常为 null
str3 = Settings.Secure "android_id"
str2 = Build.BOARD + BRAND + CPU_ABI + DEVICE + DISPLAY + HOST
     + ID + MANUFACTURER + MODEL + PRODUCT + TAGS + TYPE + USER
str4 = DayimaUtil.getPhoneMac()                  // WiFi MAC
str5 = BluetoothAdapter.getDefaultAdapter().getAddress()

device = hex_lower( sha1( str + str3 + str2 + str4 + str5 ) )
```

拼接顺序是 `str + str3 + str2 + str4 + str5`，注意 `str2`（Build 串）在 `str3` 之后，容易看反。

### 5.2 hook 定位：用 flag 门控 MessageDigest

直接 hook `MessageDigest.update` 会被全 App 的摘要调用淹没。课件的做法是**两个 hook 配合**：

- `PeriodAPIV2.setDeviceCode` 进入时把 `flag = true`
- `MessageDigest.update([B)` 只在 `flag` 为真时打印

这样一次只输出 `setDeviceCode` 内部那次 update，即拼好的完整串。同一手法在"方法内部调用了通用加密 API"的场景通用：**用外层业务方法打标记，内层通用 API 只在标记内输出**。

实测拿到的拼接内容（分 5 段更容易对账）：

| 段 | 实测值 | 说明 |
| --- | --- | --- |
| `str` | `null` | IMEI 拿不到，拼的是**字符串 "null"**，不是空串 |
| `str3` | `a8da7415550cd43a` | android_id，可随机 |
| `str2` | `taimengooglearm64-v8ataimenRP1A.201005.004.A1abfarm-01392…android-build` | Build 13 个字段连写 |
| `str4` | `C6:07:96:ED:C1:32` | WiFi MAC，大写冒号分隔 |
| `str5` | `02:00:00:00:00:00` | 蓝牙 MAC，未开启时是这个默认值 |

### 5.3 实现注意

Java 侧是逐字节 `Integer.toHexString(b & 255)` 再补零，等价于 Python 的 `hashlib.sha1(...).hexdigest()`（小写、定长 40）。不要用 `digest()` 再自己拼。

`str` 那一句是"坑中坑"：`getDeviceId()` 在现代 Android 上大概率返回 `null`，而 Java 的字符串拼接会把 `null` 变成字面量 `"null"`（4 个字符）。自己实现时如果写成空串，整串就短 4 个字符，SHA1 必然对不上。

同理，MAC/蓝牙在 Android 10+ 也可能拿不到，`device` 会随设备环境变化——**它不是一个可写死的常量**，要么按 hook 实测的拼法生成，要么干脆固定一个曾成功过的完整串。

## 6. `password`：AES-128-CBC + 固定 IV

反编译搜 `"password"`，落到：

```
DayimaPrivateUtil.privateStrHandle(明文密码, 手机号)
```

内部两步：

```
key = md5(手机号).hex_lower()[:16]      // 16 个字符
iv  = "yoloho_dayima!%_"                // 固定 16 字符
password = Base64( AES/CBC/PKCS5(明文密码, key, iv) )
```

`AESUtil.genAESCipher` 里就是标准三件套：`SecretKeySpec(key.getBytes(), "AES")`、`IvParameterSpec(iv.getBytes())`、`Cipher.getInstance("AES/CBC/PKCS5Padding")`。

两个细节：

1. **key 取的是 MD5 的 hex 前 16 位字符**，不是 16 字节摘要。所以它是"16 个 ASCII 字符"→ 16 字节 → AES-128。跟上一个案例（唯品会）刚好相反，那边用的是 `digest()`；判断依据只能是看代码里有没有 `.substring(0, 16)`。
2. **iv 恰好 16 字符**，是硬编码业务串 `yoloho_dayima!%_`。少一位直接抛 `InvalidAlgorithmParameterException`。

hook 点选 `AESUtil.encrypt` 的三个入参最省事，一次能同时确认明文、key、iv：

```
lqz12345   9eb091a1fb36369d   yoloho_dayima!%_
```

（`9eb091a1fb36369d` 是手机号 `md5` 前 16 位，换手机号就变——不要当常量抄。）

## 7. `sign`：native 摘要，三条绕法

### 7.1 明文从哪来

`loginByAccount(str, str2)` 里：

```
sb = getDeviceCode() + "user/login" + 手机号 + password密文
sign = Crypt.encrypt_data(0L, sb.toString(), sb.length())
```

`Crypt` 是 JNI 类，`encrypt_data(long, String, long)` 三个参数：占位 `0`、明文串、**明文字符数**（不是字节数）。

hook 一下确认：

```
0   fd6d0ce86280f3fa11a0a0774c06fef2446aee82user/login18953675221WA89qByLlDeaGjmVNzXm/w==   85
```

注意明文里带的是**密码密文**（含 `==` 补位），所以密码换一种加密方式，sign 的输入也跟着变。`85` 与字符串长度一致。

### 7.2 so 里长什么样

`libCrypt.so` 是 64 位，IDA 用 64 位打开，导出符号 `Java_com_yoloho_libcore_util_Crypt_encrypt_1data`（`_1` 是 JNI 对 Java 方法名里 `_` 的转义，`encrypt_data` → `encrypt_1data`）。

函数骨架很短：

```
len  = GetStringUTFLength(str)
p    = GetStringUTFChars(str)
sub_1DA0(0, p, len, out)      // out 是栈上 char[36]
return NewStringUTF(out)
```

`sub_1DA0` 里连续 16 次 `sprintf(out+2*i, "%02x", digest[i])`，最终产出 32 位小写 hex —— 即"16 字节摘要转 hex"。到这一步已经能看出是标准摘要，但课件选择**不继续逆**：字符串格式化的调用点太多，逐个确认输入处理（是否加盐、是否截断）成本高。

### 7.3 四条路线的取舍

| 路线 | 原理 | 跑在哪 | 成本/局限 |
| --- | --- | --- | --- |
| 硬破 so | 读汇编还原算法 | 本地纯算 | 最难，改动/加固后全废 |
| **frida-rpc** | 让 App 里的方法替自己算 | 电脑 + 连着手机 | 依赖 frida、设备、App 在跑 |
| 自建 APK 调 so | 把 so 搬进自己的工程直接调 | 手机上 | 要处理包名/类名/依赖类 |
| unidbg | 用 Java 模拟执行 so | 纯电脑 | 环境补全麻烦，但可离线批量 |

判断标准很简单：**算法价值 < 调用成本时，就走"调它"而不是"抄它"**。这个 sign 只是 md5 类摘要，硬破收益低；而 rpc 能保证结果与服务端一致，先用起来。

## 8. frida-rpc

### 8.1 是什么

frida 的跨进程调用机制：JS 侧用 `rpc.exports` 暴露函数，Python 侧用 `script.exports_sync.xxx(...)` 调用；被调函数里可以 `Java.perform` + `Java.use`，于是等价于"在 App 进程里执行它的 Java 方法"。

课件给的定位很准确：它把"手机上的加密方法"变成一个可远程调用的函数，本质是**把逆向问题转成接口调用问题**。

### 8.2 流程

```
手机端：启动 frida-server → 手动打开 App（让它把 so/类加载进内存）→ 端口转发
电脑端：attach("大姨妈") → create_script(rpc 脚本) → exports_sync 调用
```

`attach("大姨妈")` 用的是**应用名**（也可用包名或 pid）。关键点是"App 必须先跑起来"——`libCrypt.so` 没加载、`Crypt` 类没进内存时，`Java.use` 会失败。

### 8.3 脚本骨架（结构记录，不逐行抄）

```
rpc.exports = {
  xx: function (j2, str, j3) {
     var res;
     Java.perform(function () {
        var Crypt = Java.use("com.yoloho.libcore.util.Crypt");
        res = Crypt.encrypt_data(j2, str, j3);
     });
     return res;
  }
}
```

Python 侧 `script.load()` 后直接 `script.exports_sync.xx(0, 明文, len(明文))`。新版 frida-python 是 `exports_sync`；老版本写作 `script.exports`，混用会报 `AttributeError`。

## 9. frida-rpc 的类型转换（最容易卡住的一段）

跨语言调用的规则只有一条：**Python → JS 必须能 JSON 序列化；JS → Java 必须显式构造 Java 类型**。

### 9.1 Python 能传什么

`dict / list / tuple / str / int / float / True / False / None` 都可以。`bytes`、`bytearray` 不行，直接报：

```
TypeError: Object of type bytearray is not JSON serializable
```

要传二进制就转成整数列表，到了 JS 侧再还原：

```
var bs = Java.array('byte', v1);     // 列表 → Java byte[]
```

### 9.2 JS 侧怎么交给 Java

| Python 传入 | JS 处理 | 交给 Java 的东西 |
| --- | --- | --- |
| `int` / `str` | 直接用 | 基本类型 / `String` |
| `list`（字节） | `Java.array('byte', list)` | `byte[]` |
| `dict` | `TreeMap.$new()` + 循环 `put` | `java.util.Map` |
| 任意字符串拼接 | `StringBuilder.$new()` + `append` | `String` |

`dict → TreeMap` 那段还要注意取值方式：`v4_obj.get("key")` 返回的是 Java 对象，打印或比较前先 `.toString()`；遍历用 `keySet().iterator()`，而不是 JS 的 `for...in`。

这套转换不是 rpc 专属——**任何"Python 驱动 frida 调 Java 方法"的场景都适用**，包括上个案例里 hook 后主动构造 `TreeMap` 参与签名的场景。

## 10. 自建 APK 调 so

思路：把 `libCrypt.so` 搬进自己的 Android 工程，写一个同名类调它，就能脱离 frida、直接在手机上算 sign。

四个关键动作：

1. so 放进 `libs/arm64-v8a/`（按 so 架构建目录），`build.gradle` 里加 `sourceSets { main { jniLibs.srcDirs = ['libs'] } }`
2. 类必须**同包名同类名**：`package com.yoloho.libcore.util; public class Crypt`
3. `System.loadLibrary("Crypt")` + 同样的 `public static native String encrypt_data(long, String, long)`
4. 调用方传同样的三个参数（`0`、明文、长度），把返回值打到日志/界面上

第一步里的"同名"是硬性要求：`Java_com_yoloho_libcore_util_Crypt_encrypt_1data` 这串符号是**静态注册**，运行时按"类全名 + 方法名"去匹配，包名或类名差一个字符就 `UnsatisfiedLinkError`。

课件特别提醒的一点：**如果 so 内部还调用了原 App 的其它类，得把这些类一起补进工程**。so 里出现 `FindClass("com/yoloho/...")` 时，缺类会在运行期抛 `NoClassDefFoundError`——这时候不是 so 的问题，是"依赖没搬全"。

## 11. 代码整合：三个参数串起来

课件最后把三段拼成一个脚本，结构是"两段本地算 + 一段远程调"：

| 步骤 | 做法 | 依赖 |
| --- | --- | --- |
| `device` | 拼接串直接写死（就是 hook 到的那条），`sha1(...).hexdigest()` | 无 |
| `password` | `md5(手机号).hexdigest()[:16]` 当 key，固定 iv，AES-CBC + PKCS7 补位，Base64 | 加密库 |
| `sign` | 先拼 `device + "user/login" + 手机号 + 密码密文`，再走 `exports_sync` 调 App 的 `encrypt_data(0, 串, 串长)` | frida + 真机 + App 在跑 |

三个要点：

1. **拼装顺序有依赖**：`sign` 的明文里含 `password` 的密文，必须先算密码再算 sign，顺序颠倒全错。
2. **两处"写死"性质不同**：`device` 拼接串写死是因为它是设备指纹（换机/换系统就失效）；脚本里注释掉的 `KEY = "9eb091a1fb36369d"` 是手机号 md5 前 16 位，属于"换手机号就变"，留着只是方便调试，不能当通用常量。
3. **请求参数分两处**：query 放 `device` 与设备信息（`ver=630`、`screen_width/height`、`model`、`sdkver`、`releasever`、`channel` 等），body 放 `username / password / sign / androidid / mac / imei / density / brand`。抓包比对时一起看，才能区分是"错了一个参数"还是"整包都不对"。

## 12. 坑与要点清单

1. **先绕检测再谈逆向**：启动即拦截的 App，root 弹窗不解决，抓包和 hook 都无从下手。
2. **别只挡 `isRooted`**：`isSimulator` 和第三方 SDK 的 `checkEnvSafe` 要一起处理，否则提示反复弹。
3. **Shamiko 与"强制排除"互斥**：配置 denylist 但不要开 enforcement，这是模块 README 明写的条件。
4. **银行类还会查 Magisk 包名**：光刷模块不够，得用"隐藏 Magisk 应用"改掉包名。
5. **通用加密 API 要用业务方法门控**：`MessageDigest.update` 全 App 都在用，只有 `setDeviceCode` 里那一次才是目标。
6. **`null` 会变成字符串 `"null"`**：Java 的 `String + null` 是 4 个字符，自己实现时写成空串就全错。
7. **`device` 不是常量**：IMEI / MAC / 蓝牙 MAC 都受系统版本与权限影响，换机就变。
8. **注意 key 是 hex 还是 digest**：本案例 `md5(...).substring(0,16)` 是 hex 前 16 字符（16 字节 ASCII）；换到别的 App 可能是 16 字节二进制，看代码确认。
9. **iv 长度必须 16**：`yoloho_dayima!%_` 刚好 16 字符，抄错一个字符就是 padding/长度异常。
10. **sign 的明文含密码密文**：密码加密方式一改，sign 输入跟着变，两个参数要一起改。
11. **`encrypt_data` 第三个参数是字符数**：传 `len(str)` 即可，别传字节长度（有中文时会不一致）。
12. **frida-rpc 不能传 bytes**：转 `list`，JS 侧 `Java.array('byte', ...)` 还原。
13. **rpc 必须等 App 起来**：so 没加载、类没进内存时 `Java.use` 直接失败；流程是"先开 App，再 attach"。
14. **`exports_sync` 与老版 `exports` 不通用**：按 frida 版本选，报 `AttributeError` 先查这里。
15. **so 是 64 位就用 64 位 IDA**：符号、偏移、寄存器都对不上时先看架构。
16. **自建 APK 的包名类名不能改**：静态注册靠"全限定类名 + 方法名"绑定，改名必崩。
17. **rpc 不是终态**：它依赖 frida + 真机 + App 运行；要批量/离线，得走 unidbg 或把 so 抽出来自建 App。

## 13. 本案例关键知识清单

- **Root 检测的检测面**：固定路径下的 `su` 文件 + 模拟器特征（`Build.FINGERPRINT` 等）+ 第三方 SDK 的独立环境检查。
- **四类绕过手段**：开源 antiroot hook 脚本、Shamiko/Zygisk 模块（denylist 不开 enforcement）、业务层 hook 检测函数、AOSP 改 su 名。
- **`device` 指纹算法**：IMEI + android_id + Build 13 字段 + WiFi MAC + 蓝牙 MAC 顺序拼接 → SHA1 → 小写 hex。
- **"业务方法门控通用 API"**：hook `setDeviceCode` 置标记，只在标记内打印 `MessageDigest.update`。
- **`password` 算法**：AES-128-CBC/PKCS5，key = `md5(手机号)hex[:16]`，iv = 固定 16 字符业务串，输出 Base64。
- **JNI 符号命名**：`Java_包名_类名_方法名`，Java 名字里的 `_` 转义成 `_1`；静态注册依赖类名匹配。
- **native 摘要的识别**：`GetStringUTFLength` + `GetStringUTFChars` + 循环 `sprintf("%02x")` = 16 字节摘要转 32 位 hex 的典型形态。
- **"不硬破"的四条替代路线**：frida-rpc、自建 APK 调 so、unidbg、纯算还原；按"算法复杂度 vs 调用成本"选。
- **frida-rpc 机制**：`rpc.exports` ↔ `exports_sync`，在 App 进程内执行 Java 调用，等价于远程函数。
- **跨语言类型转换**：Python 侧必须可 JSON 序列化；字节走 `list → Java.array('byte')`；字典走 `TreeMap.$new()`。
- **自建 APK 调 so 的四要素**：so 放对架构目录、`jniLibs.srcDirs`、同包名同类名、补齐 so 依赖的其它类。
