## 1. 三天课件要点（复刻依据）

| 课次 | 破解对象 | 结论 |
| --- | --- | --- |
| day17 | `POST /x/report/click/android2` 请求体 | TreeMap 排序拼串 → `sha256(明文 + 9cafa6466a028bfb)` → 拼 `&sign=` → 整体 AES-256-CBC（key `fd6b639dbcff0c2a1b03b389ec763c4b` / iv `77b07a672d57d64c`） |
| day17 | did | `mac|蓝牙|设备总线|sn` → 首字节异或长度 → 链式异或 → Base64 去 `=` |
| day18 | 请求头四指纹 | buvid（`XW/XY/XX/XZ` + md5 取 2/12/22 位 + 全串，大写）、session_id（4 随机字节 hex）、fp_local（`md5(buvid+model+band)` + 14 位时间 + 8 随机字节 + 校验码） |
| day19 | `POST /x/report/heartbeat/mobile` | session = `sha1(buvid + 毫秒时间戳 + rand(0,1e6))`，无盐 |
| day19 | heartbeat sign | 不在 Java 层；`libbili.so` 动态注册，`md5(排序明文 + 560c52cc + d288fed0 + 45859ed1 + 8bffd973)` |

## 2. 复刻方案

```
┌─────────────── 真机 Pixel 2 (Android 11) ───────────────┐
│ BiliReplica.apk (com.example.bililike)                  │
│   MainActivity  启动即自检                               │
│   DeviceProfile 生成 did/buvid/session_id/fp_local/remote│
│   ClickReport   TreeMap + SHA256盐 + AES-CBC             │
│   HeartbeatReport  SHA1 session + native MD5 四盐        │
│   BiliSign ──► libbili.so (JNI_OnLoad RegisterNatives)   │
└───────────────┬─────────────────────────────────────────┘
                │ adb reverse tcp:8899
┌───────────────▼──────────────┐
│ PC: mock_server.py :8899     │  独立验签：AES 解密 / 重算 SHA256 / 重算 MD5
│ verification_log.jsonl       │  逐条落盘，作为评测证据
└──────────────────────────────┘
```

关键设计：
1. 算法参数与课件完全一致（同一个盐、同一个 key/iv、同四段盐），保证 hook 出来的值与
   课件截图能对上。
2. 服务端不复用客户端代码，用 Python + pycryptodome 独立实现验签，避免「自己验自己」。
3. 再写一份 `client_replica.py` 作为第二实现，三份实现（App / mock / Python）互相对账。

### 3.2 编码（对应关系）

| 文件 | 做的事 |
| --- | --- |
| `app/jni/bili_sign.c` | 手写 MD5（init/update/final/hex）；`JNI_OnLoad` 里 `RegisterNatives` 注册 `nativeSign`；明文 1 次 update + 四段盐各 1 次 update；结果 `NewStringUTF` 返回；`bili_md5_update` 加 `noinline` 并导出，供 hook |
| `BiliCrypto.java` | sha256(明文‖盐)、AES/CBC/PKCS5、md5、hex、fp 校验码 |
| `DeviceProfile.java` | did 异或链、buvid XW、session_id、fp_local/fp_remote |
| `ClickReport.java` | TreeMap 排序拼串 → 盐签 → `&sign=` → AES |
| `HeartbeatReport.java` | session SHA1、statistics 紧凑 JSON + URL 编码、调用 native 签名 |
| `ReportInterceptor.java` | 组装 Buvid / Device-ID / fp_local / fp_remote / session_id / UA |
| `MainActivity.java` | 启动自动跑自检，结果打 logcat（tag `BiliReplica`）并显示在屏幕 |

### 3.3 构建（不用 Gradle）

`build.ps1` 七步：清理 → `aarch64-linux-android21-clang` 编 so → `aapt2 link` 出壳 APK →
`javac` 编 Java → `D8` 出 dex → Python 把 dex/so 塞进 APK → `zipalign` + `apksigner`。

产物：`BiliReplica.apk` 25,049 字节，`libbili.so` 9,376 字节（arm64-v8a）。

## 4. 动态验证（Frida，复刻 day18/19 的手法）

设备端 `frida-server` 常驻，PC 端 `run_hook.py` 负责 spawn → 挂脚本 → 等自检 → 落盘。

| 脚本 | 复刻的手法 | 实测输出 |
| --- | --- | --- |
| `01_hook_crypto.js` | hook `SecretKeySpec` / `IvParameterSpec` / sha256 入口 | `salt=9cafa6466a028bfb`、`key=fd6b639dbcff0c2a1b03b389ec763c4b`、`iv=77b07a672d57d64c` |
| `02_hook_headers.js` | hook 拦截器的头组装 | 打出 Buvid / Device-ID / fp_local / fp_remote / session_id 五个值 |
| `03_hook_register_natives.js` | 枚举 `libart.so` 的 RegisterNatives，按类名过滤，读 `JNINativeMethod[]` | `name=nativeSign sig=(Ljava/lang/String;)Ljava/lang/String; module=libbili.so offset=0x23cc` |
| `04_hook_native_md5_update.js` | 按「基址 + 偏移」挂 update，打印每段入参 | 偏移 0x17dc；两组心跳各 1 段明文 + 4 段盐（`560c52cc` `d288fed0` `45859ed1` `8bffd973`，各 len=8） |
| `05_hook_newstringutf.js` | hook `NewStringUTF`，过滤长度 32 的纯 hex | 命中 md5，backtrace 栈顶 `libbili.so!native_sign+0x19c` |

要点复述：
- 偏移是稳定的、绝对地址每次都变；脚本打印的是 `fnPtr - module.base`。
- 四段盐在 update 里是「8 字节 + 8 字节 + 8 字节 + 8 字节」，hook 一眼能看出来。
- `NewStringUTF` 是 so 把字符串交回 Java 的必经之路，长度/正则过滤足够定位签名。

## 5. 静态核对（课件原 APK，只读）

```powershell
aapt2 dump badging 软件\B站-v6240.apk
# package: name='tv.danmaku.bili' versionCode='6240300' versionName='6.24.0'
```

对 59 个 dex/so 做字节级搜索：

| 常量 | 命中位置 |
| --- | --- |
| `x/report/click/android2` | classes5.dex |
| `x/report/heartbeat/mobile` | classes5.dex、classes9.dex |
| `9cafa6466a028bfb`（SHA256 盐） | classes10.dex |
| `fd6b639dbcff0c2a1b03b389ec763c4b`（AES key） | classes10.dex |
| `77b07a672d57d64c`（AES iv） | classes10.dex |
| `fp_local` | classes3.dex、classes5.dex |
| `560c52cc`（MD5 盐） | **dex 里没有**，与课件「盐在 so 里」一致 |

补充观察：
- APK 只带 `lib/armeabi-v7a/libbili.so` 和 `lib/x86/libbili.so`，**没有 arm64**。Pixel 2 会以
  32 位模式加载，正好对应课件「32 位 so 偏移要 +1」的经验。
- 四段盐在 so 里也不是明文 ASCII（`strings` 搜不到），和课件里 `sprintf("%08x", v22)` 把整数
  格式化成 8 位 hex 再 update 的写法吻合——所以只能 hook update 拿值，不能靠搜字符串。

## 6. 踩坑与修复（都是实打实遇到的）

| # | 现象 | 原因 | 修复 |
| --- | --- | --- | --- |
| 1 | `build.ps1` 报「字符串缺少终止符」 | Windows PowerShell 5.1 把无 BOM 的 UTF-8 脚本按 ANSI 读，中文注释撑坏了引号 | 脚本转成 UTF-8 **带 BOM** |
| 2 | `javac` 找不到 | PATH 里只有 JRE 的 `java.exe` | 脚本里显式指定 `C:\Program Files\Java\jdk-1.8\bin` |
| 3 | `d8.bat` 退出码 0 但没产出 dex | `.bat` 在中文路径下参数传递异常 | 改成 `java -cp build-tools\...\lib\d8.jar com.android.tools.r8.D8` |
| 4 | mock server 起不来：`UnicodeDecodeError 0xc9` | `HTTPServer.server_bind()` 调 `socket.getfqdn()`，本机主机名是中文 | 重写 `server_bind`，跳过 getfqdn |
| 5 | Frida 挂上 update 但一次都不触发 | clang `-O2` 把导出函数内联进了调用方 | `__attribute__((noinline))` 后重建 |
| 6 | RegisterNatives 有符号无回调 | 脚本没包在 `Java.perform` 里，`Java.vm.tryGetEnv()` 返回 null | 改为 `Java.perform(hookRegisterNatives)` |
| 7 | App 侧显示 FAIL 但服务端 verified=true | `json.dumps` 默认带空格，客户端按 `"verified":true` 匹配不到 | 比较前去掉空格 |
| 8 | Python 侧 AES 报「must be padded」 | pycryptodome 不像 Java 的 PKCS5Padding 自动补块 | 手动 PKCS#5 填充 |
| 9 | Frida 日志文件只写入第一行 | frida-python 的 `type=log` 消息只走 log handler，不 emit `message` 事件，回调里的 `log()` 从未执行 | 改用 `script.set_log_handler()` |
| 10 | 日志缺后半段（只抓到开始心跳） | `device.kill()` 后会话断开，回调线程里未处理的消息丢失 | 先落盘再 kill；并把等待窗口从 12s 提到 40s（hook 拖慢启动） |
| 11 | App 显示 3/3 PASS，`/summary` 数字却不涨 | `Invoke-WebRequest` 命中 HTTP 缓存，读到旧响应 | 统计以 `verification_log.jsonl` 重算为准 |

## 7. 代码总结：这套实操到底做了什么

1. **请求体侧（day17）**：把 18 个字段按 key 排序拼成 `k=v&...`，用固定盐做 SHA256，
   拼上 `&sign=` 后整体 AES-256-CBC 加密，得到二进制请求体；设备号 did 用「异或链 + Base64」。
2. **请求头侧（day18）**：生成并携带 buvid、device-id、fp_local、fp_remote、session_id，
   其中 fp_local 是「md5 + 秒级时间 + 随机 + 两位校验码」，校验码是把前 62 个字符按两位
   一组当 hex 累加后 `%256`。
3. **完播率侧（day19）**：session 用 `sha1(buvid+ms+rand)` 无盐生成；sign 在 native 层，
   `md5(排序明文 + 四段盐)`，拼在表单体尾部；开始/结束两条心跳的 `played_time`、
   `paused_time`、`total_time` 由 `start_ts` 推算。
4. **验证侧**：mock 服务端独立解密/重算，三份实现（App、Python、服务端）互相对账；
   Frida 五个 hook 把 Java 层常量与 so 层盐全部还原出来，偏移量可复用。
5. **工程侧**：不用 Gradle，aapt2/javac/d8/clang/apksigner 全手动串起来，APK 只有 25KB，
   构建时间十几秒，适合反复改算法做实验。

## 8. 局限与未做的事

- 没有对 B站线上接口发任何业务请求，因此**不产出真实播放量/完播率数据**，这是刻意为之。
- 没有使用 IDA/GDA：自建 so 把 update 导出了，偏移由脚本算；真实样本仍需 IDA 按偏移定位
  （课件里 `sub_22B0`、`0x1c97` 那一套）。
- 没有复刻「换 IP / 代理池」部分：本地 mock 不涉及风控，同 IP 限制无从验证。
- `aid/cid` 用固定值（8848 / 175882888），真实场景应从 Web 页 `var options = (...)` 或
  `x/player/pagelist`、`x/web-interface/view` 取——这部分只在笔记里记录，未在本工程实现。
